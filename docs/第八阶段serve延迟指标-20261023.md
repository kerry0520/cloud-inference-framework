# 第八阶段：真实 `vllm serve` 路径上的延迟指标（2026-10-23）

前七个阶段的数字全部来自**进程内引擎**：`LLM` 直调、配对 ABBA、请求级或轮级重采样。它回答的是
“min-p 内核快了没有”，不回答招聘面试里最常问的那一层：**真实 HTTP 服务下 TTFT/TPOT/P99 变没变**。
本轮搭一个可复现的 serve 测试台，把补丁接到真实采样路径上，先证明“接进去了、数值没坏”，再看
端到端能不能看见收益。

## 1. 方法

- 被测服务：`python -m vllm.entrypoints.cli.main serve <model> --dtype float16
  --max-model-len 2048 --max-num-seqs 8 --gpu-memory-utilization 0.6`，模型 Qwen3-0.6B，
  端口 8123，每场新起进程、测完 `SIGTERM`→`SIGKILL` 并等端口释放。
- 两臂：`base`（上游内核）与 `patched`（`patches/mrv2_min_p.py`）。补丁**不改 vllm-src**：
  `scripts/sitecustomize.py` 在解释器启动时挂 import 钩子，等
  `vllm.v1.worker.gpu.sample.states` 导入完成后把模块全局 `apply_min_p` 换成候选实现；
  只有设了 `CI_MINP_PATCH` 的进程才动作（见 §2 的 `base_installs=0`）。
- 为什么不用 `--worker-extension-cls` 自动安装：`vllm/v1/worker/worker_base.py:289-315` 把扩展类
  **追加到 `__bases__` 末尾**，并断言扩展的非 dunder 属性与 worker 不重名；`init_device` 是
  Worker 自己的方法，扩展类无法覆盖，所以初始化时机的钩子挂不上去。
- 会话顺序 ABBA：每块 `base, patched, patched, base`，共 2 块 8 场；两臂的会话在同一块内相邻，
  把机器状态漂移摊到两臂。
- 每场两个相位：`nop`（`min_p=0`，vLLM 在 `states.py:94` 直接 return，不启动 min-p 内核）与
  `minp`（`min_p=0.1`）。两相位**prompt 池不相交**（`prompt_set(0)` / `prompt_set(1)`），因为
  prefix caching 默认开启（`vllm/config/cache.py:142`），同一条 prompt 第二次到达会被缓存接走。
- 每相位 64 条请求、并发 8、分 8 波发完；prompt 128 个合成 token，`max_tokens=64`、
  `min_tokens=64`、`temperature=0.8`、`ignore_eos`、每请求固定 seed、流式返回
  （`stream_options={"include_usage": true}`）。warmup 用第三组 prompt，按全并发跑 2 轮 ×
  `min_p ∈ {0, 0.1}`，把编译/cudagraph 捕获挡在测量之外。
- 指标：TTFT = 首个 chunk 到达；ITL = chunk 间隔；TPOT = 总时延减去 TTFT 后按
  `usage.completion_tokens` 校正；另记 req/s、tok/s、每请求输出 sha1（两臂比对用）。
- 统计粒度：每场每相位 64 条 pooled 出 p50/p99；两臂比较用**会话中位数**（每块 base 两场 vs
  patched 两场），不做请求级 bootstrap——同一波并发里的请求互相排队，不是独立样本。

复现：

```bash
bash scripts/run_stage.sh serve          # 8 场，约 10 分钟
bash scripts/run_stage.sh serve-order    # 反序诊断：minp 先跑，4 场
python scripts/serve_table.py results/serve-<ts>/summary.json
```

## 2. 接入与数值一致性（`results/serve-20261023T045524Z-WU58ZQ/`）

`status.json`：`passed=true`，8/8 场 ok，`patched_installs=4`、`base_installs=0`、
`verify_mismatches=0`、`paired_blocks=2`；退出码 0。

- patched 臂的 worker 日志各有一次 `CI_MINP_INSTALLED`，base 臂一次都没有 → 补丁只进了该进的臂。
- patched 臂每场前 48 次调用同时跑上游实现与候选实现（4 场共 192 次），`torch.equal` 逐字节比对 logits：
  `mismatches=0`，且实测形状是 `(8,151936)`、`(3,151936)`、`(2,151936)`、`(1,151936)`（收尾步行数不足 8）。
- 两臂输出文本 255/256 完全一致，1 条不同——同 seed、同 `min_p`、同 logits 时两次采样仍可能
  不同（torch 采样在浮点并列上的非确定性），不能当成数值错误；反过来也说明“逐字节 logits
  相等”才是强证据。

## 4. 结论

1. **接入成立**：补丁在真实 serve 进程的采样路径上执行（安装计数、内核形状、192 次逐字节 logits
   比对），不是“离线能跑、上线不生效”。
2. **服务级收益不可分辨**：四组配对的符号互相矛盾，幅度都在 ±5% 内，TPOT 只有 ±1.7%；
   离线配对给的 −1.10%（CI −1.37…−0.85）在这个测试台的噪声里看不出来。诚实说法是
   “本机并发 8、64 token 输出下，1.1% 的步级收益落在噪声内，不能宣称端到端提速”——
   与第五阶段“上限 1.18%、不能冒充整请求提速”的口径一致，不是新结论，而是**换一个口径复核后仍然成立**。
3. 想在这个口径下分辨 1% 级别的差异，需要比 8 场多得多的重复，或者更小的观测噪声（例如把
   TTFT 的 p99 长尾先压掉，见下条）；本轮不做，因为成本与结论价值不匹配。
4. **服务级看不见的机制**（§6 反序诊断）：打开 `min_p=0.1` 让 decode 步在服务里慢 ~1.2 ms
   （5.5→6.9），而 min-p 内核只有 ~123 µs。补丁压掉的是这 1.2 ms 里的一小截，所以服务级收益
   天然是 1% 量级；要把 min-p 的收益做进端到端，得先回答那 ~1.1 ms 花在哪。这条是本轮唯一
   新提出的可追问题。

## 5. 限制与未验证

- 单机单卡、0.6B、合成 prompt、固定并发 8、输出 64 token；TTFT 只有 ~70 ms，min-p 那几十微秒
  没有放大空间。
- 会话级配对（2 块）只能压到 ±2%，不是请求级置信区间；跨块方向不一致本身就是噪声的证据。
- base 臂 `minp` 相位的 TTFT p99 是 295.6 ms，patched 是 87.5 ms；这来自个别场次的尾部事件
  （首 token 编译/调度抖动），不是补丁带来的，样本量不足以解释它。
- `minp` 相位比 `nop` 相位慢 1.2–1.3 ms/步（TPOT 5.7→7.0）。§6 的反序对照证明它跟着 min_p
  走、不跟着相位位置走，但**成因没定位**：不能写“min-p 开销 1.2 ms 都能优化”，也不能把这条
  算到补丁头上——它解释的是收益上限，不是补丁的缺陷。
- 没有测并发扫描（1/2/4/8/16）、没有测长输出、没有测 prefix caching 命中率、没有和 `nop`
  之外的采样参数（top_p/top_k）交叉；这些是后续 serve 阶段可以展开的面。

## 6. 反序诊断：1.2 ms/步跟着 min_p 走，不跟着相位位置走

`results/serve-order-20261023T050646Z-iQiesm/`：`passed=true`，4/4 场，`patched_installs=2`、
`base_installs=0`、`verify_mismatches=0`，token agreement 126/128；相位顺序倒置为
`minp → nop`，其余参数与主实验相同（`--verify-first 0`，不付逐字节比对的开销）。

| 臂 | 相位 | TTFT p50 | TTFT p99 | TPOT p50 | 总时延 p50 | tok/s |
|---|---|---|---|---|---|---|
| base | minp | 72.5 | 207.9 | 6.9 | 507.0 | 993 |
| base | nop | 69.9 | 79.4 | 5.5 | 415.5 | 1210 |
| patched | minp | 68.0 | 78.6 | 6.7 | 486.5 | 1042 |
| patched | nop | 67.1 | 74.8 | 5.8 | 431.7 | 1194 |

把顺序倒过来后，minp 相位**仍然**比 nop 慢：base +1.4 ms/步、patched +0.9 ms/步；主实验里同向
（base +1.24、patched +1.30）。两个方向的四组测量都指向同一件事，所以 §5 里“1.2–1.3 ms/步”
不是热漂移，而是**打开 `min_p=0.1` 本身带来的路径开销**：

- 纯上游（base 臂）5.5→6.9 ms/步，慢约 25%；
- min-p 内核微基准在 batch 8 只有 ~123 µs（上游）／14 µs（补丁），也就是补丁压掉的那 ~109 µs
  只占这 1.2 ms 的一小截。
- 机理未定位：可能在内核之外的张量搬运/同步/图捕获边界上（`states.py:94` 的
  `np.all(self.min_p.np[...] == 0.0)` 每步做一次主机侧判断、min_p 非零时才进入的计算链等），
  本轮没有剖析，**不归因、不作为结论**，列为下一步待查问题。
- 它顺带解释了 §4 的“服务级看不见”：整条 min-p 路径在服务里的固定成本约为内核收益的十倍，
  只要这 1.2 ms 还在，把内核从 123 µs 压到 14 µs 在端到端就仍然只有 1% 量级。
