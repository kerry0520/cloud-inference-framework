# 第五阶段：端到端配对、单参数带宽模型与三张图（2026-10-17）

起点 `0525d75`。第四阶段交付了可审查的 min-p 补丁与引擎内逐字节验证，但端到端只有
4 次调用、两轮块级计时，既没有区间，也没有解释"局部 8.9× 为什么只剩 1%"。这一轮补两件事：

1. 用配对 ABBA + 轮级 bootstrap 给出整请求收益的区间，并用内核成本算出可对照的上限；
2. 用留一法的单参数模型检验"decode 步时间 ∝ 权重字节"，包括从未参与拟合、且在 CUDA 图外的 `lm_head`。

## 方法

### 配对 A/B（`scripts/abba_patch.py`）

- 同一个引擎进程、同一个 dispatch 包装：两臂只有内核实现不同（`base` 调 wheel 里的
  `apply_min_p`，`candidate` 调 `patches/mrv2_min_p.py` 的 `apply_min_p`）。两臂都常驻，
  用 `minp_select` 翻转标志，避免每次调用重新 import 模块（第一版每次都 import，见失败表）。
- 24 轮 × 每轮 4 次调用，顺序 `ABBA` / `BAAB` 交替；每轮两臂各 2 次取均值，得到 24 个
  轮级配对差。区间由 10,000 次轮级 bootstrap 重采样给出（95% 分位）。按轮而不是按请求做
  区间，因为同一轮内的请求共享同一次调度状态、不独立。
- 两个指标：
  - `wall`：`perf_counter` 包住 `llm.generate`，含客户端与调度开销；
  - `decode`：vLLM 的 `first_token_ts` / `last_token_ts` 差值除以 token 间隔数，
    只反映逐 token 解码。
- 固定条件：Qwen3-0.6B、FP16、prompt 128 token、输出 64 token、temperature 0.8、
  min_p 0.1、每请求固定 seed、prefix caching 关闭、batch 1/2/4。
- 数值等价单独做：等价相位按 `base, candidate, candidate, base` 生成 4 次并比较 token id；
  更强的判据是第四阶段的 filtered-logits 逐字节一致（`results/minp-patch-engine-20261017T095122Z`）。
- 派发证明：patched 臂的内核计数来自 worker 扩展（`_min_p_partial_max` +
  `_min_p_apply_threshold`），并断言旧 `_min_p_kernel` 为 0。

### 单参数带宽模型（`scripts/roofline_model.py`）

对每个"每步正好把整块权重读一遍"的角色（`qkv_proj`、`o_proj`、`gate_up`、`down_proj`、
`lm_head`），令 `time = bytes / B`。用留一法检验：每个角色只用其余四个角色拟合出 `B`，
再预测自己，残差才是有信息量的量。字节数来自权重形状（`attribution.json` 的 `weight_bytes`
× 每步内核数），时间来自同一份逐层归因。

## 结果

### 端到端（`results/abba-20261017T103216Z`，EXIT=0）

| batch | 上游 wall 中位 | 补丁 wall 中位 | wall Δ%（95% CI） | decode Δ%（95% CI） | id 与首个 base 相同（base / patched） |
|---|---|---|---|---|---|
| 1 | 295.5 ms | 290.7 ms | −1.35 [−1.63, −1.14] | −1.58 [−1.82, −1.51] | 48/48 / 48/48 |
| 2 | 330.0 ms | 326.6 ms | −1.16 [−1.69, −0.35] | −1.10 [−1.37, −0.85] | 48/48 / 48/48 |
| 4 | 350.3 ms | 346.2 ms | −1.02 [−1.21, −0.25] | −1.21 [−1.52, −0.68] | 44/48 / 47/48 |

三个 batch 的 95% 区间都排除 0，方向和幅度一致：整请求快 1% 左右。

**与内核成本上限的一致性检验**：profiler 下上游 min-p 每次调用 62.5 µs（12 次累计
750.37 µs），候选每次约 5.6 µs（24 次启动累计 67.20 µs）；batch2 的 decode 步是
4.812 ms，预期节省 `(62.5 − 5.6) / 4812 ≈ 1.18%`，实测 `1.10% [0.85, 1.37]`。
两者在区间内重合，说明"局部 8.9×、整请求 1%"不是两个孤立数字，而是同一个分母的结果。

batch1 的实测节省（1.58%）更大，方向与"大词表 + 小 batch 时 min-p 相对更贵"一致，
但本轮没有单独测 batch1 的引擎内内核时间，只能算旁证。

### 采样 id 不可复现（重要教训）

第一版脚本断言"跨臂 token id 相同"，在 batch4 第 1 轮失败。检查失败运行的 `timing.jsonl`
发现：**同一个 arm 的两次相同调用也会差 1 个 token**（第 3 个 token，之后又收敛）。也就是说
这台机器上的 vLLM 采样不是逐位可复现的，token id 只能当旁证，不能当数值等价的判据。

因此最终版：等价相位（A/B/B/A）记录 4 次调用是否全等（本次三个 batch 全部相等），
timing 阶段不再断言 id，只统计与首个 base 调用的相同率；数值等价以第四阶段的
filtered-logits 逐字节一致为准。batch4 的漂移是双向的：base 臂 44/48、patched 臂 47/48
与首个 base 相同，首个分歧都在第 3 个 token——两臂幅度相当，说明是采样器状态而不是补丁差异。

### 第二轮独立复现与 batch 8（`results/abba-scale-20261018T035002Z`）

第二天换了一个引擎会话、不改代码，把 batch 加到 8 重跑一遍（`run_stage.sh abba-scale`）。
这一步同时做两件事：独立复现第一轮，以及检验"收益 ∝ min-p 开销占比"的预测——decode 步随
batch 变长，若分子是固定的约 57 µs，百分比就应当随 batch 稀释。

| batch | run A（10-17）decode Δ%（95% CI） | run B（10-18）decode Δ%（95% CI） | run B wall Δ%（95% CI） | run B decode 步 | run B 实测节省 | 模型预测 |
|---|---|---|---|---|---|---|
| 1 | −1.58 [−1.82, −1.51] | −1.23 [−1.61, −0.88] | −1.17 [−1.45, −0.75] | 4.294 ms | 53.8 µs | −1.32% |
| 2 | −1.10 [−1.37, −0.85] | −1.00 [−1.21, −0.82] | −0.42 [−1.33, +0.11] | 4.485 ms | 45.7 µs | −1.27% |
| 4 | −1.21 [−1.52, −0.68] | −0.81 [−2.53, −0.46] | −0.61 [−2.30, −0.13] | 4.785 ms | 69.2 µs | −1.19% |
| 8 | — | −0.91 [−1.55, −0.75] | −0.69 [−1.33, −0.54] | 4.954 ms | 54.9 µs | −1.15% |

模型列仍用"上游 min-p − 候选 min-p ≈ 56.9 µs"除以该 batch 的 decode 步，没有为 run B 重新拟合。

- **两次会话方向与量级一致**：四个 batch 的 decode 区间全部排除 0；run A 的 1/2/4 与 run B 的
  1/2/4 逐点接近（batch2 两次都是 −1.0% 到 −1.1%；batch1 的 −1.58% 与 −1.23% 区间相接）。
- **分子几乎是常数**：run A 的节省 75.0 / 53.7 / 58.0 µs，run B 为 53.8 / 45.7 / 69.2 / 54.9 µs，
  两轮平均 62.2 µs 与 55.9 µs，落在 profiler 推得的 56.9 µs 附近；百分比随 decode 步变长而下降。
  这是"固定节省 ÷ 越来越大的整步"的算术，不是优化变弱。
- **wall 仍然更钝**：run B 的 batch2 wall 区间含 0（[−1.33, +0.11]），batch4 区间也宽。
  两轮一致地说明：1% 量级的效应要用 decode 指标测量，wall 只能作旁证。
- **会话间绝对值不可比**：run A 的 decode 步是 4.49–5.13 ms，run B 是 4.29–4.95 ms（快约 4%），
  与第三阶段"时钟状态不可跨进程比较"一致；百分比只在同一会话的配对内解释。
- 复现命令：`dsh-stage.sh abba-scale`（同一脚本，仅 `--batches 1,2,4,8`）。

### 单参数模型（`results/roofline-20261017T102511Z`，EXIT=0）

| 角色 | 字节/步 | 实测 µs | 留一法预测 µs | 残差 | 其余四角色拟合 B |
|---|---|---|---|---|---|
| qkv_proj | 234.9 MB | 629.05 | 625.50 | −0.6% | 375.5 GB/s |
| o_proj | 117.4 MB | 338.07 | 310.37 | −8.2% | 378.4 GB/s |
| gate_up | 352.3 MB | 909.69 | 951.73 | +4.6% | 370.2 GB/s |
| down_proj | 176.2 MB | 526.96 | 459.71 | −12.8% | 383.2 GB/s |
| lm_head | 311.2 MB | 774.07 | 849.19 | +9.7% | 366.4 GB/s |

全体拟合 `B = 375.09 GB/s`，留一法最大残差 12.8%。`lm_head` 从未参与自己的拟合，
而且它在 CUDA 图外、走 eager 路径（774 µs 里只有一次 311 MB 只读），仍然落在 +9.7% 内。
这让"时间 ∝ 权重字节"不是同义反复，而是一个可被推翻的预测。

仍有一个未解释的矛盾：standalone 实测的流带宽上限只有 322–347 GB/s（copy / sum /
Triton 纯读内核），低于引擎内隐含的 375 GB/s。时钟假设无法证实（nvidia-smi 在 WSL 下
单次查询上百毫秒，分阶段采样几乎全是 0–1 个样本；也没有锁频权限），因此这里只把它当作
经验拟合常数，不声称它等于硬件峰值。

| `abba-20261017T102757Z` | 首次 EXIT=0，但每次调用重新 import 模块；wall 中位 +0.10%/+0.71% 与 decode −1.41%/−1.02% 矛盾 | 两臂常驻 + `minp_select` 翻转，去掉 import/GC 噪声 |
| `abba-20261017T103120Z` | `Call to collective_rpc method failed: patched` | 选择方法只接受 `base`/`candidate`，把 arm 名映射后重跑 |

`102757Z` 的数字（wall −0.37%/+0.10%/+0.71%，decode −1.83%/−1.41%/−1.02%）不再引用，
只作为"测量方式会影响结论"的证据保留。

## 限制

- 单机、单模型、RTX 5060 Laptop 8 GB；不外推到服务器或其他 batch。
- 单步时间来自带 profiler 的 trace，含 profiler 开销；不能当无诊断性能。
- 未锁频、未测功耗；`375 GB/s` 是拟合常数，不是硬件上限。
- batch4 的采样漂移说明 1% 量级的比较必须配对 + 区间，不能比单次运行。
- 只测了 `min_p = 0.1`；`min_p = 0` 走原路径（第四阶段已断言不启动内核）。
