# 项目叙事（面试版，2026-10-17）

目标：把已有的工程与实验压缩成一段可复述、可追问、数字可核对的主结果。所有数字都能在
`results/` 里找到对应目录、退出码与 sha256（见文末索引）。

## 一句话

在 vLLM 0.31 的真实采样路径上，用 Triton 重写 min-p 内核并做成可审查补丁：局部 8.9×，
整请求 **−1.10%（95% CI [−1.37, −0.85]）**；这个 1% 不是"优化没生效"，而是 min-p 只占
单步 1.3%，同时用逐层归因证明了剩下的时间由权重流带宽决定，不是算力。

## 三个必须一起说的数字

| 数字 | 含义 | 来源 |
|---|---|---|
| 3,792 µs | batch2 单步内核时间；其中 83.8% 是 GEMM，`lm_head` 一项 774 µs（20.4%）且在 CUDA 图外 | `docs/第三阶段逐层归因与带宽对照-20261017.md` |
| 8.9× | V151936 batch2 的 min-p 内核局部加速（122.9 → 14.0 µs） | `results/minp-micro-*`、第五阶段图 3 |
| −1.10% | 整请求 decode 配对差，24 轮 ABBA，bootstrap 95% CI [−1.37, −0.85]；第二天换会话复跑得 −1.00% [−1.21, −0.82]，batch 8 为 −0.91% [−1.55, −0.75] | `results/abba-20261017T103216Z/summary.json`、`results/abba-scale-20261018T035002Z/summary.json` |

**为什么局部 8.9× 只剩 1%**：profiler 下上游 min-p 每次 62.5 µs、候选每次约 5.6 µs，
decode 步 4.81 ms，`(62.5−5.6)/4812 = 1.18%`，实测 1.10% [0.85, 1.37]，在区间内重合。
局部倍率的分母是内核，整请求倍率的分母是整步——这是算术，不是调参。

**为什么不是偶然**：第二天换引擎会话复跑（batch 1/2/4/8），batch2 仍是 −1.00%
[−1.21, −0.82]；四个 batch 的 decode 区间全部排除 0。节省的绝对量几乎不变
（两轮平均 62.2 µs 与 55.9 µs，profiler 推得 56.9 µs），百分比随 decode 步从 4.29 ms
增长到 4.95 ms 而稀释到 −0.91%——与"固定分子 ÷ 变大分母"的预测一致。

## 项目实际上回答的三个问题

1. **一步 3.8 ms 花在哪？** 同一份 trace 里 385 个内核、28 层 × 13 个、固定序列；
   按角色拆开后 GEMM 3,177.84 µs，`gate_up` 909.69（24.0%）、`lm_head` 774.07（20.4%）、
   `qkv_proj` 629.05、`down_proj` 526.96、`o_proj` 338.07，attention 292.12。
2. **为什么是带宽不是算力？** 五个"每步读一遍权重"的角色，字节数从 117 MB 到 352 MB，
   时间与字节的比值落在 334–402 GB/s；留一法用其余四个角色拟合一个常数 `B=375 GB/s`
   预测第五个，最大残差 12.8%（`lm_head` +9.7%，而它从未参与自己的拟合）。M=2 的算术强度
   只有约 2 FLOP/byte，远低于 roofline 拐点，所以瓶颈在读取，不在乘加。
3. **一个 8.9× 的内核，端到端应该期待多少？** 1% 左右，且方向、量级、区间都可事先算出；
   单请求 1% 的差异必须配对测量——这台机器上同一实现的两次采样输出都会差一个 token，
   单次 A/B 会被噪声吞掉。

## 我做过的判断、被推翻的说法

- 最初想说"引擎已到 HBM 上限"。standalone 实测 copy / sum / Triton 读只有 322–347 GB/s，
  低于引擎内隐含的 375 GB/s，**撤回**；现在只说"375 GB/s 是拟合常数"，并保留矛盾。
- 想用 SM 时钟解释这个差距。WSL 下 `nvidia-smi` 单次查询上百毫秒、分阶段采样几乎无样本，
  也没有锁频权限，**降级为未证实假设**，没有写进结论。
- 把采样 token id 当作数值等价判据。结果同一实现两次调用在 batch4 也会漂移，
  **改用 filtered-logits 逐字节一致 + 96 组 parity**，id 仅作旁证。
- 端到端第一版每次调用都重新 import 模块，wall 出现 +0.10%/+0.71% 与 decode −1.4% 矛盾；
  **改成两臂常驻 + 开关翻转**后 wall 与 decode 同向。

## 工程交付

- `patches/0001-mrv2-min-p-two-stage.patch`（147 行纯增量，可 `git apply` 到 pinned 上游）
  与完整文件 `patches/mrv2_min_p.py`；派发窗口 rows 1–8、vocab ≥ 32000、dtype f16/bf16/f32、
  列连续；`min_p = 0` 与窗口外走原内核，行为不变。
- 数值：96 组逐字节对照（含 padding、边界探针、dtype 守卫）、真实 MRV2 logits 4 次一致、
  引擎内 3,107 次调用全部由新内核完成且旧内核 0 次。
- 测量：24 轮 × 每轮 4 次 ABBA/BAAB、轮级配对、bootstrap 区间、等价相位、单参数带宽模型、
  四张 SVG 图；第二天换会话把 batch 扩到 8 复跑一遍，结论与预测一致。
- 证据纪律：每轮新目录、保留失败与真实退出码、manifest 记录 sha256；带 profiler 的记录
  不用于速度承诺；本机结果不外推服务器。

## 被追问时的边界

- "能不能更快？"——在这条路径上，min-p 的天花板约 1.3%（120 µs / 3.79 ms）；
  要两位数提速必须动 83.8% 的权重流 GEMM 或 20.4% 的 `lm_head`，本轮没有证据支持，
  也不声称有。
- "为什么不上服务器？"——单机 8 GB 笔记本 GPU、单模型、batch ≤ 8；跨设备需要重测，
  租卡与上游发言都需要明确授权（见下）。
- "这算不算框架贡献？"——目前是本地可审查补丁，不是上游合并；合并概率受"1% 端到端收益
  + 147 行维护成本"限制，这个判断本身也写在交接里。
