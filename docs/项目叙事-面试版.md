# 项目叙事（2026-10-18 修订）

定位：**基于 vLLM 的小批量 Decode 性能分析与采样内核优化**。项目目录名“云端推理框架”不代表从零实现完整推理框架。以下是工程结果；用户尚需亲自理解、复现、调试，不能把AI完成的内容直接当作已掌握。

## 主讲线

在固定 vLLM 0.31.0 的 MRV2 真实采样路径上分析 min-p 开销，先实现两阶段 Triton 归约／过滤，再比较只改启动参数的简化方案；通过真实 logits 对照、内核调用证明及交替配对计时，区分局部收益和端到端收益。

| 结果 | 条件与口径 |
|---|---|
| 两阶段局部约8.8× | FP32、V151936、batch2，122.9→14.0 µs，局部微基准；非真实请求速度 |
| 两阶段 decode约−1.10% | 请求平均decode间隔的轮级配对变化，24轮ABBA/BAAB；95% bootstrap区间[−1.37,−0.85] |
| 独立会话约−1.00% | 同batch2，新引擎会话；[−1.21,−0.82] |
| 两行参数版约−0.80% | batch2同类配对decode指标；wall区间跨0，因此不能说所有请求指标都显著改善 |

本机是RTX5060Laptop/WSL、Qwen3-0.6B、短合成prompt、小batch、min_p>0。min_p=0／greedy基线不会因为这个算子变快。区间仅描述当前采样协议，不是跨设备或生产保证。

## 为什么内核变快而请求只改善约1%

真实profiled min-p每次约62.5→5.6 µs；用节省56.9 µs除以另一份未插桩decode间隔约4812 µs，得到约1.18%，与配对结果量级一致。两份测量口径不同，这是解释量级的估计，不是精确的端到端成本分解。

正确性主证据是filtered logits逐字节一致、padding／边界检查和真实调用张量复核；采样token ID会发生同臂漂移，因此不能仅靠最终文本相同验收。每请求first/last-token平均间隔不等于逐token ITL的P50/P99。

## 分析背景与收敛判断

第三阶段单条batch2编译路径trace约3792 µs内核时间，全部GEMM占83.8%，其中lm_head占20.4%，层内四类合计约63.4%；lm_head位于当时的图外段。固定序列归因只在该配置下验收，不能凭内核名字推广到其他配置。

时间与权重字节近似成比例，留一法模型最大残差约12.8%，支持权重读取重要的假设；尚未用硬件计数器或锁频对照证明达到带宽上限。FP8现成配置观察到约24%～27%间隔下降，同时改变内核／融合／精度，不是自研优化收益，也没有模型质量验收。

两阶段方案需要新内核和派发；两行BLOCK_SIZE/num_warps方案收益稍小、维护成本低。本机参数对照支持简化，但不能据此宣称所有形状或所有GPU不退化。选择简单方案是可解释的工程判断。
