# 面试问题地图：这个项目到底能被问多少（2026-10-23）

你担心“面试官能问的不多”。更准确的说法是：**可问面窄的不是项目，是叙述**。别人把项目
压成一句“优化了采样算子，局部 8.8×”，面试官自然只能追问一句“端到端呢”，然后结束。
这份文档把项目拆成三条独立的故事线，每条给 10–13 个真问题、一行答案要点和证据路径；
把简历 bullet 换成[简历与面试](简历与面试-20261020.md) 里那三条之后，每个 bullet 都是一个入口。

## 0. 先回答“不如一个开源 vLLM”这个纠结

| | 一个已合并的 vLLM PR | 这个项目 | 你其实已经有 |
|---|---|---|---|
| 给的信号 | 能过 review、代码风格、社区信任 | 端到端 ownership、测量纪律、能证伪 | 两个 vLLM PR（#62393、#62693），open 未合并 |
| 面试官会问 | 改了什么、为什么这样改、review 里被指出什么 | 怎么定位、怎么证明、边界在哪 | 租约/窗口/TTL/兼容回退（见故事 C） |
| 可问深度 | 通常一个点 | 三块：测量建模 / 内核与证伪 / 并发协议 | 两者叠加 |

关键事实：**你并不是“没有开源 vLLM 经历”**。#62393 和 #62693 就是 vLLM 仓库里的 PR，
有设计文档、测试、第三方真机验证；面试官问 PR 时问的是设计取舍，不是 merge 徽章。
真正缺的是“合并”这个信号，而它买不到，只能等维护者。

所以别在“要不要换一个更热闹的项目”上纠结：现有素材能撑起 30+ 个真问题，
缺的是把每条线讲成可以追问的样子。

## 1. 故事 A：一个 decode step 的钱花在哪（测量与建模）

钩子：“我把 batch 2 的一步拆成 385 个 kernel，发现 83.8% 在 GEMM，而且时间基本正比于权重字节。”

1. **385 是怎么来的？13 个 kernel 分别是什么？**
   28 层 × 13 + 7 个准备 + 尾部；13 个是 qkv/o/gate_up/down 四个 GEMM、norm、rope、
   attention 与 KV 写入、激活等。证据 `results/attribute-20261017T093052Z/attribution.json`。
2. **为什么说是权重流受限，不是算力受限？**
   batch 2 的 GEMM 是 M=2 的 gemv 型：每字节权重只做约 2 次乘加，算术强度 ~2 flop/byte；
   5060 Laptop 算力/带宽比是 ~110 flop/byte，差两个数量级，所以卡在带宽侧。
3. **lm_head 为什么占 20%？**
   vocab 151936 × hidden 1024 ≈ 311 MB 权重，一步只产出 2 行；311 MB / 总权重字节
   （311 + 880.6）≈ 26%，实测 20.4%（还有别的 kernel 分摊）。
4. **为什么说 lm_head 在 CUDA 图外？**
   trace 里它的 graph node id 为 0；采样依赖 logits、形状随 sampling 配置变，图捕获不了。
5. **CUDA graph replay 没有 correlation id，你怎么归因到层？**
   三个条件：模态步（数量）、28×13 固定序列逐位置断言、graph node id 区分图内外；
   任何一步数量不对就整步丢弃，不猜。
6. **375 GB/s 是实测还是拟合？为什么不等于 HBM 峰值？**
   五类角色留一法拟合的常数，误差 ≤12.8%；它吸收时钟状态、L2 命中与未建模开销，
   只能当“有效带宽”，不能当硬件上限。
7. **3,792 µs 和 4.79 ms 的 decode 步差在哪？**
   前者是内核累计（带 profiler），后者是请求级 decode 间隔，含启动、同步、图外
   kernel 与 CPU 时间；两个口径不能相减当“优化空间”。
8. **为什么不用 Nsight Compute？**
   Nsight Compute 是单 kernel 重放、带 counter，适合看 stall/占用率；我们要的是整步
   时间线与层间比例，CUPTI trace 更合适。两者不是替代关系。
9. **怎么保证没漏 kernel？**
   数量断言 + 序列断言 + 丢步；并且交叉验证：内核累计 × 占比要和独立微基准同量级。
10. **换模型、换卡，哪些数字会变？**
    权重字节比（结构决定）、KV/attention 占比（序列长度决定）、SM 与带宽（卡决定）；
    绝对时间不可移植，比例与“权重流”这个机制可移植。
11. **小 batch 下 attention 占多少？为什么不是瓶颈？**
    128 token prompt、KV 短，attention 的字节量与计算都远小于 880 MB 权重流；
    长上下文（8k）时才会变（第三阶段与第六阶段有扫描）。
12. **能外推到生产 7B / 70B 吗？**
    只能推机制：lm_head 占比取决于 vocab×hidden，层内 GEMM 取决于层数与 hidden；
    7B 的权重流比例更高、KV 更大，绝对值必须重测。**不要说“同理可推”。**

## 2. 故事 B：一个采样内核，以及它的边界（实现与证伪）

钩子：“min-p 慢在并行度而不是带宽；我改完局部快 4–10×，但整请求只有 1.1%，因为它在一步里只占 1.18%。”

1. **min-p 的数学定义是什么？为什么要扫两遍？**
   阈值 = max(logits) + log(min_p)，小于阈值的置 -inf，再走采样；先求 max 才知道阈值，
   所以是“先扫 max、再扫过滤”两遍。
2. **两阶段版为什么快？**
   上游一行一个 CTA、串行扫 148 个 1024 宽的块；改成每行切 37 个 4096 宽的分片，
   8 行就有 296 个 CTA，把 26 个 SM 填满。
3. **BLOCK=4096、num_warps=4 怎么定的？**
   `minp_param_sweep.py` 扫过 block/n_warps；4096 是“分片够多、归约不贵”的折中，
   不同形状还有两行旋钮版（16384/16）。
4. **两行旋钮版和两阶段版怎么选？**
   旋钮版只改启动参数、无派发风险，本机 batch 1–8 约 −0.8%；两阶段版更快（局部 4–10×）
   但多一套代码与路由，需要维护。**收益差 0.3 个点，换维护成本。**
5. **为什么 batch>8 直接回落？**
   `PARALLEL_MAX_ROWS=8`：32 行时上游已有 32 个 CTA，再切分只剩调度与归约开销，
   微基准只有 4%（161→155 µs），所以主动回落。
6. **正确性怎么保证？**
   96 组逐字节对照（FP32/FP16/BF16 × 多种 vocab × batch）、包括 padding 区域；
   NaN/-inf/全零边界；真实 logits 的调用级 verify 模式。
7. **你怎么知道引擎里真的走了你的内核？**
   worker 给三个内核装了启动计数器；batch 16 的调用形状是 `(16, 151936)` 一次调用，
   不是“每 8 行一组”——这条还推翻了我以前的笔记。
8. **端到端 1.1% 怎么测的？为什么用 ABBA？**
   两臂常驻同进程、只切函数指针；ABBA/BAAB 交替抵消漂移；每轮一个配对差，
   轮级 bootstrap 取 95% 区间（请求之间不独立，不能按请求算）。
9. **1.1% 和 1.18% 上限是什么关系？**
   上限 = min-p 在一步的占比（~1.18%，约 57 µs / 4.79 ms）；实测省 53 µs 左右，
   所以 1.1% 已经接近“把它优化到零”的极限。**这不是失败，是分母决定的。**
10. **batch 8 这次区间含 0，怎么解释？**
    24 轮 + 单机未锁频，1% 量级的效应会被整轮漂移吃掉；历史 run B 是 −0.91 [−1.55,−0.75]。
    要收紧就加轮数、控制时钟、或用更多请求；现有证据只能说“方向一致、本轮不显著”。
11. **Triton 版已经能跑，为什么还写 CUDA 版？写出来更快吗？**
    为了补“手写 kernel + CUDA 构建”的经历，不是为性能。结论是**同量级但没更快**：fp16 V151936
    b1–b8 为 18.6/22.2/22.2/25.3 µs，Triton 16.1/18.9/22.3/24.3，上游 212/272/194/159。
    b8 已贴带宽上限（4.9 MB / 25 µs ≈ 200 GB/s），b1/b2 的 2–3 µs 差在两次 launch 与波次。
12. **手写 CUDA 时踩的最大的坑是什么？**
    第一版一 row 一 CTA，batch 8 只有 8 个 CTA、26 个 SM 闲着，67.9 µs；改成按列分块
    `grid=(38, rows)` 才到 25 µs。另一个是 NaN 语义：我以为要传播，实测上游忽略 NaN（`fmaxf`），
    用 `nan_mode=0/1` 探针才定下来。**语义是测出来的，不是读出来的。**
13. **怎么证明 CUDA 内核在真实 serve 里被调用了？**
    `patched_installs=4`、`base_installs=0`；`CI_MINP_VERIFY_FIRST` 让 worker 前 48 次调用同时跑上游
    与候选、逐字节比较，192 次 0 mismatch；`CI_MINP_STATS kernels={}` 是预期的——CUDA 分支不经过
    Triton 的三个内核。端到端则诚实地说：nop 安慰剂相位（两臂同代码）都有 ±5–10% 的假差异，
    minp 相位差值更小，**不能宣称提速**。

## 3. 故事 C：池满之后还能保存吗（并发与一致性，来自 vLLM PR #62693）

钩子：“给读者的不是 LRU，是一个在途信号：scheduler 判命中到 worker 真读之间有个窗口。”

1. **池满后保存失败，根因是什么？**
   没有空闲页可分配；删除/覆写不是“回收”，得先证明没人在读。
2. **为什么不能直接加 LRU？**
   scheduler 用 `batch_key_exists` 判“外部命中”，worker 稍后才 `get_key_locations`；
   中间若淘汰，命中会变成加载失败或读到别人的数据——比保存失败更严重。
3. **租约的语义是什么？**
   acquire：返回位置并 pin 住；release：数据进 host buffer 后立即释放；
   只有 complete、未被租、且不是本请求命中的键才可淘汰，最旧优先。
4. **为什么 release 要先清标志再发 RPC？**
   RPC 失败会重试；若先清后发失败，重试时本地状态已一致；反过来会把别人的租约减掉。
5. **TTL 为什么是 120 s？**
   实测 28k prompt 加载 ~1.1 s、60k ~1.9 s；3FS 故障时最坏停滞 16–18 s；120 s 约 7× 余量。
   且**故意不续期**，避免“续期卡住反而钉住页”。
6. **“死线取同键所有租约的最晚者”为什么重要？**
   否则先过期的租约会让键被提前回收；已写进 `acquire_keys` docstring 并用测试钉住。
7. **崩溃的读者怎么办？**
   过期租约在下一次分配时被回收（测试 `test_expired_lease_is_reclaimed`）。
8. **旧 server 没有新路由怎么办？**
   404/405 回退到普通 lookup；旧 server 从不淘汰，所以 lookup 安全。不写这条，滚动升级会 500。
9. **并发双写为什么本 PR 不做写租约？**
   同 key 内容应相同（未观测到损坏），要排除需写租约；本 PR 只解决满池可写，不扩范围。
10. **第三方验证覆盖了什么、没覆盖什么？**
    两台 H100 + 真 3FS：池满后保存继续、被租 29/29 存活、未租 0/29、TTL 134 s 回收、
    28 次 needle 0 错答案；没覆盖：读者进程真被杀、吞吐/命中率影响、写租约。

## 5. 低成本扩大可问面的五个动作（按性价比）

1. **serve 指标（1–2 天）**：`vllm serve` + 固定并发测 TTFT/TPOT/P99，min-p 开关对比。
   新增话题：continuous batching、调度队列、prefix caching、分位数。**已完成（第八阶段）。**
2. **CUDA 版 min-p（3–5 天）**：batch ≤ 8、V151936，和 Triton 对齐数值再比时间。
   新增话题：线程/共享内存/访存合并/占用率，直接补 JD 的硬门槛。**已完成（第九阶段）**：96 个逐字节
   case、fp16 V151936 b1–b8 为 18.6/22.2/22.2/25.3 µs，比上游快 6–12×、与 Triton 同量级（0.85–1.00×），
   serve 里 192 次 in-path 逐字节一致。可问：为什么 b8 贴着带宽上限、为什么 CUDA 没跑赢 Triton、
   为什么单 CTA 扫整行是错的、NaN 语义怎么定下来的。
3. **把 HF3FS 讲成系统设计（0 天，只是换叙述）**：一致性、租约、TTL、兼容升级。
   新增话题：分布式 KV、元数据服务、故障恢复。
4. **lm_head 下探（2–3 天）**：按行分批 GEMM 或 fp8 对照，验证 20% 那块的边界。
   新增话题：量化、算子融合、图外开销。
5. **一篇英文 README/博客（1 天）**：把三条线压成 1 页。新增话题：你能不能对外讲清楚。
