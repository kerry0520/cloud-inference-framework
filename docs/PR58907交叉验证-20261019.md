# PR #58907 交叉验证：per-lane 归约与本机 5060 上的端到端效果（2026-10-19）

## 1. 为什么做这件事

上游 `vllm-project/vllm` PR #58907 的作者 `cyanseek` 在 2026-10-18 推送了第二个
commit `95e9d21`，把两条独立的优化合并在一起：

1. per-lane 部分最大值（`max_val` 保留为向量，循环结束后只做一次 `tl.max`），
2. 启动参数调优（`BLOCK_SIZE = 8192`、`num_warps=16`，对 `vocab > 16384` 且
   `num_tokens <= 32`）。

他在评论里给出 A100 80GB 与 RTX 2080 Ti 的内核数据（固定 8192/16 隔离归约改动：
36.59 → 29.06 µs、35.88 → 28.19 µs），以及 A100 上 Qwen3-0.6B 生成任务的整请求
时间（batch 8 −2.72%、batch 32 −2.43%），并明确问我们能否在 5060 上交叉验证。
本文就是我们这一侧的结果。

这不是为了支持某个结论而重跑：内核级数字、固定启动参数下的隔离对照、以及本机
引擎内的整请求配对，三件事各自独立，任何一项与作者的说法不符都会写出来。

### 隔离 per-lane 归约本身

PR 同时改了两件事，所以"PR 比我们的 16384/16 快"**不能**归因于归约。用历史
sweep（`results/minp-sweep-20261018T051134Z`，上游内核、8192/16）与本次 PR 的
8192/16 相比，才是同一启动参数下的归约对照：

| batch 1/2/4/8（fp16, V151936） | 上游内核 @8192/16 | PR @8192/16 | 比值 |
| --- | --- | --- | --- |
| 1 | 18.7 | 14.4 | 1.30× |
| 2 | 20.6 | 16.5 | 1.25× |
| 4 | 20.9 | 16.7 | 1.25× |
| 8 | 20.6 | 15.7 | 1.31× |

作者在 A100 上给出的同参数比值是 36.59 → 29.06 = 1.26×。两套硬件上 1.25–1.31 与
1.26 一致：per-lane 归约的收益是内核结构性的，不依赖我们的旋钮。

## 4. 引擎级：整请求配对

`scripts/abba_patch.py`，两臂常驻同一进程（`minp_select` 只翻标志），每轮
`base, patched, patched, base`（下轮反向），轮级配对差 + bootstrap 95% 区间；
prompt 128、输出 64 token、min_p=0.1、greedy 关闭（temperature 0.8 采样）。

### 两次运行

同一脚本跑了两遍（第二次 24 轮，用于收窄区间）。中位数 [95% bootstrap 区间]，负值为更快：

| batch | wall Δ% 运行 A（16 轮） | decode Δ% 运行 A | wall Δ% 运行 B（24 轮） | decode Δ% 运行 B |
| --- | --- | --- | --- | --- |
| 2 | −1.04 [−1.18, +0.84] | −0.63 [−0.90, +0.08] | −0.42 [−2.62, +4.68] | −0.61 [−3.36, +3.97] |
| 8 | −0.62 [−1.33, +0.61] | −0.60 [−1.38, +0.56] | −0.67 [−1.02, +1.52] | **−0.85 [−1.40, −0.16]** |
| 32 | −1.16 [−10.34, +3.93] | −1.17 [−10.42, +3.41] | −0.55 [−2.07, −0.23] | **−0.81 [−1.61, −0.26]** |

- 运行 A 的 batch 32 有一轮整轮漂移（base 2586 ms / patched 2850 ms），把区间拉宽；
  运行 B 把该批的区间收窄到 ±1.6% 以内。
- 运行 B 的 batch 2 反而更抖（区间 ±3.4%），说明这一档的单次运行在 8 GiB 卡上不稳，
  不能只看一次。
- 输出 id：运行 A batch 2/8 两臂各 32/32 与首个调用一致；batch 32 的 base 臂 31/32
  （第 26 个 token 分叉）、patched 臂 32/32。运行 B 两臂 batch 2/8 各 48/48、batch 32
  patched 47/48。**同一臂内也会分叉**，所以 id 只作旁证，不能当 oracle（与早期结论一致）。
- 每步 decode 间隔在 batch 8/32 上约 4.79 ms（base 臂轮级平均），batch 2 的长尾来自
  预热轮，不计入中位。

### 派发形态的一个意外

运行 B 的 worker 统计（patched 臂，batch 32）：

```json
{"calls": 24960, "shapes": {"(8, 151936)": 24192, "(1, 151936)": 280,
 "(7, 151936)": 280, "(2, 151936)": 88, "(6, 151936)": 88,
 "(3, 151936)": 12, "(5, 151936)": 12, "(4, 151936)": 8},
 "_min_p_kernel": 12480}
```

即使请求 batch 是 32，MRV2 也把采样拆成**每 8 行一组**再调内核（24,960 次调用里
24,192 次是 `(8, 151936)`，没有任何一次超过 8 行）。这解释了两件事：为什么
`num_tokens <= 32` 的启动窗口在这条路径上比实际行数宽（真正传进去的行数 ≤ 8，
`<= 8` 今天会等价），以及为什么本机引擎里 PR 与我们的 16384/16 旋钮几乎不可区分——
两者在 rows-8 上只差 2–3 µs/次，相对 4.8 ms 的 decode 步是千分之一量级，落在
配对区间内。

（注意：上面的 calls 计数里还包含预热与等价相位的调用，不能直接除以步数当作
"每步几次内核"；这里只用它来确认**行数上界**。）

## 5. 与作者 A100 结论的关系

一致的部分：

- 固定 8192/16 时 per-lane 归约的收益，本机 1.25–1.31× vs 作者 A100 的 1.26×。
  这是本文最强的一条交叉验证：同一处代码改动、同一启动参数、两套架构，比值的
  误差在时钟噪声范围内。
- 输出逐字节一致（本机 14 个形状 × 3 变体全部通过），作者的 "outputs matched
  exactly" 在本机也成立。

不一致、也不能直接比较的部分：

- 作者报告的整请求收益是 batch 8 −2.72%、batch 32 −2.43%（A100、min_p=0.05、
  他自己的生成任务脚本）；本机同 batch 的 decode 中位是 −0.60…−0.85% 与
  −0.81…−1.17%。这不矛盾，是分母不同：本机 0.6B 模型的 decode 步在 batch 8/32
  上约 4.79 ms（权重流受限，见第六阶段），每步省下的约 50 µs 只占 1%；A100 的
  步更短，同一个绝对节省占比自然更大。
- 本机没有复现作者的生成任务脚本（构造的 Qwen3-0.6B 编辑任务、八轮配对），所以
  "2.72%/2.43%" 这个数字我们没有独立确认，只确认了方向与量级关系（内核 ~4×，
  整请求 ~1%）。
- 本机 min_p=0.1、temperature 0.8；作者 min_p=0.05。两遍扫描的成本与阈值无关，
  但采样分布会影响每步实际的内核次数（本机每步约 4 次 rows-8），这点没有做
  敏感性实验。

## 6. 限制

- 单机单卡（RTX 5060 Laptop 8 GiB），不能替代数据中心卡上的结论。
- batch 32 的运行 A 出现过一轮 +10% 的整轮漂移，运行 B 才把区间收窄；batch 2 的
  运行 B 反而更抖。单次运行不足以下结论。
- 采样在 batch 4 及以上的同一臂内不可逐位复现（早期发现），id 只作旁证。
- 内核计时在本机时钟状态下测得，跨会话绝对值不可比；比值可跨会话比较。
