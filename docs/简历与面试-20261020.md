# 简历与面试：这个项目怎么说

这份文档只做一件事：把项目里的数字**变成能在面试里站住的话**。
所有数字都注明了口径与条件；不能说的数字单独列在最后一节。

---

## 一、一句话版本（简历项目名下面那行）

> 在 vLLM 0.31 上测量 Qwen3-0.6B 的小批量 decode：用逐层 trace 归因与权重字节模型
> 定位到 83.8% 时间在 GEMM，据此完成一个采样内核优化（局部 4–10×、整请求 −1.1%，
> 95% CI 不含 0），测出它的收益边界（≤8 行），并把同一内核在 RTX 5060 与 5090 上复核。

## 二、三条 bullet（推荐简历用这个）

- **逐层归因**：对 vLLM 编译路径的 batch-2 decode 步做 trace 归因（385 kernel/步），
  得到一步 3,792 µs 中 GEMM 占 83.8%、`lm_head` 单点占 20.4% 且在 CUDA 图外；
  用“时间 ∝ 权重字节”的单参数模型（375 GB/s，留一法误差 ≤12.8%）解释各角色耗时。
- **内核优化与边界**：针对 min-p 采样内核“每行一个 CTA、串行扫两遍全词表”的并行度瓶颈，
  实现两阶段 Triton 归约（局部 4.2–9.7×）与两行启动参数版本（3.6–4.2×），
  在真实引擎路径上以 ABBA 配对测得整请求 decode −1.10%（95% CI [−1.37, −0.85]），
  与“该算子占一步 1.18% 成本”的上限推算一致；再把 batch 推到 32，测出收益边界——
  1–8 行 0.8–1.3%，越过 8 行回落上游内核、收益归零（是路由悬崖，不是逐渐稀释）。
- **跨机复核与上游协作**：把同一内核在 RTX 5090 上复核，发现上游实现在两代卡上
  都是 66–71 µs（发射受限而非带宽受限），解释了上游为何在大 batch 下没有空间；
  为 vLLM PR #58907 提供独立测量与 batch>8 的启动配置分析，被作者采纳进实现；
  另独立完成 HF3FS 页预算修复（PR #62393）与读租约 + LRU 淘汰（PR #62693，
  第三方在两台 H100 + 真 3FS 上验证）。两 PR 均 open，未合并。

## 三、一段式（自我介绍里 40 秒）

> 我做的项目是在 vLLM 上分析小批量 decode 的性能。先用 trace 把一个 decode 步拆成
> 385 个 kernel，发现 83.8% 的时间在 GEMM，而且时间基本正比于权重字节——
> `lm_head` 一项就有 311 MB，占 20%。有了这个模型，我选择一个采样内核去优化：
> 它慢在并行度而不是带宽，改成两阶段归约后局部快 4–10 倍，但整请求只快 1.1%，
> 因为它在一步里只占 1% 出头。我用配对测量加 bootstrap 给了区间，也把这个上限
> 算清楚了。后来我把同一个内核拿到租来的 5090 上复核，发现上游实现换卡也没变快，
> 这反过来证明瓶颈是发射而不是带宽。

## 五、高频追问与答法

**Q1：你的贡献是什么？框架本来就快。**
A：三个层面。测量上，我建立了这套 trace 归因与权重字节模型；工程上，我写了 min-p
两阶段内核和只改两行的版本，并验证它真的接进 MRV2 的采样路径（派发计数可查）；
判断上，我用配对测量算出了这类优化的天花板是 1.18%，并说明了为什么。

**Q2：为什么只有 1%？是不是你做得不好？**
A：分母决定的。min-p 在一步里约 120 µs，一步 4.8 ms。就算把它干到零也只有 2.5%；
我的实现把它压到 15 µs 左右，省 100 µs，理论上限 1.8%，实测 1.1%。
所以这不是“优化失败”，而是“选错了对象”的一个可量化案例——这也是我后来把
`lm_head`（占 20%）标成下一个目标的原因。

**Q3：怎么证明不是测量噪声？**
A：两个臂常驻同一进程，只切换函数指针；每轮 ABBA/BAAB 交替；对轮级配对差做
bootstrap 取 95% 区间；换会话复跑一次得到 −1.00% [−1.21, −0.82]。
另外用“无插桩配对”和“profiler 推算”两条独立路径得到 1.10% 与 1.18%。

**Q4：为什么 CUDA graph 里能归因到层？**
A：没有 correlation id，所以用三个条件：模态步（385 kernel）、28×13 的固定序列
逐位置断言、graph_node_id 区分图内外。任何一步数量不对就整步丢弃。

**Q5：fp8 为什么没到 −35%？**
A：层内 GEMM 确实减半（3,220→1,506 µs），但 lm_head 没被量化（884 µs 不变），
还多了 112 个量化 kernel（约 165 µs），三项相加就是 −26%。

**Q6：换到 5090 为什么没变快？**
A：因为瓶颈是发射/延迟。这个 kernel 每行一个 CTA，串行扫 148 个 1024 宽的块；
SM 更多、带宽更大都不会让它更快，只有加大 BLOCK 或改归约方式才行。

**Q7：你改的上游代码被合入了吗？**
A：没有。PR #58907 是别人的，我提供独立测量与 batch>8 的启动配置分析，作者采纳后
更新了实现；我自己提的是 HF3FS 的 #62393，目前 open、没有人类 review。
上游要求人类对每一行负责，我不代提纯 agent PR。

**Q8：如果给你 8 卡 A100，你会怎么做？**
A：先验证可移植的部分（字节占比、占比决定上限），再测不可移植的部分（TP 下的
通信、KV 分布、batch scaling）。具体第一步是把 min-p 与 lm_head 的结论在
tensor parallel 下重跑，因为 TP 会改变每个 rank 的权重字节和采样行数。

**Q9：这个项目最难的部分是什么？**
A：不是写 kernel，是**判断该不该写**。我花了两天做归因，结论是“能省 1%”，
然后我用配对测量把这个上限钉死，而不是继续调参数刷数字。

**Q10：你从中学到了什么？**
A：三件事。① 先建模型再优化，模型错了优化就是碰运气；② 局部收益不等于端到端收益，
必须用分母换算；③ 失败要留档，我的失败博物馆里有 9 条，每条都对应一次被浪费的小时。

**Q11：为什么 batch 越大收益越小？**
A：要拆成两段。窗口内（≤8 行）是“固定节省 ÷ 越来越长的 decode 步”，1.27%→0.77%；
越过 8 行是我的补丁主动回落上游内核（`PARALLEL_MAX_ROWS=8`），分子直接归零，
所以 16/32 行测到的是 0 而不是“更小”。batch 32 的 −0.81% 是 PR #58907 那条臂的数，
不能拿来当我这个补丁的成绩。

**Q12：你怎么证明它真的回落了、不是测错？**
A：worker 里给三个内核装了启动计数器：≤8 行时上游 `_min_p_kernel` 计数为 0、两个
并行内核都有；16/32 行时上游内核有几千次、并行内核只剩收尾那几个不满行的步。
第一次跑我还在这条断言上写错过（要求 >8 行也为 0），失败目录留着。

**Q13：为什么上游不改，只在 ≤8 行快？**
A：上游一行一个 CTA，8 行只有 8 个 CTA，26 个 SM 大量空闲；32 行时上游已有 32 个 CTA，
再切分只剩调度与归约开销（微基准 161→155 µs）。所以快不快由“SM 有没有活干”决定，
不由 batch 数字决定。

## 六、不要写进简历的话

- ❌ “实现了 8.9× 加速” → 会被追问端到端，然后发现是 1%。
  正确写法：“局部 4–10×，端到端 −1.1%（95% CI 不含 0）”。
- ❌ “向上游提交了 PR 并被采纳” → 我们的 PR 没有被合入；被采纳的是**建议**。
- ❌ “掌握 CUDA” → 项目里现在有一个**手写 CUDA 内核**（第九阶段：两阶段按列分块、`uint4` 向量化、
  96 个逐字节 case），覆盖 fp16/bf16/fp32、单卡、batch ≤8；但没写过大模型/多卡/Tensor Core/异步拷贝，
  也没做过 CUDA 图定制。正确写法：“写过并验过一个 min-p CUDA 内核（`.cu` 约 340 行 + 加载器/派发
  两个小模块，含 pybind 与构建缓存），与 Triton 同量级、比上游快 6–12×”，不写“掌握 CUDA”。
- ❌ “优化了大模型推理” → 模型是 0.6B，负载是合成的 128 token，说“大模型”会露馅。
- ❌ 把 fp8 的 −26% 说成“我的优化” → 那是换精度带来的配置差异，不是内核优化。
- ❌ 写“batch 32 也快 0.8%” → 0.81% 是 PR #58907 那条臂；我们的补丁在 >8 行归零。

## 七、面试前要亲自过一遍的五个动作

1. 打开 `results/attribute-20261017T093052Z/attribution.json`，指着 per-role 表讲一遍。
2. 手算一次 `t = bytes / B`，解释为什么 `lm_head` 占 20%。
3. 打开 `results/abba-*/summary.json`，解释 `wall_pct_of_paired_rounds` 与
   `decode_pct_of_paired_rounds` 的区别。
4. 讲清楚 min-p 内核为什么扫两遍、两阶段版本为什么快。
5. 讲清楚 5090 那组数据为什么能支持“发射受限”。
