# 阶段复核与建议（2026-10-18）

复核起点：`20b91dd`，工作区干净。范围：最新交接、第三至六阶段相关记录、面试叙事、上游可行性和远程迁移说明，以及 quant_decode、remote_bootstrap、repro_l4、run_stage、preflight 和 min-p 依赖路径的静态检查。没有重跑 GPU 实验、连接租用机、核查在线 PR 最新状态或对全部原始数据重新验算。本轮只给建议，未修改实验实现。

## 判断与优先级

项目已有足够的实验主线：定位 decode 成本 → min-p 两阶段候选 → 两行启动参数方案 → 真实路径与配对统计 → FP8 和上下文干预。现在优先修证据表述和远程复现入口，再做一次有边界的第二设备验证；不建议继续同时扩张 KV 量化、投机解码和更多新算子。上游合并不是项目完成的必要条件。

## P0：租卡前修远程准备入口

1. `remote_bootstrap.sh --torch-only` 实际装的是未指定版本／CUDA 构建的 `torch triton`，并不能解决旧驱动兼容；后续还无条件下载模型并执行含 FlashInfer 的 preflight。`minp_param_sweep.py` 与待加载的 min-p 文件仍导入 `vllm.triton_utils`。因此当前“只装 torch 就能跑三个阶段”的路径不成立。应明确选择兼容的依赖组合，或为纯内核阶段准备可审查的独立导入路径，分别验收；不能把更换软件栈的结果与原栈直接混为一个对照。
2. 脚本未激活 venv，却用 `command -v modelscope` 查全局入口；回退则硬编码 `.venv/bin/huggingface-cli`，并未验证实际安装包提供该入口。应统一使用 venv 的明确入口，并在新目录做下载冒烟。
3. 仅凭 `config.json` 就跳过模型下载，不能识别中断后缺权重；已有 `min_p.py` 就跳过源码固定也不能证明 revision 正确。应验证完整文件及固定版本，保存依赖锁定清单和 CUDA 实际初始化结果，失败不能只打印后继续。
4. `CI_RUNTIME_DIR` 只改了外层目录，`quant_decode.py` 的 MODEL 仍硬编码 `/opt/cloud-inference-framework/models/Qwen3-0.6B`。自定义路径尚未端到端打通。先做无安装的路径／依赖检查和小规模冒烟，再启动全套长实验。
5. `repro_l4.sh` 的计划只有 `minp-compare`（默认 FP16），没有已有的 `minp-compare-f32`；真实采样 logits 是 FP32，应把 FP32 列为第二设备的优先项。WSL 内 rsync 的本地目的地应使用 `/mnt/c/...`，不能照抄文档中的 `C:/...`。

这些结论来自静态调用链检查，不等于已验证某租用机具体会在哪一步失败。建议先把全量路径修通，老驱动备选可暂时撤下，避免增加两套未验收环境。

## P1：修结论强度与算账口径

- 第三阶段的 83.8% 是全部 GEMM（含 lm_head），层内四类合计约 63.4%。第六阶段把 83.8% 当层内 GEMM 来预测约 −40%，起始拆账有误。若暂按原 trace、只让层内部分减半且其他不变，预测下降约 31.7%；激活量化等新增成本另算。不同 trace 的绝对时间不可混用，必须注明这个预测的条件。
- 第六阶段用 FP8 臂的 lm_head 884.71 µs 从 FP16 臂总 GEMM 4105.60 µs 中相减，无法得到 FP16 层内 GEMM 的直接测量。需从各臂自己的 trace 单独归属 lm_head，再比较。当前 0.468× 只能是代理估计，不能称“精确减半”。
- FP16→FP8 W8A8 同时改变权重／激活精度、内核、融合及量化开销。它支持“减少权重流是重要优化方向”，尚不能单独证明唯一瓶颈就是带宽。没有额外对照时，把“证实／精确”改为“支持／与模型一致”。
- profiler 内核时间和未插桩请求间隔是不同口径；不能把两种降幅之差直接全部归给图外启动／同步。需要同口径时间线与空隙证据，否则写为尚未归属的差额。
- 长上下文相对 128 token 的时间增量可支持 KV 成本增长，但“增量／总时长”不是直接测得的完整 attention 占比，基线也含 attention。隐含带宽计算还需明确使用上下文增量而非全部上下文字节。42.5%／60.5% 应标为增量成本比例估计，而非内核归因结果。
- 跨 GPU 的比例、lm_head 占比和 FP8 降幅同样需要重测；迁移说明里的数字应作为待检验假设，而不是预先要求复现的答案。FP8 的模型质量尚未评估，26% 应称现成量化配置的性能观察，不能写成自研优化收益。

## P2：收敛交付与面试材料

- 面试叙事落后于当前进展：仍写“无 remote、无上游评论”，并把 83.8% GEMM 与 20.4% lm_head 像两个独立部分并列；min-p 上限一行的 `120 µs / 3.79 ms ≈ 1.3%` 也算术不符。优先同步现状，分清两阶段与旋钮版、局部与端到端、已有配置与自有实现。
- 上游可行性文档同时含已发表评论、旧的“没有发言”、以及未来再开 issue 的计划。保留历史但标注已取代；合并概率没有统计依据，建议改为具体条件与风险。
- 原始失败曾有删除记录，与当前 AGENTS 的证据保存规则不一致；已经删除的应保留缺失说明，后续一律保留，不要在材料里声称所有失败原件都齐全。
- 最终形成一个当前结果总表：两阶段 min-p、旋钮 min-p、现成 FP8 配置三行，各写自有改动、正确性契约、真实路径证据、未插桩收益、硬件和限制。面试主讲其中一条，其他作为支撑。

## 推荐续做顺序

1. 修 P0 和 P1，做不花钱的静态检查及最小冒烟，并同步面试材料。
2. 用户开机并明确授权后，先采环境，再跑真实 FP32 形状的小算子正确性／三方性能对照；通过后跑旋钮版的配对端到端，最后按剩余预算选 FP8 或上下文验证。第二设备收益消失也是有效结果。
3. 通过以上步骤后，再决定是否给 lm_head 接低精度。该方向需额外明确 tied embedding、量化误差及任务质量标准，不宜仅凭微基准 1.9× 就承诺整模型收益。

本轮没有改脚本或重新验收远程路径，以上问题仍待实现轮处理。
