# 第三阶段：Decode 步逐层算子归因与带宽对照

本轮把第二阶段留下的问题——编译版（CUDA graph）decode 步的每个内核归属到具体层和角色——做完，并用同形状 standalone 对照检查“这一步是不是权重流带宽受限”。结论按证据强度分三层：**归因本身在 trace 内部自洽**；**时间与权重字节成正比**有明确数据；**“已达硬件带宽上限”不成立**，因为 standalone 对照给出的可达流带宽低于 trace 隐含值，两个测量上下文的时钟状态未能对齐。

范围仍是 batch2、Qwen3-0.6B、RTX5060Laptop/WSL 与固定 vLLM 0.31.0，只有一条带 profiler 的 trace，不是未插桩性能，也不能推广到服务器。

## 方法：为什么按位置归因

`profile-pinned-20261017T020913Z` 的 trace 里，层内内核都是同一张 CUDA 图的 replay。graph replay 的内核没有可用的 launch 关联，逐层归属不能靠 correlation，只能靠“模态步 + 固定内核序列 + graph node id”。归因按以下规则固定下来，并写成断言：

- 用 `gpu_user_annotation` 切出 11 个稳态窗口，取每步内核数 385 为模态值；11 步里 10 步为 385，1 步 373（丢弃；另有 step 0 为 386 也在窗口外）。
- 10 个保留步的内核序列逐位置完全一致（`sequence_identical_across_kept_steps: true`），因此序列位置可当角色用。
- 每步结构：索引 0–6 为七个准备内核（FillFunctor、arange、`_prepare_pos_seq_lens`、`_combine_sampled_and_draft_tokens`、`_gather_block_tables`、`_compute_slot_mappings`）；7–370 为 28 层 × 13 内核；371 final_norm；372 memcpy32_post；373 vectorized_gather；374 lm_head；375–384 十个采样内核。
- 层块固定顺序：input_norm、qkv_proj、rotary、kv_cache_write、attn_prep、attention、attn_combine、o_prep、o_proj、post_norm、gate_up、silu_mul、down_proj。脚本用内核类名/名字模式校验每一位，不匹配则失败而不是猜测。
- 单步 385 个内核中，7–372 共 366 个内核各带一个非零 graph node id（366 个互不相同，即一内核一节点）；0–6 与 373–384 无 graph node id，属于图外 eager 段。

形状不来自 trace（trace 没有形状字段），而来自第二阶段实测的 M=2 与模型配置；权重字节由 `X[M,K]×W[N,K]^T` 的 N、K 与 2 字节直接算：qkv 8,388,608、o 4,194,304、gate_up 12,582,912、down 6,291,456、lm_head 311,164,928 字节。

## 带宽对照：同内核、同形状的一个反证

[bandwidth.json](../results/bw-20261017T093636Z/bandwidth.json) 在同一台机器、同一 venv 内测三件事：可达流带宽、五个真实形状的 standalone GEMM、以及把整步 113 个 GEMM 串成一张图重放。

对照 trace 的同形状数字（qkv 22.47 / o 12.07 / gate_up 32.49 / down 18.82 / lm_head 774.07 / 整步 GEMM 3177.84 µs），standalone 一律更慢：四个层内 GEMM 慢 1.24–1.33×，lm_head 慢 1.17×，整步慢 1.22×。**同一族内核**已核对：qkv 两侧都是 `cutlass_80_wmma_tensorop_f16_s161616gemm_f16_16x16_128x1_tn_align8`，o/gate_up/down/lm_head 都是 `..._128x2_tn_align8`，所以差异不是内核选择不同。

脚本第一版还犯过一次单位错误：`triton.testing.do_bench` 返回的是毫秒，被当成微秒用，打印出 copy 320866 GB/s 这种数字。修正为 ×1e3 后重跑；那次失败运行的日志仍保留在 `bw-20261017T093055Z`，不作为结果引用。

这条对照同时否掉了两个原本想当然的说法：

- **“trace 里的有效带宽说明逼近 HBM 上限”不成立。** 按字面算 trace 隐含 334–402 GB/s（lm_head 402），高于我在同一机器上能测到的流带宽上限 346.4 GB/s。两个数字不可能同时是硬件上限，说明这是两个测量上下文的差异，而不是“引擎已经把带宽吃满、没有余量”。
- **“换成更快的内核就行”没有证据。** standalone 用的是实际路径同款内核，没有出现“引擎里的内核更慢”的可挖余量；差别是整段的、均匀的（各形状 1.17–1.33×），更像时钟状态或测量上下文因子，而不是某个算子实现落后。

已排除或已限制的解释：内核不同（同名同模板）、L2 命中（311 MB 对 32 MB L2，最多影响约 10%）、`do_bench` 清 L2 的伪影（无 flush 的 CUDA events 与 do_bench 相差 <1%）、grid/block 配置（tail 参数显示满词表 1187 列块）。时钟无法作为证据：WSL 下 `nvidia-smi` 单次查询就要上百毫秒，分阶段采样大量出现 0–1 个样本（本轮 step 阶段只采到 1 个 352 MHz 的样本，明显落在阶段边界），整段循环 40 次重放的 min 与中位只差 0.3%（3894.24 / 3899.79），也说明循环本身没有把时钟推上去。可观测的 SM 时钟范围是 352–2677 MHz、显存恒为 11001 MHz，但没有一个可信的“引擎运行时的稳定时钟”。

因此本轮能站住的结论是：**时间与权重字节成正比、GEMM 占 83.8%、lm_head 占 20.4% 且在图外**；**不能**说这已是硬件上限，也**不能**给出“还有 x% 可挖”。要给出带宽结论，需要在同一进程、同一时钟状态内对照，或锁定时钟后重测；本轮没有做，也不把这两组数字混用。

## 限制

- 用的是带 profiler 的单条 trace（batch2，128 token 输入、短输出），CUPTI 会改变时序，不作为未插桩性能；未插桩基线仍在第一阶段的 batch 数据里。
- 归因依赖“固定内核序列”，对同一 vLLM 版本、同一模型、同一编译配置成立；换版本或换 batch 需要重新核对序列，脚本会断言失败而不是静默错位。
- standalone 与 trace 不是同一进程，时钟状态未对齐（见上）；本轮所有 GB/s 只在各自上下文内可比。
- 第一层 down_proj 偏高的异常未解释。
- 只有一张卡、一条 trace，没有服务器结果，也没有上游改动。
