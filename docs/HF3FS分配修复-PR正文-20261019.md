## Overview

Allocate HF3FS metadata pages only for distinct cache misses. A mixed batch containing an already complete key must not fail when the remaining pages are sufficient for its new keys.

Refs vllm-project/vllm#62389. This addresses the near-capacity allocation subproblem; it does **not** implement eviction or resolve exhaustion of a genuinely full pool. Please keep the issue open.

## Claims

- Existing complete keys reuse their current pages without contributing to the new-page budget.
- Duplicate new keys in one metadata allocation call consume one page, avoiding an unreachable allocation hidden by the key-based response.
- If the distinct misses do not fit, they still fail together; existing hits and the free pool are preserved.

## Details

Previously the allocator reserved `len(keys)` pages before discovering complete cache hits. With two pages, one confirmed key and one free page, requesting `[cached, new]` asks for two new pages. The all-or-nothing primitive returns none, so the new key fails despite having enough space. Resolving hits first makes the reservation size equal to the number of distinct new keys; the response retains the original key order and format.

All changes remain under the existing metadata lock. There is no page recycling, ownership transfer, connector protocol change or additional device synchronization. Incomplete multi-rank keys retain the existing treatment.
