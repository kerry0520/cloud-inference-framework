# 第六阶段：量化干预与上下文长度对 decode 步的影响（2026-10-18）

第五阶段拟合出一个单参数模型：batch-2 decode 步的时间 ≈ 权重字节 / 375 GB/s，
层内 GEMM 占 83.8%，`lm_head` 占 20.4% 且在图外。**相关不等于因果**。本阶段做一个
干预实验：同一台机器、同一个引擎、同一批 prompt，只把权重字节减半（fp16 → fp8
W8A8），看 decode 间隔是否跟着减半；再用不同 prompt 长度把 attention 项放大，检查
"128 token 合成 prompt 让 attention 只占 7.7%"这个已知短板有多大影响。

全部结果在 `results/` 下各自带 `.log` 与 `.exitcode`，证据清单一并给出。

## 1. 预测（跑之前写下来）

若字节模型成立：batch-2 fp16 步时 3.99 ms = 3.18 ms（层内 GEMM）+ 0.81 ms（图外
尾部）。fp8 把权重字节减半，层内 GEMM 应降到约 1.59 ms，步时约 2.40 ms，即 **−40%**。
若瓶颈其实是启动延迟或指令发射（竞争解释），间隔应几乎不动。

注意这条预测的隐含假设：`lm_head` 也被量化。vLLM 的 `quantization="fp8"` 是 W8A8
在线量化，实测**不**量化 `lm_head`，所以真实上界比 −40% 低，后面的数据会看到。

## 2. fp8 在这张卡上是否可用（`results/quant-probe-20261018T090015Z`）

| 项 | 结果 |
| --- | --- |
| GPU / 驱动 | RTX 5060 Laptop，sm_120，torch 2.13.0+cu130，CUDA 13.0，Triton 3.7.1 |
| `torch._scaled_mm` | 可用；`torch.float8_e4m3fn` 可用 |
| vLLM 量化方法 | 含 `fp8`（另有 fbgemm_fp8 / mxfp4 / mxfp8 / modelopt_mxfp8 / gpt_oss_mxfp4） |

单算子对照（同一进程、同一权重、M=1/2/8，µs）：

| 形状 | fp16 | fp8 | 加速 |
| --- | --- | --- | --- |
| `lm_head` M=1/2/8 | 905.20 / 853.04 / 860.40 | 467.66 / 441.49 / 449.92 | 1.94× / 1.93× / 1.91× |
| `qkv_proj` M=1 | 42.03 | 29.33 | 1.43× |
| `qkv_proj` M=2/8 | 28.85 / 29.66 | 34.78 / 34.69 | 0.83× / 0.86× |
| `o_proj` M=1/2/8 | 28.91 / 29.58 / 29.74 | 34.10 / 34.80 / 34.35 | 0.85× / 0.85× / 0.87× |
| `gate_up_proj` M=1/2/8 | 53.79 / 29.92 / 31.28 | 43.54 / 34.24 / 34.22 | 1.24× / 0.87× / 0.91× |
| `down_proj` M=1/2/8 | 32.26 / 62.98 / 36.48 | 58.27 / 32.94 / 34.45 | 0.55× / 1.91× / 1.06× |
| 真实数值误差 | — | rel_err ≈ 0.037–0.039，全部有限 | — |

两个结论：

1. 只有 `lm_head` 这种"一个 kernel 读 311 MB"的形状能干净地把字节优势换成时间优势
   （**1.9×**）。层内四个 GEMM 在 M=1/2/8 时只有十几到几十微秒，启动与时钟噪声主导，
   单独测根本测不准——所以必须到引擎里做配对测量。
2. fp8 走的是真 tensor core：内核名从
   `cutlass_80_wmma_tensorop_f16_s161616gemm_f16_*_tn_align8` 变成
   `nvjet_sm120_qqhsh_mma_64x64x64_12_32x32x64_tmaAB_bz_TNNN`，不是反量化回退。

## 3. 同进程干预：fp16 vs fp8 端到端（`results/quant-decode-20261018T090119Z`）

协议：一个进程里先后启动两个引擎（8 GB 卡放不下两个），greedy、prompt 128 token、
`max_tokens=64`，每臂预热后测量，臂顺序逐轮交替；引擎启动约 26 s，记入
`boot_seconds` 但不算进 decode 间隔。数字是每 token 的 decode 间隔中位数（ms）：

| batch | fp16 | fp8 | 配对变化 |
| --- | --- | --- | --- |
| 1 | 4.2348 | 3.0587 | −25.94% |
| 2 | 4.5187 | 3.3633 | −26.75% |
| 4 | 4.5971 | 3.5400 | −24.24% |

`quantization_applied` 读回为 `"fp8"`，即引擎真的按 fp8 加载，不是静默回退。

**−26% 而不是预测的 −40%**，差额需要解释，不能含糊过去。

## 4. 差额来自哪里：同进程双 trace 分族（`results/quant-profile-20261018T090919Z`）

一次进程里先抓 fp16 臂的 trace，再抓 fp8 臂的 trace（prompt 128、batch 2、12 token），
用 `scripts/attribute_decode.py --by-family` 按内核族聚合（不假设 13 内核层块），
每步 µs：

| 内核族 | fp16 | fp8 | 说明 |
| --- | --- | --- | --- |
| `gemm_fp16` | 4105.60（113 个，max 1100.14） | 884.71（1 个，就是 `lm_head`） | 层内 112 个 GEMM 全部换成 fp8 |
| `gemm_fp8` | — | **1506.25**（112 个） | 层内 GEMM 时间 |
| `quantize` | 1.47 | 164.62（112 个） | fp8 每步多做 112 次激活量化 |
| `attention` | 321.59 | 299.65 | |
| `attention_combine` | 99.92 | 73.02 | |
| `kv_cache_write` | 56.49 | 37.03 | |
| `rms_norm` | 60.17 | 1.00 | 融合进 fp8 路径的其他内核 |
| `other` | 109.14 | 134.81 | |
| `rotary` | 31.93 | 2.08 | |
| `silu_mul` | 22.39 | — | 融合 |
| `sampler` | 15.32 | 15.08 | |
| 合计 | 4824.02 | 3118.25 | profiled −35.4% |

把 `lm_head` 从 fp16 的 `gemm_fp16` 里减掉：层内 GEMM
**4105.60 − 884.71 = 3220.89 → 1506.25，即 0.468×**。预测是 0.5×，实测 0.468×——
字节减半确实把层内 GEMM 时间砍半，字节模型在这一项上成立。

于是"为什么不是 −40%"有了三项可指认的账：

1. `lm_head` 没被 fp8 量化，仍是 884.71 µs，约占整步 20%——这部分完全不缩。
2. fp8 路径每步多 112 个激活量化内核，约 164.62 µs。
3. 未插桩的配对只降到 −26%，而内核层是 −35.4%；差的约 9 个百分点是图外固定开销
   与 fp8 路径额外的启动/同步成本（profiler 自身开销也计入内核和，两者口径不同）。

也就是说：**层内 GEMM 是字节受限（干预后精确减半），但整步还有 20% 的 `lm_head`
与固定的图外尾部不吃这个干预。** 如果要把整步压到 −40%，下一步该做的是让 `lm_head`
也走低精度（例如 W8A8 或 W4A16），而不是继续优化层内 GEMM。

## 5. 把 attention 项放大：prompt 长度扫描（`results/quant-context-20261018T091413Z`）

第五阶段所有测量都用 128 token 的合成 prompt，attention 只占 7.7%——这是"玩具化"
质疑里最实的一条。于是把 prompt 拉到 2048 与 8192 token（fp16、batch 1/2、
`max_model_len = 最长 prompt + 64`），其余协议不变。每 token decode 间隔中位（ms）：

| prompt | batch 1 | batch 2 |
| --- | --- | --- |
| 128 | 4.195 | 4.374 |
| 2048 | 4.976 | 5.856 |
| 8192 | **7.299** | **11.075** |

与 128 token 相比的增量，以及增量对应的 KV 读取量（Qwen3-0.6B：28 层 × 2 × 8 KV 头
× 128 维 × 2 字节 = 114,688 字节/token/序列）：

| 配置 | 增量 | 每 token 读的 KV | 隐含带宽 |
| --- | --- | --- | --- |
| 2048 / b1 | +0.781 ms | 0.235 GB | 301 GB/s |
| 8192 / b1 | +3.104 ms | 0.940 GB | 303 GB/s |
| 2048 / b2 | +1.482 ms | 0.470 GB | 317 GB/s |
| 8192 / b2 | +6.701 ms | 1.879 GB | 280 GB/s |

四个点落在 280–317 GB/s，和权重流（层内 334–402 GB/s、standalone 322–347 GB/s）
是同一个量级——**上下文越长，decode 步越像"按字节读 KV"**。按此拆分，attention 项
占整步的比例从 128 token 的 7.7% 升到 8192 token 的 **42.5%（b1）/ 60.5%（b2）**。

这条扫描同时说明前几个阶段的结论边界：min-p 内核优化、fp8 干预都是在"权重流主导"
的区制里测的；真实长上下文负载里，KV 流会吃掉越来越大的份额，`lm_head` 与 attention
的排序也会变。不能把 128 token 的百分比直接搬到 8k 上下文。

### 第二轮复现：换会话、同一脚本连跑两轮

`scripts/repro_l4.sh` 原本是给租来的 24 GB 卡准备的一条命令。在把它交出去之前先在本机
跑了一遍，等于给上面每个结论补了一次独立复现（新进程、新会话、若干小时后）：

| 结论 | 第一轮 | 第二轮 | 第三轮 |
| --- | --- | --- | --- |
| fp8 vs fp16 decode（b1/b2/b4） | −25.94 / −26.75 / −24.24% | **−25.71 / −26.56 / −24.99%** | — |
| decode 间隔 b1（128/2048/8192） | 4.195 / 4.976 / 7.299 ms | 4.126 / 4.867 / 6.845 ms | **4.185 / 4.937 / 7.508 ms** |
| decode 间隔 b2（128/2048/8192） | 4.374 / 5.856 / 11.075 ms | 4.330 / 5.666 / 9.287 ms | **4.435 / 5.769 / 8.861 ms** |
| min-p 旋钮 decode 差（b1/b2/b4/b8） | −0.77 / −0.80 / −0.78 / −0.80% | **−0.99 / −0.63 / −0.87 / −0.99%** | — |
| `lm_head` fp16 vs fp8 | 1.90–2.06× | 1.94–2.07× | — |

三件事值得记：

1. **效应方向与量级稳定**：fp8 端到端三轮都在 −24%~−27%；min-p 旋钮四轮区间全部
   排除 0（第二轮 batch2 的 decode 区间 [−2.96, −0.48] 明显更宽，但方向一致）。
2. **绝对时间不稳**：8192 token 的 decode 间隔在三次会话里分别是 7.30 / 6.85 / 7.51 ms
   （b1），9.29–11.08 ms（b2），波动约 ±15%。这与第五阶段"跨会话只比配对差、不比绝对值"
   的结论一致：8k 上下文对时钟与内存状态更敏感。
3. `repro_l4.sh` 本身被这条链路验证过：`--dry-run` 打印计划，正式跑按 stage 顺序执行、
   每步保留 `.log`/`.exitcode`，失败的 stage 不中断后面的并汇总报告。

（第一次冒烟时发现 `preflight` 不是 `run_stage.sh` 的 stage，脚本把它当普通 stage 调用
导致该步失败；已改成直接调用 `scripts/preflight.sh`。另有一次 `--dry-run` 未生效，
原因是 Windows 侧写的启动脚本用了 CRLF，转发出去的参数成了 `--dry-run\r`，已改为 LF。）

## 7. 限制

- 单卡、单模型（Qwen3-0.6B）、未锁频。绝对 ms 与 GB/s 不能外推到服务器；可外推的是
  比例（层内 GEMM 减半、`lm_head` 占 26.1% 权重 / 20.4% 时间、attention 随上下文上升）。
- fp8 改变数值，token id 只记录不断言；逐字节数值契约在 min-p 的工作里单独验证。
- KV cache 两个臂都是 fp16，所以第 5 节测的是"上下文长度"而不是"KV 量化"。
- `quant-decode` 的 `boot_seconds` 约 26 s，两臂串行意味着总时长约 1 分钟级，时钟漂移
  仍靠臂顺序交替抵消，但没有锁频证据。
- 8192 / batch 2 的第一轮单次测量出现过 18.4 ms 的离群值（CUDA graph 预热），中位数
  已把两轮四次测量合在一起，离群值仍记录在 `timing.jsonl`。

## 8. 复现

```bash
# 单卡本机（WSL）
dsh-stage.sh quant-probe      # fp8 可用性与单算子对照
dsh-stage.sh quant-decode     # 同进程 fp16 vs fp8 端到端
dsh-stage.sh quant-profile    # 同进程双 trace
dsh-stage.sh quant-family /opt/cloud-inference-framework/results/quant-profile-<utc> --by-family
dsh-stage.sh quant-context    # 128 / 2048 / 8192 prompt 扫描

# 换一台机器（例如租 24 GB 卡）一条命令复跑核心结论
bash scripts/repro_l4.sh --dry-run   # 看计划与预计时长
bash scripts/repro_l4.sh             # 逐 stage 跑，失败也保留目录
```
