## 0. 一句话结论

改动本身能被上游接受的概率，比我们最初以为的高一点，但**不在“两阶段 147 行”这个版本上**：对上游 `min_p.py` 只改两个启动参数（`BLOCK_SIZE 1024→16384`、加 `num_warps=16`）就能拿到本机 3.5–4.2×（大词表、batch 1–8）的内核加速，整请求 decode 仍有 −0.77%~−0.80%，而改动只有 2 行、没有派发、没有回退分支、大 batch 不退化。这是唯一值得拿去上游的形态；两阶段版本更适合留在本项目当“受控接入”的完整案例。

## 3. 方案 A：只改两个启动参数（新证据）

`patches/mrv2_min_p_knob.py` 与 `patches/0002-mrv2-min-p-launch-knobs.patch` 是 pinned 上游文件 + 两处改动：`BLOCK_SIZE = 16384`、`num_warps=16`。没有任何派发逻辑。

| 指标 | 旋钮（2 行） | 两阶段（147 行 + 派发） |
| --- | --- | --- |

## 4. 同方向 PR 已存在：`#58907`，以及同机三方对比

查上游时先搜到的是 <https://github.com/vllm-project/vllm/pull/58907>，**不是 issue**。它是别人已经开着的 PR，做的是“减少 min-p 过滤里的跨 lane 归约”：

- 内核体改成每 tile 用 `max_val = tl.maximum(logits, max_val)`（`max_val` 是长为 `BLOCK_SIZE` 的向量）累积，循环结束后只做一次 `tl.max(max_val, 0)`；
- 启动参数按形状切换：`BLOCK_SIZE = 8192 if vocab_size > 16384 and num_tokens <= 8 else 1024`；
- 顺带新增 `benchmarks/kernels/benchmark_min_p.py`（43 行）与 `tests/v1/worker/test_gpu_min_p.py`（70 行）；作者报告 RTX 5090 上 batch 1 从 70.54 → 27.86 µs、batch 8 → 32.15 µs；
- 状态：`mergeable_state=blocked`，唯一 review 来自 `claude[bot]`，自 2026-09-27 起没有人类 review。

这意味着我们的“两行旋钮”**不是这篇 PR 的内容**（它没有改 `num_warps`，也没有放开大 batch 的 tile），但方向上撞车：审阅者多半会问“为什么不直接改这个 PR”。

### 4.2 收益来自哪里：单独扫 `BLOCK_SIZE`

不改内核体、只改 `BLOCK_SIZE`（fp16、`vocab=151936`、batch 1）：

| BLOCK_SIZE | 1024 | 2048 | 4096 | 8192 | 16384 |
| --- | --- | --- | --- | --- | --- |
| µs | 66.5 | 39.0 | 24.8 | 18.7 | 15.9 |

`num_warps` 在 4/8/16 之间只造成 <10% 差异（见 `results/minp-sweep-20261018T051134Z`）。也就是说：**加宽 tile 解释了几乎全部收益**（每行的跨 lane 归约次数从 149 次降到 10 次），#58907 去掉逐 tile 跨 lane 归约只在其上再省几微秒。

### 4.3 一个具体的短板

#58907 在 `num_tokens > 8` 时退回 `BLOCK_SIZE = 1024`，于是 batch 32 只剩 fp16 40.9 µs（旋钮 28.7 µs）——而大 batch 正是吞吐场景里每个 decode step 都要付这个开销的地方。这一点已写进评论。

## 5. 流程门槛（这是主要风险，不是技术）

`docs/contributing/README.md`（main 上 `CONTRIBUTING.md` 已 404）原文：

> **AI Assisted Contributions** — 1. **Be involved**: Do not submit "pure agent" PRs. The human submitter is responsible for reviewing all changed lines, validating behavior end-to-end, and running relevant tests.
> …2. **Disclose in PR**: Always mention when a pull request includes AI-generated code. 3. **Mark commits**: Add attribution using commit trailers such as `Co-authored-by:`.

含义：**以“agent 自动提交”的形式发 PR 不可行**。要发的话，用户本人必须逐行审阅、在 PR 里披露 AI 参与、并对行为负责。这是硬门槛，不是概率问题。

其他风险（按严重度）：

1. **硬件差异**：所有数字都来自 RTX 5060 Laptop 8GB。`BLOCK_SIZE=16384 + 16 warps` 在 A100/H100/L4 上是否同样有效、是否有寄存器/占用率副作用，未测。上游评审会要求数据中心卡结果。
2. **审阅带宽**：同一文件“只加测试”的 PR #37083 都被 stale 关闭。纯性能 PR 没有 issue 铺垫，很可能同样搁置。
3. **证据标准**：上游性能 PR 通常要 `benchmarks/` 下可复现脚本 + 前后对比 + 多形状矩阵；本项目已有 96 组数值矩阵和 ABBA 方法，但脚本格式与上游不一致。
4. **flashinfer 替代**：mrv2 采样路径刻意用 Triton（为了不绑定 flashinfer 且支持更多 GPU），需要一句话说清，否则会被建议“用现成实现”。
5. **未知项**：`num_warps=16` 对 prefill/大词表以外形状的影响未测；Triton 编译时间与首次 JIT 代价未测；不同 Triton 版本对 16384 块的寄存器分配未测。

## 6. 结论与概率

分三件事，别混在一起：

| 动作 | 成本 | 我的估计 | 理由 |
| --- | --- | --- | --- |
| 开一个 issue，贴本机数据 + 复现脚本，问维护者是否值得做 | 1 小时 + 用户授权 | **高（>80%）能发出去**；有 30–40% 概率得到实质回复 | issue 不要求硬件矩阵，数据本身有说服力；对应文件的 perf 类 issue 近期有先例（#61998） |
| 直接提“两阶段 147 行”PR | 1 天整理 | **低（≤15%）被合并** | 改动大、要派发、只有消费级卡数据、无测试、无 benchmark |
| 提“两行旋钮 + pytest + benchmark_min_p.py”，并附数据中心卡数据 | 3–5 天（含租卡） | **中等（30–45%）** | 改动面小、可测、可回滚；但仍受审阅带宽与硬件验证约束 |

我的建议顺序（**部分已执行**）：在 PR #58907 下贴数据（已完成，两条评论）→ 等维护者表态 → 若仍要独立的最小 PR，先租 L4/A10 复现（1–2 GPU 小时，约 1–2 美元）→ 再写 pytest + benchmark。反过来先写 PR 大概率白做。

修订后的概率：

| 动作 | 状态 | 估计 |
| --- | --- | --- |
| 在 #58907 下贴独立复现与同机对比 | **已完成**（`6246048928`、`6246069554`） | 有 30–40% 概率得到实质回复（PR 已 3 周无人类 review） |
| 另开一个重复 issue | 不应做 | — |
| 独立提“两行旋钮 + pytest + benchmark”PR | 等 #58907 处置 | 若 #58907 被关闭或明确“欢迎简化版”，**中等偏低（25–35%）**；若 #58907 合入，独立价值只剩“放宽大 batch tile” |
| 把 `BLOCK_SIZE` 归因与大 batch 数据并进 #58907 | 可做（需作者/维护者点头） | **较高**：数据直接补上该 PR 的短板，但改动归属在作者 |

## 7. 若用户授权，最小行动清单

1. 租 1 张 L4（或 A10），装 vLLM 0.31.0 wheel，复跑 `scripts/minp_param_sweep.py` 与 `scripts/abba_patch.py`（`--patch-module patches/mrv2_min_p_knob.py`），确认加速与不退化。
2. 在上游 `tests/v1/sample/test_min_p_kernel.py` 写三层测试：与 PyTorch 参考实现逐元素一致、`min_p=0` 行不变、padding/行步长；用我们已有的 96 组矩阵当扩展参数化。
3. 在 `benchmarks/kernels/benchmark_min_p.py` 写基准，形状覆盖 vocab 32k/128k/152k × batch 1–64，报告上游与旋钮的 µs 与加速。
4. 开 issue（附数据、复现命令、明确“愿意提 PR”），等维护者表态。
5. 得到正面回应后再提 PR：披露 AI 参与、`Co-authored-by` 标注、用户本人 review 每一行。
