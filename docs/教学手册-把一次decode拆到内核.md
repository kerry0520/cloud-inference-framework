# 教学手册：把一次 decode 拆到内核

这份手册把项目里做过的事按“**先问什么、再怎么测、最后怎么证明**”重排一遍。
目标不是让你记住结论，而是让你在换一个模型、换一张卡、换一个框架之后，
仍然能自己走完同一条路。

阅读顺序建议：第 1–3 章建立直觉，第 4–5 章学会测量与归因（最容易出错的部分），
第 6–8 章是干预与验证，第 9 章是失败博物馆，第 10 章自测。
每章末尾的“你应该能回答”就是自测题，答案在第 10 章。

原始数据都在 `results/`，逐阶段的叙述在 `docs/第*阶段*.md`，按时间顺序的学习笔记在
`docs/连续学习记录.md`（15 个阶段）。本手册是它们的**结构化重排**，不是替代。

## 1. 先分清三种“时间”

新手第一个坑：把三种完全不同的数字混着说。

| 时间 | 怎么得到 | 能回答什么 | 不能回答什么 |
|---|---|---|---|
| wall time | `perf_counter` 包住一次完整请求 | 用户体感、吞吐 | 内部哪一步慢 |
| decode 间隔 | 相邻 token 时间戳之差 | 生成速度（tok/s 的倒数） | 单个算子的成本 |
| 内核时间 | profiler / CUDA events 量的单个 kernel | 谁占了多少 | 端到端收益 |

本项目的三个基准数字，各自的口径是：

- **一步 3,792 µs**：batch 2、CUDA graph 重放路径上，一个 decode 步里所有 kernel 的
  时长之和（`results/attribute-20261017T093052Z/attribution.json`）。
- **decode 间隔 4.8 ms**：batch 2 请求相邻 token 的实际间隔，比内核时间多出来的约 1 ms
  是调度、采样、Python 侧开销与图内外切换。
- **整请求 −1.10%**：24 轮 ABBA 配对后 decode 间隔的变化中位数，带 95% bootstrap 区间。

同一个优化，在这三个口径下分别是“省 50 µs”“省 1%”“省 1% 且区间不含 0”。
面试时如果只报第一个，就是在误导。

> 你应该能回答：为什么“内核快了 8.9 倍”和“请求快了 1%”可以同时为真？

## 2. 为什么 decode 是小批量、且被权重流卡住

### 2.1 算术强度

一次 GEMM，形状 `X[M,K] × W[N,K]^T`：

- 计算量 ≈ `2·M·N·K` FLOPs
- 访存 ≈ `2·(M·K + N·K)` 字节（FP16）

算术强度 = 计算量 / 访存。当 `M` 很小（decode 时 `M` = batch 大小）：

```
M=2,  N=4096, K=1024  →  2·2·4096·1024 / (2·(2·1024 + 4096·1024)) ≈ 2 FLOP/byte
```

而这张卡的“机器平衡点”（峰值算力 / 峰值带宽）在几十 FLOP/byte 量级。
**2 ≪ 平衡点**，所以这类 GEMM 只能跑到带宽的一小部分，瓶颈是“把权重读进来”。

这就是“decode 是 memory-bound”的定量版本。注意它依赖 `M` 小：`M` 大了，
强度上升，才会转向计算受限。

### 2.2 用数字验证

Qwen3-0.6B 的权重字节（FP16，2 字节/参数）：

| 角色 | 形状 | 权重字节 |
|---|---|---|
| qkv_proj | 4096 × 1024 | 8.39 MB |
| o_proj | 1024 × 2048 | 4.19 MB |
| gate_up_proj | 6144 × 1024 | 12.58 MB |
| down_proj | 1024 × 3072 | 6.29 MB |
| lm_head | 151936 × 1024 | **311.16 MB** |

28 层 × (8.39+4.19+12.58+6.29) ≈ 880.6 MB，加上 lm_head 共约 **1.19 GB**。
一步 3,792 µs 读 1.19 GB，等效约 **314 GB/s**；按角色算有效带宽在 334–402 GB/s。

单参数模型 `t = bytes / B`，用留一法（每次用其余四类拟合 B，再预测被留出的一类）
得到 B ≈ 375 GB/s，五类角色的预测误差最大 12.8%（`results/roofline-20261017T102511Z`）。

**这一步的意义**：不是“发现 decode 是带宽受限”（这是常识），而是**得到一个可以被证伪
的定量模型**——如果某个角色的实测离预测很远，说明那里还有别的东西。

> 你应该能回答：为什么 lm_head 一项能占 20%？它的字节占比是多少？

## 3. 一次 decode 步里到底有哪些 kernel

### 3.1 结构

batch 2、开 CUDA graph 的编译路径，一个稳态步有 **385 个 kernel**：

```
[7 个准备 kernel]
  FillFunctor / arange / _prepare_pos_seq_lens / _combine_sampled_and_draft_tokens
  / _gather_block_tables / _compute_slot_mappings
[28 层 × 13 个 kernel]
  input_norm → qkv_proj → rotary → kv_cache_write → attn_prep → attention
  → attn_combine → o_prep → o_proj → post_norm → gate_up → silu_mul → down_proj
[尾部]
  final_norm → memcpy32_post → vectorized_gather → lm_head → 采样器(10 个)
```

关键观察：**层内 13 个 kernel 的顺序在 28 层里完全一致**，只有第 1 层的
rotary kernel 名字略有不同（`red_fused_1` vs `red_fused_3`）。

### 3.2 为什么能这样断言

`classify()` 给每个位置一个“角色”，然后逐位置断言 28 个层块的角色序列与预期一致；
不一致就抛错，而不是“差不多就行”。这是本项目的习惯：**归因脚本自己会拒绝不可信的输入**。

### 3.3 图内 vs 图外

CUDA graph 里的 kernel 有 `graph_node_id`，图外的没有（记为 0）。实测：

- 图内 366 个 kernel，合计 2,981.76 µs
- 图外 805.59 µs，主要是 **lm_head（774 µs）+ 采样器**，加上 7 个准备 kernel

`lm_head` 在图外是个值得注意的事实：它是单点最大的一项，却不在图里。

> 你应该能回答：为什么“把 lm_head 搬进图”最多只能省 0.7%？

## 4. 怎么测：五个必须避开的坑

### 4.1 单位

`triton.testing.do_bench` 返回的是**毫秒**。我们第一版当成微秒，算出 320,866 GB/s 的
“带宽”，比物理上限高三个数量级。落盘前先问一句：这个数字在物理上可能吗？

### 4.2 冷启动与时钟

GPU 空闲时 SM 时钟在 200–800 MHz，跑满才 2.4–2.7 GHz。同一个 kernel，
冷启动测出来可以是热态的 3–5 倍。做法：先跑一个大矩阵乘 3–5 秒把时钟顶上去，
再测目标；同时记录每个阶段的中位时钟，写进结果文件。

### 4.3 L2 命中

L2 只有 32 MB，而很多 kernel 的输入只有几 MB。如果循环里反复读**同一份权重**，
数据会留在 L2 里，测出来的是 L2 带宽而不是 HBM 带宽。
做法：让每轮读不同的权重切片，保证循环读量 ≫ L2（我们用了“整个 step 的 113 个 GEMM
≈ 1.19 GB”）。

### 4.4 启动开销混进来

单次调用 + 一次 `synchronize` 会把 CPU 端的 Python/驱动开销算进“GPU 时间”。
在 M=2 这种**总时长只有几十微秒**的 kernel 上，这一项足以让结论反转。
做法：连发 100 次再取最小/中位，或者用 CUDA graph 重放。

我们的两套口径：

- `interleaved`：多个变体轮流、每个连发 100 次，取最小。反映“稳态下单次成本”。
- `cudagraph`：把整串调用录进图后重放。反映“真实引擎里排队后的成本”。

两者可以差 30%（比如 PR 版 17.6 vs 13.4 µs），所以报数时必须说明口径。

### 4.5 profiler 的开销

CUPTI 抓 trace 时每个 kernel 都多几微秒。**带 profiler 的绝对时间不能当性能数字**，
只能用来做占比和归因。我们的做法是：归因用 profiler，性能用无插桩的配对测量，
两者交叉验证量级（56.9 µs 的节省 ÷ 4.8 ms 的步长 = 1.18%，与实测 1.10% 一致）。

> 你应该能回答：为什么同一份 kernel 在 profiler 里和不在 profiler 里，占比可以差 10 倍？

## 5. 怎么归因：CUDA graph 里没有 correlation id

正常情况可以用 kernel 的 `correlation` 关联到“哪一次 launch”。但 CUDA graph 重放时，
kernel 是驱动一次性推下去的，trace 里**没有可用的 correlation**。

我们用的替代方案，三个条件缺一不可：

1. **模态步**：相邻两个用户标注（`gpu_user_annotation`）之间是一个 step，取 kernel 数
   最多的那个数（385）作为基准，数量不同的步整步丢弃（我们丢了 step 0 和 step 11）。
2. **固定序列**：28 层 × 13 个 kernel，逐位置断言。
3. **node id 对照**：图内 kernel 的 `graph_node_id` 互不相同，图外的为 0。

三条合起来，才能说“第 14 个 kernel 是第 2 层的 qkv_proj”，而不是“大概是”。

> 你应该能回答：如果某一层用了不同的融合 kernel（位置数变了），上面的方法会怎样失效？

## 6. 干预：把相关关系变成因果关系

有了 `t = bytes / B` 的模型，下一步不是“再优化一点”，而是**去改 bytes，看时间跟不跟**。

### 6.1 fp8 干预

把层内权重换成 fp8（字节减半），预测：层内 GEMM 时间减半，`lm_head` 不变
（vLLM 的 fp8 量化不覆盖 lm_head），所以整步应该降约 35%。

实测（同进程、两个引擎、同一批 prompt）：

| 指标 | fp16 | fp8 | 比值 |
|---|---|---|---|
| 层内 111 个 GEMM | 3,220.89 µs | 1,506.25 µs | **0.468×** |
| lm_head | 884.71 µs | 884.71 µs | 1.00× |
| 新增 quantize kernel | — | 112 个，164.62 µs | — |
| 一步 kernel 总和 | 4,824 µs | 3,118 µs | −35.4% |
| **整请求 decode** | — | — | **−25.9% / −26.8% / −24.2%** |

三个数字放在一起讲：**层内确实减半**（模型成立），**lm_head 拖后腿**（模型也成立），
**整请求只有 −26% 而不是 −35%**（因为新加的 112 个量化 kernel 和 profiler 外的开销）。

### 6.2 长上下文干预

把 prompt 从 128 拉到 8192，预测：attention 的占比上升，decode 变慢。

实测 decode 间隔（batch 1 / batch 2）：4.20/4.37 ms → 4.98/5.86 → 7.30/11.08 ms；
attention 占比 42.5% / 60.5%。这说明“我们只有 1% 收益”不是方法问题，而是
**在一个 attention 只占 7.7% 的短上下文负载上做优化**。

### 6.3 为什么要做干预

只看 trace，你能说“时间 ∝ 字节”。做了干预，你才能说“**改字节，时间就按比例变**”。
前者是相关，后者是因果。面试里这两句话的可信度差一个数量级。

> 你应该能回答：如果 fp8 之后整请求只快了 26% 而不是 35%，你会怎么定位差的那 9%？

## 7. 内核级：min-p 为什么能快 4–10 倍

### 7.1 上游实现

`vllm/v1/worker/gpu/sample/min_p.py` 的内核：**每行一个 CTA**，`BLOCK_SIZE=1024`，
分块把整行词表（151936）扫两遍：

1. 第一遍求行最大值 `max_val`
2. 计算阈值 `threshold = max_val + log(min_p)`
3. 第二遍把所有 `< threshold` 的 logits 置 `-inf`

一个 CTA 串行扫 148 个块，每次只有 1024 个线程在干活。这解释了为什么它慢：
**不是带宽，是并行度**。

### 7.2 两种改法

| 方案 | 做法 | 代价 | 局部收益 |
|---|---|---|---|
| 两阶段 | 每 (行, 4096 列块) 一个 CTA 求部分最大，再一个 CTA 归约+过滤 | 新增暂存 + 派发 | 4.2–9.7× |
| 两行旋钮 | 只把 `BLOCK_SIZE` 改成 16384、`num_warps` 改成 16 | 两行 | 3.6–4.2× |

两行旋钮能拿到大部分收益，因为它把“一个 CTA 串行 148 次”变成“一个 CTA 一次处理
16384 列，9 次扫完”。收益来自**并行度**，不是算法。

### 7.3 跨机器验证：为什么这不是“笔记本特例”

在租来的 RTX 5090 上重跑同一内核（同 pinned 文件、同 PR diff、同计时协议）：

| batch | 5060 上游 | 5090 上游 | 5090 旋钮 |
|---|---|---|---|
| 1 | 66.0 | 66.7 | 18.6 |
| 8 | 67.5 | 70.2 | 17.6 |
| 32 | 71.8 | 70.3 | 17.6 |

**换一张快得多的卡，上游内核一点没变快。** 这条比“我快了 4 倍”更有说服力：
它直接证明成本是发射/延迟，而不是带宽。

> 你应该能回答：为什么“换卡不变慢也不变快”能支持“发射受限”这个结论？

## 8. 端到端：1% 的差异怎么测才算数

### 8.1 为什么不能“多跑几次取平均”

GPU 时钟、CPU 频率、后台进程都会漂移，同一配置两次运行可以差 2%。
把 A 跑 10 次、B 跑 10 次再比均值，漂移会直接变成“结论”。

### 8.2 配对设计

- 两个臂**常驻同一进程**，只切换一个函数指针（不重启引擎、不重新加载模型）；
- 每轮按 ABBA / BAAB 交替，抵消顺序效应；
- 每一轮内两臂各测一次，得到**轮级配对差**，再对轮级差做 bootstrap（10000 次）取 95% 区间。

这样做的代价是每轮要多跑几次请求，好处是漂移被配对消掉了。

### 8.3 采样不可复现

vLLM 的采样在 batch ≥ 4 时，同一臂连续两次调用都可能差一个 token（我们在 batch 4 上
量到过第 3 个 token 分叉）。所以：

- **不能用“输出完全一致”当验收标准**；
- 正确性用**过滤后的 logits 逐字节对比**；
- token id 只作旁证，报告“48/48 一致”时要说明这是旁证而不是证明。

### 8.4 结果怎么写

```
batch 2：decode 间隔 −1.10%，95% CI [−1.37, −0.85]，24 轮 ABBA
batch 8：−0.91% [−1.55, −0.75]
batch 32：−0.81% [−1.61, −0.26]
```

区间不含 0 才能说“有改善”；区间宽说明轮数不够或负载抖动，要如实写出来
（我们有两次运行就是因为 batch 32 出现整轮漂移，把区间拉宽到 ±10%）。

> 你应该能回答：为什么“局部 10×、整请求 1%”不是失败，而是一个可预测的结果？

## 9. 失败博物馆（都是真发生的）

| 失败 | 症状 | 根因 | 教训 |
|---|---|---|---|
| 单位错误 | 带宽 320,866 GB/s | `do_bench` 返回毫秒 | 先做物理合理性检查 |
| 闭包晚绑定 | 三个变体数字完全相同 | `lambda w=work: ...` 捕获了循环变量 | 变体对比先断言“结果不同” |
| 独立随机张量 | 边界探针 parity 失败 | 两次 `rand()` 生成不同数据 | 对照组必须是同一 base 的克隆 |
| 目录覆盖 | 两个结果互相覆盖 | 目录名只精确到秒 | 加随机后缀 |
| CRLF 吃掉参数 | `--dry-run\r` 不匹配 | PowerShell 写脚本默认 CRLF | shell 脚本一律 LF，并在 CI 里 `bash -n` |
| 中文路径经 argv | `cp: cannot stat '/patches/...'` | wsl.exe 传参损坏 | ASCII 路径 / 软链 |
| `pkill -f` 自杀 | SSH 会话被自己杀掉 | 模式匹配到了自己的命令行 | 用 `[p]attern` 或按 PID |
| profiler 当性能 | 占比与无插桩差 10 倍 | CUPTI 开销 | 归因与性能分开测 |
| PowerShell 改 UTF-8 | 整篇文档变乱码 | PS 5.1 按 ANSI 读 | 中文文档用编辑器/工具改，不用 shell 重写 |

这份表比任何“最佳实践”都值钱，因为每一条都对应一个被浪费的小时。

## 10. 自测题（答案要点）

1. **为什么内核快 8.9× 而请求只快 1%？**
   分母是 4.8 ms 的一步，min-p 只占其中约 120 µs；8.9× 省下约 100 µs，占 2%；
   再扣掉派发、图外开销，实测 1.1%。收益上限由“该算子在步里的占比”决定。
2. **为什么 lm_head 占 20%？**
   它一步读 311 MB，占 1.19 GB 的 26%，时间占比 20.4%，与字节占比同量级。
3. **为什么“把 lm_head 搬进图”最多省 0.7%？**
   图内外之间的空档实测约 28 µs/步，而一步约 3.9 ms。
4. **profiler 里和不在 profiler 里为什么差 10 倍？**
   CUPTI 在每个 kernel 前后插入记录，M=2 的内核只有几微秒，插桩开销与之同量级。
5. **CUDA graph 里怎么归因？**
   模态步 + 固定序列断言 + graph_node_id；不能依赖 correlation。
6. **fp8 为什么不是 −35%？**
   层内 GEMM 确实 0.468×，但 lm_head 未量化、新增 112 个量化 kernel，
   两者抵消了约 9 个百分点。
7. **为什么换卡后内核时间不变？**
   一个 CTA 串行扫 148 次的发射/延迟成本与 SM 数量、带宽关系不大；
   变快的是“并行度”，所以调大 BLOCK 立刻见效。
8. **为什么采样 id 不能当验收？**
   同臂内也会漂移（batch≥4 观测到第 3 个 token 分叉），只能作旁证。
9. **配对测量解决什么问题？**
   把时钟漂移、后台干扰从“组间差异”变成“轮内噪声”，再用轮级 bootstrap 给区间。
10. **这个项目最该被质疑的地方是什么？**
    单机消费级卡、合成 128 token 负载、端到端收益 1% 量级、上游未合入。
    诚实的答法是：结论的**结构性部分**（字节占比、占比决定上限、发射受限）可移植，
    **绝对值**不可移植。

## 11. 最小复现路径（30 分钟）

```bash
# 1) 环境（一次性）
bash scripts/setup_cuda.sh && bash scripts/preflight.sh

# 2) 一步的归因（用已提交的 trace）
dsh-stage.sh attribute          # → results/attribute-*/attribution.json

# 3) 单参数模型
dsh-stage.sh roofline           # → results/roofline-*/roofline.json

# 4) 内核三方对照（需 GPU + torch + triton）
bash scripts/free_gpu_compare.sh --out /tmp/free --batches 1,2,8

# 5) 端到端配对（需完整 vLLM 栈 + 权重）
dsh-stage.sh abba-knob --rounds 8 --batches 2
```

`dsh-stage.sh` 是本机的一个薄封装（把中文路径软链成 ASCII 再调
`scripts/run_stage.sh`）。每个 stage 都会新建带时间戳的目录，写出
`<stage>.log` 与 `.exitcode`，失败结果不覆盖。
