RTX 5060 Laptop 8151MiB、SM120，WSL2 Ubuntu 24.04，Python 3.12.3；vLLM 0.31.0、torch 2.13.0+cu130、FlashInfer 0.7.0.post1。固定源码提交及模型 revision 见[环境与复现](环境与复现.md)。当前使用官方 wheel，阅读的上游 checkout 干净。

真实启动日志确认 MRV2、FlashAttention 2，生效配置记录确认 FULL_AND_PIECEWISE CUDA Graph。没有显式关闭异步调度，但首轮配置快照未独立导出 resolved async_scheduling 字段，不把版本默认值冒充实测开关记录；采集脚本已为后续补该字段。使用 FP16，关闭 prefix caching 避免重复输入缓存影响。WSL pinned memory 经现成开关启用，小规模复制验证通过；没有修改上游的内存策略。

成功预检查：[preflight-20261017T020628Z](../results/preflight-20261017T020628Z/)。GPU 矩阵乘、pinned-memory 异步复制、FlashInfer top-k/top-p 采样均有真实退出码 0 和非空结果。它们不代替模型准确率评估。

## 无 profiler 的第一组基线

记录：[baseline-pinned-20261017T020743Z](../results/baseline-pinned-20261017T020743Z/)，外层退出码 0，status=passed，16 条批次记录经 SHA256、输出数量及长度复核。4 组各 1 轮预热、3 轮测量；共 60 次请求，其中 45 次属于正式测量。每请求输入 128 个合成有效 ID、固定输出 128 token，忽略 EOS。

| 同时提交请求数 | 批次 wall 中位数 ms | 总输出吞吐 token/s | 各请求平均 Decode 间隔的中位数 ms |
|---|---:|---:|---:|
| 1 | 549.6 | 232.9 | 4.20 |
| 2 | 565.7 | 452.5 | 4.24 |
| 4 | 562.3 | 910.5 | 4.18 |
| 8 | 634.4 | 1614.2 | 4.66 |

wall 包含 prefill 和引擎处理，不是纯模型计算。Decode 平均间隔由同一引擎时间域的首末 token 时间差除以后续 token 数；表中再对请求取中位数，并不是逐 token P50。总吞吐也不等于单请求出字速度。每组仅 3 次测量，batch8 的 wall 有明显波动（约604～716ms），不能据此作稳定性能承诺。

同 batch 重复 greedy token 序列一致，只证明这些有限合成输入的生成轨迹可复现；没有完整 logits、任务质量或跨后端数值验收。

## 两组时间线及初步判断

1. [稳定 batch2](../results/profile-pinned-20261017T020913Z/)：外层退出 0；采到 12 对 CPU/GPU 标记，全为 `context_0 / generation_2`。有 4,621 条 GPU kernel 记录和 12 次 cudaGraphLaunch。
2. [请求陆续结束](../results/churn-pinned-20261017T021129Z/)：8 个请求分别固定生成 8/16/24/32/40/48/56/64 token。预热与采样各一轮均完成，外层退出 0；24 步采样中 generation8/7/6/5 分别出现 6/9/8/1 次，有 9,260 条 GPU kernel 记录和 24 次 cudaGraphLaunch。只覆盖完成请求造成的批次收缩，不覆盖新请求到达、抢占或取消。

剔除首个 GPU 标记，按随后首个标记起点到最后标记终点裁剪，把所有 kernel 时间段合并求并集：两份记录的窗口内 kernel 活动覆盖约 96.2% 和 96.1%。这是特定带 profiler 窗口的时间覆盖，不是 SM 利用率、算力利用率或未插桩运行的 GPU 利用率。它只提示所采窗口没有很大的无 kernel 空档，不能排除依赖、同步或低效率内核。

按名称包含 gemm 的内核累计时长，分别约占全部 kernel 累计时长的 83.8% 和 81.2%。这使线性层执行值得优先继续归因，但不能据此宣称显存带宽瓶颈或认定现有 GEMM 已最优。

CPU 标记耗时中位数约 1.04/1.07ms，GPU 标记约 3.11/3.31ms；它们覆盖范围不同且可以重叠，不能相加推断一步耗时。GPU 标记以外也有采样、准备等 kernel。记录中的同步 API 不自动等于缺陷，需要看线程、用途及依赖。

所有 profiler 请求耗时都排除在正式性能结果之外。单次短 trace 只用于初筛，需要后续针对性实验。

## 本轮筛选结果

暂不优先修改 CPU 调度或输入元数据准备：在当前模型、短上下文、batch1～8、本机 GPU 与这些纯 Decode 场景下，没有足够证据证明它们是主要可消除瓶颈。这个结论不推广到服务器或其他负载，也不否定此前候选问题域。

下一轮优先把耗时矩阵乘对应到具体线性层和实际 M/N/K，核实默认算子/后端已经做了哪些选择，再判断它是既有配置问题、形状专项算子问题还是值得修改的框架执行路径。不预先承诺自写 GEMM，也不因内核名含旧架构字符串就认定不适配当前显卡。

- WSL 官方模型文件请求曾停滞，保留 v1/v2 日志，通过 Windows 同一官方固定 revision 补词表后完成 blob/LFS 校验。

这些是环境准备成果，不当作框架贡献。最终依赖快照为 bootstrap 的 requirements-final.lock.txt，原始初装快照也保留。
