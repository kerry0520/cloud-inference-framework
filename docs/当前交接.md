## 本轮结论（可直接引用）

- **同机三方对比**（`vocab=151936`，µs，单次启动中位；括号内为排队口径）：
  fp32（PR 基准脚本与我们引擎真实 logits 的 dtype）：upstream 66.9 (69.5) / knob **20.3 (22.6)** /
  #58907 25.4 (27.5) @ batch1；batch32 76.1 (78.7) / **49.4 (51.8)** / 54.9 (57.8)。
  fp16：batch1 64.2 (66.0) / **12.6 (15.9)** / 15.5 (18.4)；batch32 69.1 (71.5) / **26.2 (28.7)** /
  38.4 (40.9)。**两个 dtype、两种口径、所有 batch，两行旋钮版都更快。**
- **收益归因**：内核体完全不动、只改 `BLOCK_SIZE`（fp16、V151936、batch1）：
  1024→66.5、2048→39.0、4096→24.8、8192→18.7、16384→15.9 µs；`num_warps` 4/8/16 差异 <10%。
  即“加宽 tile 把跨 lane 归约从 149 次摊到 10 次”解释了几乎全部收益，#58907 去掉逐 tile 归约只是
  在此之上再省几微秒。
- **#58907 的短板**：`num_tokens > 8` 退回 `BLOCK_SIZE=1024`，batch32 只有 fp16 40.9 µs
  （旋钮 28.7）。这条已写进评论。
- 结论边界：单卡 RTX 5060 Laptop、未锁频、PyTorch 2.13.0+cu130 / Triton 3.7.1、只测 Qwen3-0.6B
  的词表与 `min_p=0.1`；旋钮同时改了 tile 与 `num_warps`（未做纯 tile 的严格消融，但 4/8/16 的
  差异 <10% 已把 warps 的影响限住）；不能外推到数据中心 GPU。
- 概率修订：重复 issue 不应发；“两行 + pytest + benchmark”独立 PR 的命运取决于 #58907 的处置
  （若 #58907 合入且保留 1024 回退，独立价值只剩“放宽大 batch tile”）。
