# 第四阶段：min-p 两阶段内核的可审查框架补丁与真实路径复核

本轮把副目标从“worker extension 里验证过的候选内核”推进到“可以审查、可以回滚、可以直接打进 pinned 上游的一处补丁”，并在真实 MRV2 引擎里确认补丁确实走了新内核、真实 logits 逐字节不变。结论分三层：**补丁与上游语义逐字节等价**有 96 组用例和真实引擎证据；**派发边界可预测**由逐个用例的内核计数器与端点探针证明；**局部收益不等于整请求提速**，整请求仍只有前几轮约 1% 量级的小样本结论。

范围仍是 vLLM 0.31.0 / `db9527a`、Qwen3-0.6B、RTX 5060 Laptop 8GB、WSL；只覆盖 MRV2 采样路径里的 min-p 过滤，不外推到服务器、其他版本或其他模型。

## 上游实现与调用链

pinned 上游的 min-p 在 `vllm/v1/worker/gpu/sample/min_p.py`（60 行），不在 `vllm/v1/sample/ops/`：

- `_min_p_kernel(logits_ptr, logits_stride, expanded_idx_mapping_ptr, min_p_ptr, vocab_size, BLOCK_SIZE: tl.constexpr)`：每个 request 行一个 CTA，`BLOCK_SIZE=1024`，`min_p == 0` 时整行提前返回；先扫一遍求行最大值，再算 `threshold = max_val + tl.log(min_p)`，第二遍把 `logits < threshold` 原位写 `-inf`。
- `apply_min_p(logits, expanded_idx_mapping, min_p) -> None`：按 `expanded_idx_mapping` 取每行的 `min_p`，启动网格 `(num_tokens,)`。
- 调用点：`states.py:10` 导入；`SamplingStates.apply_min_p`（`states.py:94`）在 `np.all(self.min_p.np[idx_mapping_np] == 0.0)` 时整批跳过内核；`sampler.py:265` 调用该方法。

两阶段版的动机不是少扫一遍（仍然两遍），而是把“每行一个 CTA 串行扫 151936 列”换成“每行每 4096 列一个 CTA 并行求部分最大值，再一次归约算阈值并过滤”。这解释了为什么收益随行数增加而衰减：行数越多，原实现的并行度自己就上来了。

## 补丁内容

- 文件：`patches/0001-mrv2-min-p-two-stage.patch`（147 insertions、0 deletions，目标 `vllm/v1/worker/gpu/sample/min_p.py`，index `b71ae6f..d0cb01e`）与 `patches/mrv2_min_p.py`（打完后完整文件，sha256 `a4da6ec1…`）。
- 新增 `_min_p_partial_max`（每 `(row, part)` 一个 CTA，4096 列一段，部分最大值写 float32 暂存）与 `_min_p_apply_threshold`（归约 `num_parts` 个部分最大值、算阈值、过滤并回写）。
- `_use_parallel_path(logits, num_tokens, vocab_size)` 的谓词：`1 <= rows <= 8`、`vocab >= 32000`、`logits.stride(1) == 1`、dtype ∈ {float16, bfloat16, float32}。不满足就退回原 `_min_p_kernel`（`BLOCK_SIZE=1024` 不变）。
- `_apply_parallel` 每次调用新分配 `torch.empty((rows, num_parts), dtype=torch.float32)`，不缓存跨调用状态；`logits_stride` 作为运行期参数传入，不是 constexpr（允许行步长大于词表宽）。
- 内核名沿用候选阶段已被 trace 验证过的 `_min_p_partial_max` / `_min_p_apply_threshold`，上游原内核名 `_min_p_kernel` 保留，便于按名字区分路径。

边界为什么是 1–8 行、≥32000 词表：micro 证据里 V151936 的 batch1/2/4/8 分别约 9.7×/8.8×/6.2×/3.8×，而 V4096 的 batch2–8 候选反而慢 12–14%（0.88×），V151936 batch32 只有 1.03×。两阶段在大 batch 下 CTA 过碎，收益被归约与暂存吃掉，所以窗口取得保守，宁可回退。

## 验证

### 补丁本身（`run_stage.sh patch`，`results/patch-20261017T095423Z`）

- 补丁 apply 到 pinned 文件的干净副本后，与 `patches/mrv2_min_p.py` **逐字节相同**；checkout 里已安装的 wheel 文件与 pinned 源文件逐字节相同（`4cb5e2f4…`），说明"上游文件"和"运行的包"是同一份。
- 96 组用例（3 dtype × 10 vocab × 3 batch + 6 特例；storage 宽 `vocab+7` 以覆盖行 padding）全部与上游逐字节相同；其中 **21 组实际走并行路径、75 组走回退路径**，每个用例启动哪个内核由替换后的内核对象计数，不靠推断。
- 边界探针（`patch-verification.json` 的 `dispatch_probes`）：

| 探针 | 期望 | 实际派发 | 数值一致 |
|---|---|---|---|
| rows=8, vocab=32000（两端闭合） | 并行 | 并行 | 是 |
| rows=1, vocab=32000 | 并行 | 并行 | 是 |
| rows=8, vocab=31999 | 回退 | 回退 | 是 |
| rows=9, vocab=151936 | 回退 | 回退 | 是 |
| rows=0（空 batch） | 回退 | 回退 | 是 |
| 列 stride=2 | 回退 | 回退（谓词拒绝） | — |
| float64 / float8 | 回退 | 回退（dtype 守卫拒绝） | — |

- 通过补丁入口计时（同一次运行内 upstream → patched，µs）：

| vocab | batch | 走并行 | upstream | patched | 倍率 |
|---:|---:|:--:|---:|---:|---:|
| 151936 | 1 | 是 | 121.92 | 11.97 | 10.19× |

注意：倍率只能在同一运行内比较。同一次“补丁复核”此前还有一次通过到 `patch-20261017T094747Z` 的记录，那次 upstream 的绝对耗时（151936/batch1 约 173 µs）比本次高约 40%，属于 GPU 时钟状态差异，不能把两次的倍率混用；本次是因为旧目录里留了生成补丁用的 `.git` 与 `__pycache__` 垃圾，修好脚本后重跑出的干净证据，96 组结论与派发计数完全一致。也不要和第二阶段 micro 的 9.70×/8.77× 直接对比。

### 真实引擎（`run_stage.sh minp-patch-engine`，`results/minp-patch-engine-20261017T095122Z`）

worker extension 用 `importlib` 从路径加载 `patches/mrv2_min_p.py`，再包住 `SamplingStates.apply_min_p`（不改安装的 wheel、不改 `vllm-src/`）。batch2、4 token 的真实 MRV2 调用：

```json
{"mode": "verify", "calls": 4, "checked": 4, "mismatches": 0,
 "shapes": {"(2, 151936)": 4},
 "kernels": {"_min_p_kernel": 0, "_min_p_partial_max": 4, "_min_p_apply_threshold": 4}}
```

即：4 次真实 logits 与上游逐字节相同，且 4 次都实际启动了新内核、`_min_p_kernel` 一次都没启动。这说明补丁在真实路径上"接进去了而且数值对"，不是只在小矩阵里对。

## 失败与迭代（保留、不覆盖）

| 目录 | 现象 | 原因与修正 |
|---|---|---|
| `results/patch-20261017T094720Z` | 边界探针 parity 失败 | 探针里 `rand()` 给了两个独立随机张量；改为同一 base 的两次 `clone()` |
| `results/patch-20261017T094738Z` | `TypeError: 'float' object is not subscriptable` | `do_bench(quantiles=[.5])` 返回标量；改为 `quantiles=[.5,.2,.8]` 取 `[0]` |
| `results/minp-patch-engine-20261017T094858Z` | 通过 | 但目录里多复制了一份旧候选 `candidate.py`，易误认；后续加了条件复制 |
| `results/minp-patch-engine-20261017T094949Z` | EngineCore 崩溃 | 计数器用普通函数替换内核，`kernel[grid]` 报 `'function' object is not subscriptable`；改为带 `__getitem__` 的计数器类 |
| `results/minp-patch-engine-20261017T095037Z` | 通过 | 计数器已修好，但目录仍带旧 `candidate.py`；脚本修好后重跑得到 095122Z |
| `results/patch-20261017T094747Z` | 通过 | 96 组结论与派发计数同 095423Z，但目录里混进了生成补丁用的 `apply/.git` 与 `__pycache__`；`git init` 从脚本去掉、禁用字节码写入后重跑得到 095423Z |

两条脚本 bug 都被断言当场抓住（parity 不符、引擎崩溃），没有污染结论；这也说明"先写断言再跑"是值得的，代价是几轮重跑。

## 限制与未验证

- 补丁绑定 `db9527a`，其他 vLLM 版本需重生成；上游若改了采样路径，`apply_min_p` 的调用方式可能变化。
- 未测 CUDA graph 捕获下的分配行为。已有 trace 显示采样器内核在图外（尾部 375–384 的 graph node id 为 0），但那是候选阶段的证据，不是对本补丁的专门测试。
- 未测多卡/TP、异步调度、投机解码、混合 batch 中部分请求 `min_p=0` 的边界组合；`states.py` 的整批跳过逻辑未改动。
- 整请求端到端只有本机 batch1/2/4 小样本（约 1%、batch1 不稳定），不能推广；局部 4–10× 不构成端到端提速承诺。
- 向上游提 PR / issue 需要用户明确授权，本轮未做。

## 复现

```bash
# 补丁复核（apply、逐字节对比、96 组、边界探针、计时）
wsl -d Ubuntu-24.04 -- bash /tmp/repo/scripts/run_stage.sh patch

# 真实引擎路径复核（只做补丁校验，不跑整轮计时）
wsl -d Ubuntu-24.04 -- bash /tmp/repo/scripts/run_stage.sh minp-patch-engine
```

`/tmp/repo` 是指向本项目的中文路径的 ASCII 软链（`ln -sfn "/mnt/c/Users/32065/Documents/ChatGPT/云端推理框架" /tmp/repo`），因为含中文的路径经 `wsl.exe` argv 传入会损坏。WSL 重启后软链会消失，需要重建。
