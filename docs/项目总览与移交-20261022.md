## 2. 三条工作线（彼此独立，别混着讲）

### 线 A：主分析——一个 decode step 的钱花在哪

- 用 CUPTI trace 取 batch 2 的稳态步：**385 个 kernel/步**（7 个准备 + 28 层 × 13 + 尾部），
  单步内核时间 **3,792 µs**。
- **GEMM 占 83.8%**（3,177.8 µs）；`lm_head` 一个 kernel 就 774 µs（**20.4%**），
  而且它在 **CUDA 图外**（graph node id = 0），所以不会被图发射掩盖。
- 四个层内 GEMM 的时间与权重字节近似成正比，隐含有效带宽 334–402 GB/s →
  解码步是**权重流受限**（M=2 的 GEMM 退化成 gemv 型）。
- 已撤回的说法：不能说“达到 HBM 上限”，也不能用“还有多少余量”推收益。
  独立微基准只能测到 322–346 GB/s，与引擎内隐含值存在未解释的时钟状态差异。

**结论的价值**：这些比例由模型结构决定（`lm_head` 权重 311 MB vs 28 层 GEMM 880.6 MB
= 26.1%），换卡仍成立；绝对数字不能外推。

### 线 B：min-p 采样内核（副目标）

- 真实路径：`SamplingStates.apply_min_p` → `vllm/v1/worker/gpu/sample/min_p.py`，
  原实现每行一个 CTA、`BLOCK_SIZE=1024`、两遍扫词表。
- 我们的两阶段版：4096 宽并行部分最大值 + 并行归约过滤，**局部 122.9 → 14.0 µs（约 8.8×）**；
  96 组逐字节对照、真实 logits、派发计数全部通过。
- **整请求**：两轮独立会话，请求平均 decode 间隔配对变化 **−1.10% / −1.00%**
  （95% CI 不含 0）。上限约 1.3%，实测 1.1% 已接近上限。
- 提交形态：`patches/` 下完整文件 + 补丁；另有一个**两行启动参数版**
  （`BLOCK_SIZE=16384`、`num_warps=16`），本机整请求约 −0.8%，但只有 2 行、无派发风险。
- 上游同方向 PR #58907（作者 `cyanseek`）已发三条数据评论，最近一次是应其邀请对
  commit `95e9d21` 的本机交叉验证（per-lane 归约在相同 8192/16 下 1.25–1.31×，
  与其 A100 的 1.26× 一致）。

### 线 C：HF3FS KV 页管理（上游贡献，与线 A/B 无关）

- **PR #62393**（已发布，open，0 review）：修复混合 cache hit/miss 误算新页预算、
  同批重复 key 丢页号。18 个元数据测试 + 真实 HTTP + 受控 GPU 保存/加载验证。
- **PR #62693**（已发布，ready for review，stacked 在 #62393 上，head `c9b2b40`）：
  满池后的**读租约 + LRU 淘汰**。核心不是加 LRU，而是给读者一个在途信号——
  scheduler 用 `batch_key_exists` 判定命中、worker 稍后才 `get_key_locations`，
  中间窗口若被淘汰就会读错数据。
- 本地：26 个元数据测试 + 真实 localhost HTTP 探针通过。
  **第三方**（issue #62389 作者 `sivabreddy`）在两台 H100 + 真 3FS 上验证：池满后保存继续、
  被租 29/29 存活 vs 未租 0/29、过期租约 134 s 回收、28 次 needle 0 错答案。
- 两条 PR 都卡在 `pre-run-check`：仓库策略要求作者有 ≥4 个已合并 PR 或维护者加标签，
  脚本明确禁止 AI agent 索要标签。**这条不能自解，只能等**。

## 3. 数字台账（每个数都要带口径）

| 数字 | 口径 | 条件 | 能否外推 |
|---|---|---|---|
| 3,792 µs | 单步**内核**累计（带 profiler 的 trace） | batch 2、128 token prompt、28 层 | 否（含插桩） |
| 83.8% / 20.4% | 同一 trace 内的占比 | 同上 | 比例可迁移，绝对时间不可 |
| 8.8×（122.9→14.0 µs） | 内核局部微基准 | FP32、V151936、batch 2 | 只适用于该形状窗口 |
| −1.10% / −1.00% | 请求平均 decode 间隔，配对 24 轮 bootstrap | 两次独立会话 | 本机该形状 |
| −0.8% | 两行旋钮版，同口径 | batch 1–8 | 同上 |
| −25.9/−26.8/−24.2% | FP8 引擎同进程配对 | batch 1/2/4 | 硬件相关，含精度变化 |
| 4.20→7.30 / 11.08 ms | decode 间隔随上下文 128→2k→8k | batch 1 / 2 | 本机 |
| 322–346 GB/s | 独立流带宽上限 | 5060 Laptop | 硬件相关 |

**红线**：不写“8.9× 加速”“端到端提速 8.9×”“已达硬件上限”“上游已接受”。

## 5. 已知坑（都是真踩过的）

1. `triton.testing.do_bench` 返回**毫秒**，直接当 µs 用会让带宽虚高 1000 倍。
2. vLLM 采样在本机**不是逐位可复现**：同一 arm 两次相同调用也可能差 1 个 token，
   所以 token id 只能当旁证，不能当 oracle。
3. CUDA graph replay 的 kernel **没有 correlation id**，只能按“模态步 + 固定内核序列 +
   graph node id”归因。
4. PowerShell 内联中文会 `ParserError`；改中文文档用 edit 工具或写临时 `.py` 文件。
5. PowerShell 5.1 读 UTF-8 会被当 ANSI，`Get-Content|Set-Content` 会把中文文档写乱。
6. Windows 侧 `git push` 偶发连不上 `github.com:443`，改从 WSL 推（token 经临时
   askpass 文件，不进 argv、不进仓库）。
7. `pkill -f <pattern>` 会匹配到自己的 ssh 命令行，把会话杀掉。
8. WSL 重启后 `/tmp/repo` 软链消失，先重建再跑。
