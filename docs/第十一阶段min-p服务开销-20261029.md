# 第十一阶段：`min_p` 在服务路径上多出的 1 ms/步（2026-10-29）

第八、九阶段的 serve 实验反复看到一个现象：请求里带 `min_p=0.1` 时，TPOT 比
`min_p=0` 高约 **1.0–1.3 ms/步**，而这个差值与 min-p 内核本身的耗时（116 µs、
20 µs、25 µs 三种实现）不成比例。本阶段用四个探针把这块开销往下切，目标是回答
一个问题：**这 1 ms 是 min-p 内核的，还是别处的？**

结论先说：**能排除内核执行时间，不能定位到具体算子**。代价与“内核是否真的执行”
绑定，但不随内核时长缩放；段级/算子级括号计时给出的位置与微基准互相矛盾，因此
只能写到“采样段内、机制未定论”，不能声称“min-p 内核慢 1 ms”。

## 1. 问题定义

固定负载：`vllm serve` 同一个进程内跑两个相位，`min_p=0.0`（下称 nop）与
`min_p=0.1`（下称 minp），并发 8、每相位 32 条请求、输出 32 token、temperature 0.8、
每条带 seed。两个相位的唯一差别是请求里的 `min_p`。

第八阶段的读数（upstream 内核）nop 4.87 ms / minp 5.92 ms；第九阶段换成 CUDA 内核
仍是 4.9 → 6.1 ms。内核快了 5 倍，差值几乎不变——这本身就是“不是内核”的第一个信号。

## 2. 方法与四个探针

四个探针都通过 `sitecustomize.py` 的 import 钩子装进 worker 进程（不改 vllm-src），
用环境变量控制：

| 探针 | 文件 | 做了什么 |
| --- | --- | --- |
| 调用级 time | `patches/mrv3_minp_probe.py` | 替换模块全局 `apply_min_p`，CUDA event 记每次调用的 GPU 时长与 host 时间；`CI_PROBE_MODE=time` |
| 调用级 skip | 同上，`CI_PROBE_MODE=skip` | 替换成 `return logits`：请求仍带 `min_p=0.1`、`np.all` 分支仍执行，但**不跑内核** |
| 步级 | `patches/mrv3_minp_step.py` | 懒安装 `Sampler.sample` 包装，CUDA event 包住整步采样，按“本步是否调用过 min-p”分两组 |
| 算子级 | `patches/mrv3_minp_ops.py` | 同时包 `Sampler.sample`、`apply_temperature`、`gumbel_sample`、`apply_top_k_top_p`、`apply_min_p`，每个算子一对 event |
| 微基准 | `scripts/topk_noop_probe.py` | 脱离服务，直接测 `apply_top_k_top_p` 在 `(8,151936)` fp32 上的真实代价 |

探针每 64 次/步写一次 `<OUT>.<pid>.json`，并在 SIGTERM 时 `synchronize` 后强制写
（第一版只挂 `atexit`，被 harness 的 SIGTERM 杀掉时一个文件都没留下）。

## 3. 证据

### 3.1 复现：三种内核，同一个差值

| 内核 | min-p 内核耗时 | nop TPOT | minp TPOT | 差值 |
| --- | --- | --- | --- | --- |
| upstream Triton（第八阶段） | 116–272 µs | 4.87 ms | 5.92–6.18 ms | +1.05–1.3 ms |
| 本项目 Triton 两阶段 | 20–25 µs | 4.9 ms | 6.0 ms | +1.1 ms |
| 本项目 CUDA | 18–25 µs | 4.9 ms | 6.1 ms | +1.2 ms |

内核快 10 倍，差值不动。**差值不是内核的算力/带宽成本。**

### 3.2 skip：不执行内核，差值完全消失

`results/serve-probe-20261028T174532Z-RTyOSt/`（4 场，passed，patched_installs=2、
mismatch=0）。该场的 `apply_min_p` 被换成 `return logits`，其余路径不变：

| 场 | minp TPOT | nop TPOT |
| --- | --- | --- |
| base-00 | 5.92 ms | 4.88 ms |
| base-03 | 6.15 ms | 4.87 ms |
| patched-01（skip） | **4.88 ms** | **4.88 ms** |
| patched-02（skip） | 5.35 ms | 5.33 ms |

结论：**代价与“内核是否被执行”绑定**。`min_p` 参数进入请求、`np.all` 判断、
Python 分支这些固定成本都不是原因（skip 臂这些全都还在）。

### 3.3 内核本身只有 75–83 µs

`serve-probe-20261028T173823Z-ImJO15/` 与 `...174302Z-XDMUrF/` 的 time 探针：
`calls=384, timer_checked=382, gpu_us_mean=78.1–79.3, gpu_us_p50=74.1–74.2,
host_us_mean=34.7–37.0`。步级探针（`serve-probe-step-20261028T174812Z-CFI8mI/`）：

| 组 | steps | GPU 均值 | GPU p50 | host 均值 |
| --- | --- | --- | --- | --- |
| minp 步 | 394 | 1.246–1.306 ms | 1.246–1.248 ms | 1021–1046 µs |
| nop 步 | 372 | 0.379–0.434 ms | 0.198 ms | 917–1005 µs |

采样段多出约 **1.0 ms GPU 时间**，其中 min-p 内核只占 0.083 ms。

### 3.4 算子级括号把差额记在 `apply_top_k_top_p` 区

`results/serve-probe-ops-20261028T175136Z-yRjobe/`（两个 worker 进程一致）：

| 算子 | minp GPU 均值 / p50 | nop GPU 均值 / p50 | host（两相位） |
| --- | --- | --- | --- |
| `Sampler.sample` | 1.32–1.39 / 1.283 ms | 0.371–0.436 / 0.254–0.259 ms | 1.17–1.38 / 1.07–1.16 ms |
| `apply_top_k_top_p` | **1.116–1.174 / 1.089 ms** | **0.222–0.276 / 0.118 ms** | 499–603 / 456–538 µs |
| `gumbel_sample` | 0.080–0.083 / 0.065 ms | 0.0575 / 0.038–0.049 ms | 143–168 / 133–142 µs |
| `apply_temperature` | 0.011 ms | 0.011 ms | 61–73 µs |
| `apply_min_p`（内核） | 0.075 / 0.0748 ms | — | 30–35 µs |

按括号读，差额在 `apply_top_k_top_p`（+0.97 ms）。

### 3.5 微基准反证：这个函数对我们应该是 no-op

`results/minp-topk-noop-20261029T0157Z/probe.txt`，`(8,151936)` fp32：

| case | gpu_us | 是否原样返回 |
| --- | --- | --- |
| `k=None, p=None` | **0.3–3.7** | 是 |
| `k=vocab, p=1.0` | 189.4–198.6 | 是 |
| `k=20` | 611.7–612.9 | 是 |

而 vLLM 的 `SamplingStates` 把 `top_k` 表初始化为 `vocab_size`、`top_p` 表初始化为
`1.0`（`vllm/v1/worker/gpu/sample/states.py:31-35`），请求里没有 `top_k/top_p` 时
`get_top_k_top_p` 返回 `(None, None)`（同文件 :105-112），`apply_top_k_top_p` 在
`p is None and k is None` 时直接 `return logits`（`vllm/v1/sample/ops/topk_topp_sampler.py:449-459`）。
**我们这个负载走的正是 None 分支，真实代价 0.3 µs，不可能是 1.09 ms。**

## 4. 结论

**能排除的**：

1. min-p 内核的执行时间（75–83 µs，且三种实现差 10 倍而总差值不变）；
2. 内核的带宽/算力（同上）；
3. `apply_temperature`、`gumbel_sample`（各 +0.01 / +0.03 ms）；
4. `min_p` 参数进入请求后的固定成本：skip 臂把内核换成 no-op，差值消失；
5. `apply_top_k_top_p` 的真实计算：微基准 0.3 µs。

**不能声称的**：

- 不能说“差值在 `apply_top_k_top_p`”。算子级括号在该函数是 no-op 时仍报 1.09 ms，
  说明括号把“GPU 等 CPU 提交 end event”的空转计入了 elapsed——当 GPU 已经追平
  CPU 时，event 的 elapsed 反映的是主机侧间隔，不是 GPU 工作时长。段级括号
  （`Sampler.sample` 的 minp 1.283 / nop 0.254）同样可能混入这类空转，所以
  “采样段多 1 ms”这个读法也要打折。
- 不能说“min-p 内核慢”。内核自己在括号里是 75 µs，而且 skip 实验直接否掉了它。

**仍然成立的硬事实**：稳态 TPOT 差值 1.0–1.3 ms/步存在，三种内核实现都复现，
skip 掉内核就消失。也就是说：**这 1 ms 由“执行 min-p 内核”这件事触发，但不在
内核的执行时间里**。

最可能的结构性解释（未验证）：`min_p≠0` 会让采样从 fused 路径切换到非 fused
路径（`apply_sampling_params` 做 fp32 全词表拷贝 → temperature → min-p →
top-k/top-p → gumbel），每步多出若干次 kernel launch 和一次 4.9 MB 的 D2D 拷贝；
本机单次 launch 开销约几十 µs，几十次才能凑到 1 ms，因此需要时间线证据而不是
括号计时。

## 5. 限制

- 单机单卡（RTX 5060 8 GB）、WSL2、Qwen3-0.6B；不能外推到其他 GPU/驱动。
- 探针本身有开销（每步 2–4 个 event + Python 包装），只用于相对比较，不用于绝对值。
- `/tmp` 在 WSL distro 停机后清空，step 探针的首批 json 已因此丢失；本阶段引用的
  数字来自运行期间读到的输出，结果目录里保留了 `summary.json` 与 session 日志。
- ops 探针的两个 worker json 也在 `/tmp`，未落盘到 `results/`（见 §7 说明）。

## 6. 下一步

1. 用 Nsight Systems 抓一个 decode 步（`--capture-range` 包住一次采样），看时间线上
   到底多了哪些 kernel、gap 在哪——这是唯一能终结“括号计时”争议的证据。
2. 对照实验：保留非 fused 路径但把 `apply_min_p` 换成 no-op（skip）已做；再做
   “保留内核、把结果丢弃”不改变路径的版本，区分“内核执行”与“路径切换”。
3. 若确认是路径切换成本，则 min-p 的服务级收益本来就不该期望——它换掉的是
   116 µs 的 kernel，而路径本身要 1 ms。这一点应写进面试叙述。
