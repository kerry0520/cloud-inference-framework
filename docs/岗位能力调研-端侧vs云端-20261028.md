# 岗位能力调研：端侧 vs 云端推理框架（2026-10-28）

> 目的：回答“端侧推理框架 / 云端推理框架这两类项目，岗位到底要求你会什么”，并对照本项目现有证据，
> 判断哪些能直接讲、哪些只是半张牌、哪些必须补。
> 样本来自 2026 年 9–10 月的公开招聘页与面经，**不是随机抽样，也不能当市场统计**；所有薪资均为发布方标注或作者估算。

## 0. 摘要

1. **两族岗位的约束不同，不是“同一个框架跑在不同机器上”**。端侧的硬约束是**内存、带宽、功耗、芯片碎片化**，
   核心动作是“把模型变小、把算子落到别人的 NPU 上、把内存池住”；云端的硬约束是**单位 token 成本、SLO、显存容量**，
   核心动作是“把 batch 做大、把 KV 管好、把并行切对、把调度做满”。
2. **交集是一套 Transformer 推理常识**：prefill 算力密集 / decode 带宽密集、KV cache 空间计算、PagedAttention、
   continuous batching、prefix cache、量化、算子融合、CUDA graph、profiling。两边的面试都从这套常识出发。
3. **云端岗对本项目最友好**：decode 逐层归因、375 GB/s 权重字节模型、min-p 两版内核、真实 `vllm serve` 接入、
   ABBA/安慰剂/负结果、两个 open PR——这些正好对应云端面试的“测量 + 算子 + 框架”三块。
4. **端侧岗另有一套门槛**：C++/Linux/CMake、芯片 SDK（QNN/SNPE/CANN）、端侧 runtime（MNN/NCNN/TFLite/llama.cpp）、
   量化落地与精度回归、板端 profiling。本项目几乎不覆盖，**不能靠改简历讲成端侧经历**，需要另做一个小项目。
5. **面试题高度集中**：KV cache 计算、PagedAttention/prefix cache、continuous batching、prefill/decode 瓶颈、量化、
   CUDA graph、算子融合、TP/EP/PD。本项目深覆盖前六项，**缺 TP/EP 与 PD 分离**——这是最值得补的两块“纸面能力”。

## 2. 一句话画像

- **端侧推理框架**：在别人的芯片上，把模型塞进去、跑得动、耗电可接受。你交付的是一个**能在板子上复现的 runtime/工具链**，
  而不是一篇 kernel 论文。
- **云端推理框架**：在自己的集群上，把每个 token 的成本压下去、把 SLO 守住。你交付的是**吞吐/延迟/成本的联合优化**，
  以及“为什么这个改动值得进主干”的证据。

一个常被忽略的细节：大疆的端侧 JD 里同时写了“推理服务治理（动态批处理/多模型调度/显存算力复用）”，
说明**端云边界在融合**——端侧也要懂 serving，云端也要懂芯片。但两边的**默认工具箱**仍然不同（见 §5）。

## 3. 端侧推理框架：岗位画像

### 3.1 典型职责（四类，按项目阶段分）

| 类别 | 具体工作 | 对应 JD |
|---|---|---|
| A. 交板部署 | 把 PyTorch/ONNX 模型转到目标 SoC（Qualcomm/MTK/地平线/自研 NPU），跑通精度与性能基线；处理不支持的算子、动态 shape、内存对齐 | 商汤、大疆 |
| B. 变轻变快 | 量化（PTQ/QAT、GPTQ/AWQ、GGUF Q4_K_M）、剪枝、蒸馏、稀疏化；KV cache 量化/压缩；投机解码、early exit | 大疆、商汤、牛客全景 |
| C. Runtime/算子/工具链 | 写自定义算子（GPU/NPU）、算子融合、图优化、内存池/零拷贝、多后端适配；性能剖析工具（msprof/Nsight/Perfetto） | 大疆、商汤 |
| D. 服务与协同 | 端侧多模型调度、动态批处理、显存/算力复用；端云协同、请求级缓存、隐私 | 大疆 |

注意 B/C 是“项目能力”的核心：**面试官不会问你“知不知道量化”，而是问“这个模型在 8 GB 手机上，4k 上下文，Q4 能不能放下，放不下你先砍哪一刀”**。

### 3.2 硬性要求（几乎每份 JD 都有）

- **语言**：C/C++ 是硬门槛（商汤：C/C++/Python/Git/CMake/Makefile；大疆：C++/CUDA/Python）。Python 只用于训练/脚本。
- **平台**：Linux、Android/Linux 端上部署；交叉编译、CMake、adb、NDK。
- **模型格式**：PyTorch → ONNX → 目标 runtime；熟悉至少一个端侧框架：MNN / NCNN / TFLite / llama.cpp / TensorRT(-LLM) / SNPE / QNN。
- **量化**：INT8/INT4/FP8 的原理与落地，PTQ vs QAT，per-channel/group-wise，outlier 处理，**精度回归**。
- **体系结构**：CPU/GPU/NPU/DSP 的存储层次、带宽、算子支持差异；会算内存与带宽账。
- **性能剖析**：能定位“是算得慢还是搬得慢”，会看 timeline、算子耗时、内存峰值、功耗/温控。
- **工程习惯**：Git、CMake、单元测试、可复现的 benchmark；商汤明确写“测试工具”。

### 3.3 加分项（简历上的差异化）

- 手机/平板/车机 **NPU 量产部署**经验（大疆、商汤都点名）。
- 自定义 GPU/NPU 算子；TVM/Triton/MLIR 二次开发（大疆）。
- PagedAttention / FlashAttention / Speculative Decoding / KV-Cache 的实操（大疆）。
- 顶会一作（MLSys/OSDI/ASPLOS/SC/CVPR/NeurIPS）或框架核心贡献者（大疆）。
- 端侧多模态：视觉 token 压缩、VLM 视觉塔与解码器分开量化（大疆笔试解析、牛客全景）。

### 3.4 面试/笔试考点（按出现频率）

| 主题 | 典型问法 | 要答到什么程度 |
|---|---|---|
| 端侧瓶颈 | “手机上跑 7B，decode 为什么慢？先优化什么？” | 先分 prefill 算力 / decode 带宽；给出权重字节 + KV 字节的账；主线“少读字节 + 少读次数” |
| KV cache | “Qwen3-0.6B，4k 上下文，KV 多大？8 GB 手机能开几个并发？” | 会推公式：`2 × layers × kv_heads × head_dim × seq × batch × dtype`；会算 GQA 的收益 |
| 量化 | “Q4_K_M 和 AWQ 有什么区别？精度掉了怎么定位？” | weight-only vs weight+act；group size；outlier；用 perplexity + 业务集回归；分层敏感度 |
| 算子不支持 | “NPU 不支持 RoPE，你怎么办？” | 图改写拆算子 / 回退 CPU / 自定义算子 / 换等价实现；说清拷贝与同步代价 |
| 内存 | “模型加载后 RSS 超了，怎么查？” | 权重 + KV + 激活 + 碎片 + 框架开销；内存池、零拷贝、mmap、按需加载 |
| 多模态 | “图像 token 太多，怎么省？” | resampler/Q-Former、token merge、按需分辨率、视觉塔单独量化 |
| 端云协同 | “什么时候把请求放端上，什么时候上云？” | 延迟/隐私/成本/网络抖动；缓存与降级策略 |
| 工程 | “怎么证明你的优化没改坏精度？” | 固定种子 + 逐字节/逐 token 比对 + 业务评测集 + 分层误差 |

## 4. 云端推理框架：岗位画像

### 4.1 典型职责（六块）

| 块 | 具体工作 | 对应 JD/面经 |
|---|---|---|
| 框架二次开发 | 基于 vLLM/SGLang 做适配、裁剪、特性开发；PD 分离、KV cache store、prefix cache | 魔形智能、昕原、讯飞 |
| 调度 | continuous batching、chunked prefill、请求排队/抢占、公平性、SLO 感知 | 魔形智能、讯飞 |
| KV 管理 | PagedAttention、block size、显存碎片、prefix 复用、KV 量化/卸载/外部存储 | 寒武纪、讯飞、HF3FS 类工作 |
| 并行 | TP/PP/EP/CP/SP、PD 分离、多卡通信、MoE 负载均衡 | 寒武纪、魔形智能 |
| 算子 | CUDA/Triton 自定义算子、融合、采样、attention、通信融合 | 魔形智能、昆仑芯 |
| 服务治理 | 高并发低延迟架构、动态资源分配、负载均衡、容灾、自动扩缩容、GPU 池化 | 魔形智能、讯飞 |

### 4.2 硬性要求

- **语言**：Python 熟练 + C++/CUDA 能改底层；昆仑芯写“Python/C/C++、容器、PyTorch、Megatron/vLLM、GPU 架构”。
- **框架**：vLLM 或 SGLang 至少一个**读过源码/改过**；TensorRT-LLM/DeepSpeed 是加分。
- **推理常识**：prefill compute-bound / decode memory-bound、KV cache 计算、PagedAttention、continuous batching、prefix cache。
- **性能**：Nsight Systems/Compute、nsys/ncu、msProf；能读 timeline、算 roofline、做 A/B。
- **分布式**：TP/PP/EP 的原理与通信原语（all-reduce/all-gather/all-to-all）；PD 分离的动机。
- **工程**：Linux、Docker/K8s、Git、CI；能把实验做成可复现的 benchmark。

### 4.3 加分项

- 框架 core contributor / 已合并 PR（比“用过”强一个量级）。
- 国产芯片适配（昇腾/CANN、ROCm）、vllm-ascend 类中间层经验。
- PD 分离、KV cache 外部存储（3FS/LMCache/Mooncake）、MoE 负载均衡。
- 量化（FP8/INT8/KV quant）与质量评估闭环。
- 高并发线上服务：容量规划、压测、故障演练。

### 4.4 面试考点（寒武纪 + 讯飞两份面经的并集）

| # | 问题 | 答题骨架 |
|---|---|---|
| 1 | 为什么做算子融合？ | 减少中间张量写回/读取（decode 是带宽瓶颈）+ 减少 launch；反例：寄存器压力/occupancy 下降 |
| 2 | CUDA graph 原理、作用、场景？ | 捕获 kernel 序列与依赖，replay 降 launch 开销；要求静态 shape/地址；适合 decode；vLLM 用 piecewise + batch bucket；不适用动态控制流 |
| 3 | vLLM 整体架构与请求流转？ | API server → engine core（scheduler + KV manager）→ worker/executor → model runner → sampler；V1 以 request 为中心、统一 prefill/decode 调度 |
| 4 | KV cache 空间怎么算？ | `2 × L × H_kv × D × seq × batch × bytes`；GQA 按 `H_kv/H_q` 缩；block 向上取整；预留 waterline |
| 5 | prefix cache 是什么？ | 按 block hash 复用已算 KV；命中省 prefill；要处理驱逐与一致性；对多轮/system prompt 收益大 |
| 6 | vLLM V0 vs V1？ | V0 sequence-group 调度、legacy；V1 request 级调度、统一 prefill/decode、prefix caching/async 更自然；答差异与动机即可，不必背实现 |
| 7 | TP 下各模块怎么汇总？ | column-parallel 后 all-gather（或保持切分）→ row-parallel 后 all-reduce；norm/embedding 复制；logits vocab-parallel + 采样前 gather |
| 8 | 3D 并行 & EP & CP & SP？ | TP 切层内、PP 切层间（气泡）、DP 复制（梯度 all-reduce）；EP 切专家（all-to-all）；CP 切序列（ring attention）；SP 在 TP 区内切序列降激活 |
| 9 | 量化类型/原理/作用？ | weight-only（GPTQ/AWQ/GGUF）、weight+act（SmoothQuant/FP8）、KV quant；PTQ vs QAT；per-tensor/channel/group；outlier；精度-吞吐权衡 |
| 10 | 原生 vs 异构（昇腾）？ | CUDA 生态成熟 vs CANN 算子覆盖/显存调度差异；中间层（vllm-ascend）抹平；回退与性能 gap；工具 msProf |
| 11 | 弹性扩缩容 / GPU 池化？ | MIG（硬隔离）、MPS（多进程共享）、时间切片；队列深度比 QPS 更能反映过载；冷启动（加载/上下文/图捕获）是最大敌人；HAMi-core 细粒度配额 |
| 12 | vLLM vs SGLang？ | PagedAttention + continuous batching vs RadixAttention（前缀树复用）；调度粒度/缓存结构不同；都受 KV 显存约束 |
| 13 | 降低推理成本的手段？ | 量化、蒸馏/剪枝、KV 压缩、prefix 复用、continuous batching、投机解码、PD 分离、更好内核、容量调度 |
| 14 | 是否了解 PTX？ | PTX 是 CUDA 的虚拟 ISA；内联汇编/编译产物；何时需要看（寄存器/指令选择/occupancy）；不必装精通 |
| 15 | C++ 函数模板 / 内存泄漏？ | 模板实例化与 header 实现；RAII、智能指针、move、避免循环引用；CUDA 侧 cudaMalloc/Free 配对、stream 生命周期 |
| 16 | torch.compile / CUDA graph 关系？ | compile 做图捕获与算子融合，graph 做 launch 降本；两者可叠加，但动态 shape 是共同敌人 |

## 5. 能力矩阵：端侧 vs 云端 vs 本项目

图例：● 能直接讲并有证据；◐ 懂概念/做过局部，但缺完整闭环；○ 基本空白。

| 能力维度 | 端侧要求 | 云端要求 | 本项目现状 | 证据/缺口 |
|---|---|---|---|---|
| C/C++ 工程 | 硬门槛（Linux/CMake/内存/多线程） | 中高（框架/算子） | ◐ | 有 `cpp_extension` 包装与 CUDA kernel；缺大型 C++ 模块、RAII/并发/调试实战 |
| Python | 中 | 高 | ● | vLLM 脚本、profiling、数据分析 |
| Transformer/LLM 结构 | 高 | 高 | ● | Qwen3-0.6B 逐层拆解、MHA/GQA 可讲 |
| KV cache 计算与管理 | 高（容量/带宽） | 高（Paged/prefix/PD） | ◐ | 会算空间、HF3FS 做过 KV 存储层；未改 vLLM block manager |
| 量化 | 高（PTQ/QAT/GGUF/AWQ） | 高（FP8/INT8/KV） | ◐ | 只到 FP8 配置观察（−25.9% 含精度变化），**无质量评估** |
| 算子开发 | 高（NPU/GPU 自定义） | 高（CUDA/Triton） | ● | min-p Triton + CUDA，逐字节验收，局部/端到端分离 |
| 图优化/编译器 | 高（fusion/layout/量化图） | 中高（compile/MLIR） | ○ | 只用过 CUDA graph，没有图改写/MLIR/TVM |
| 调度/continuous batching | 中 | 高（核心） | ◐ | 读过 scheduler；serve 实验固定并发 8，未改调度 |
| 分布式并行 | 低 | 高（TP/PP/EP/CP/SP/PD） | ○ | 单卡单模型；这是最大硬缺口 |
| 服务治理/容量 | 低 | 高（SLO/池化/扩缩容） | ○ | 只做单机 serve 指标，无队列/过载/冷启动 |
| 性能工具 | 高（msprof/Perfetto） | 高（nsys/ncu） | ◐ | torch profiler/nsys 用过；无 NCU 指令级、无 msProf |
| 异构/国产芯片 | 高（NPU/DSP） | 中高（昇腾/ROCm） | ○ | 无 |
| 开源/论文 | 加分 | 加分 | ● | PR #58907 测量、#62393/#62693 open；无已合并 |
| 测量方法论 | 中 | 高 | ● | ABBA、bootstrap、安慰剂相位、噪声地板、负结果 |

**读法**：本项目在“云端”列有 5 个 ●、3 个 ◐；在“端侧”列只有 2 个 ●。所以**主投云端，端侧作为第二志愿**，
不要用同一份简历硬投两边。

## 6. 对本项目的映射

### 6.1 已经能打的点（有证据，可直接进简历/面试）

1. **decode 逐层归因**：385 kernel/步、一步 3,792 µs、GEMM 83.8%、lm_head 20.4% 且在 CUDA 图外。
   这对应云端面试第 3/13 题，也对应端侧的“先定位再优化”。
2. **带宽模型**：375 GB/s 权重字节模型、留一法 ≤12.8%；能解释“为什么 batch=1 必然带宽受限、为什么 batch 8 是边界”。
   这是端侧/云端共用的第一性原理。
3. **算子优化闭环**：Triton 两阶段归约 4.2–9.7×；CUDA 版 96 case 逐字节一致，局部 6–12×，与 Triton 同量级但没有更快。
   **“没有更快”本身就是可信度**——面试官会追问“那你的价值在哪”，答案是“上限判断 + 验收方法 + 接入证据”。
4. **真实调用路径**：`sitecustomize` 注入、patched 4 次安装 / base 0 次、192 次逐字节 logits 比对、255/256 token 一致。
   这对应“你改的东西真的在跑吗”这类追问。
5. **端到端测量方法论**：ABBA、bootstrap、安慰剂相位测出 ±5–10% 噪声地板，因此不宣称提速；复跑 −1.00% [−1.21,−0.82]。
   这是云端岗最值钱的一块：**能区分“真差异”和“测量噪声”**。
6. **CUDA graph 归因**：28×13 固定序列断言、graph_node_id、lm_head 在图外。
   对应第 2/16 题。
7. **开源协作**：PR #58907 的测量被采纳；#62393/#62693 的设计-实现-验证-回复全流程。
   对应“框架 core contributor”加分项，虽然还没 merged。

### 6.2 只能算“半张牌”的点（要主动说边界）

- **FP8**：只观察了配置层的 −25.9%，没有做质量评估，不能讲成“我做了量化”。
- **continuous batching / prefix cache**：读过、用过（serve 默认开），但没改过调度器；被追问“你怎么验证命中率”会露馅。
- **HF3FS**：是 KV **存储层**的容量/淘汰，不是 KV **显存管理**；讲的时候要区分，否则会被认为在蹭 PagedAttention。
- **CUDA**：写的是“两阶段按列分块 + uint4”，不是“精通 CUDA”；NCU/occupancy/PTX 还没碰。
- **min-p 的 1.2 ms 路径开销**：已观测、未定位；这其实是个很好的“未解问题”素材，但要诚实标注。

### 6.3 明显缺口（按面试杀伤力排序）

1. **多卡/分布式**：TP/PP/EP/PD 只停留在八股，没有实验。云端岗几乎必问。
2. **调度器改动**：没碰过 vLLM scheduler / KV block manager；continuous batching 的“所以然”讲不深。
3. **端侧整条链路**：没有板子、没有 NPU SDK、没有端侧 runtime；端侧岗的第一轮技术面就会问穿。
4. **C++ 工程能力**：CUDA kernel 是“单文件 + cpp_extension”，不是“能维护一个 runtime 模块”。
5. **质量评估**：量化/精度回归没有闭环；云端做 FP8、端侧做 Q4 都需要。
6. **图编译**：TVM/MLIR/torch.compile 的图改写没做过；大疆的加分项、云端的中高要求。

### 6.4 两版简历叙事（同一项目，两种讲法）

**云端版（主投）**

> 在 vLLM 0.31 的真实 MRV2 采样路径上做小批量 decode 性能分析与内核替换：用 385 kernel/步的 trace 归因出
> GEMM 83.8%、lm_head 20.4%（CUDA 图外）与 min-p 算子 1.18% 的收益上限；实现 Triton/CUDA 两版两阶段归约内核，
> 局部 4–10×，逐字节验收 96 个形状；用 ABBA 配对 + 安慰剂相位量化 ±5–10% 噪声地板，测得整请求 −1.10%
> （95% CI [−1.37,−0.85]），明确不宣称端到端提速；跨 RTX 5060/5090 复核发现上游 66–71 µs 为发射受限而非带宽受限。

要点：**上限判断 → 内核 → 接入 → 端到端 → 负结果**。这条线对云端面试官是完整的。

**端侧版（第二志愿，需先补项目）**

> 以 Qwen3-0.6B 为对象建立端侧内存/带宽账：fp16 权重 1.2 GB、KV 112 KiB/token（GQA 8 头），
> 解释 batch=1 decode 的带宽下界；用 llama.cpp Q4_K_M 把权重压到 ~0.4 GB，在 x86/ARM 上测 TTFT/TPOT/峰值内存，
> 并用固定种子 + 业务集做质量回归；对比 CPU/GPU 后端的算子覆盖与回退路径。

要点：**这条目前是“计划”，不是“已完成”**。没有真做完之前，不能写进简历。

## 10. 结论

- 若目标是**推理框架/AI Infra 实习**：主投云端（vLLM/SGLang 生态、云厂商、模型公司），本项目已经是“能打”的样本；
  用 P0 把叙事和八股补齐，命中率会明显高于现在。
- 若目标是**端侧**：需要接受“另起一个小项目”的成本；本项目只能证明你懂 decode/带宽/算子，不能证明你懂板子和 NPU。
- 两条路都不要求你现在就会 TP/EP/PD，但**面试会问**；P0 的设计题是性价比最高的补法。
- 最值得强调的差异化不是“我优化了 1%”，而是：**我能先算出上限，再决定要不要优化；我能证明改动真的在跑；我能区分真差异和噪声。**
  这三点在端侧和云端都稀缺。
