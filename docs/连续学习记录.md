# 连续学习记录

## 2026-10-17：先分清一张时间线中的三种时间

当前主线：请求到达 → 引擎安排输入 → GPU 执行模型 → 采样生成 token → 处理结果 → 下一步。

CPU 准备输入与 GPU 执行模型可以同时发生。CPU 忙碌 2ms、GPU 忙碌 5ms，不代表这一步就是 7ms；还要看依赖与重叠。如果 CPU 在 GPU 完成之前已准备好下一步，单独减少这部分 CPU 时间可能不会加速输出。

初期区分三个观察对象：

1. 请求完成时间：从提交一批请求到拿到结果，包含 prefill、decode、排队和引擎处理。不能把它直接当作 Decode 时间。
2. 请求级平均出字间隔：如果引擎记录了同一时间域的首、末 token 时间，可以用二者之差除以后续 token 数。它是平均值，不代表每个 token 的延迟分布。
3. 时间线中的一次 GPU 工作：可能是一个内核，也可能是一个 CUDA Graph 的重放。图中看见一次提交，不代表模型只执行一个算子。

第一组实验使用固定数量输入 ID 和固定输出长度，以降低分词、自然提前停止的干扰。它是合成性能负载，不是聊天质量或模型准确率评估。greedy 重复生成一致也不能代替全 logits 数值验证；以后修改哪一层，就为那一层设计正确性验收。

初始化可能包括加载模型、编译、预热和图捕获，应与暖运行分开记录。分析工具本身也有开销，因此性能运行与采样时间线分别保存。

## 同日补充：为什么能做矩阵乘，推理引擎仍可能启动失败

PyTorch 的矩阵乘检查使用已经编译好的实现。推理引擎还可能在启动时编译特定采样内核、预热不同参数、捕获 CUDA Graph。因此基础 GPU 计算通过，只能证明一部分执行链可用。

本轮实际遇到：FlashInfer 在启动预热中需要编译采样模块。最初环境没有提供编译工具路径；补齐后，又发现自动安装的编译器为 13.4、头文件为 13.0。需要固定一致的工具组件，而不是修改推理算法。虽然正式测量使用 greedy，初始化仍可能预热随机采样路径，所以这项依赖也不能略过。

另一个区别是 pinned memory：它是方便 GPU 进行传输或访问的一类主机内存。固定 vLLM 版本在符合内核要求的 WSL2 上提供显式启用开关。本机小规模复制检查通过，不代表所有规模和路径都已验证；它是环境配置，不是本项目发明的优化。

## 第一份 Decode 时间线：为什么先不改 CPU

本轮基线与稳定/收缩批次 trace 已取得。正式运行中各请求平均出字间隔约4～5ms；带 profiler 的短窗口里 GPU kernel 活动较连续，矩阵乘占较多累计 kernel 时间。这还不能证明带宽瓶颈，但能帮助决定下一步先看什么。

CPU 需要准备位置、请求映射和下一步输入；模型本身仍要在 GPU 上计算。即使某段 CPU 工作每步重复，也要先确认减少它会让后续执行提前。看到一次同步同样不能直接删除，因为它可能在保护尚未传输完成的输出。

接下来从一条线性层解释矩阵的 M/N/K，查它在真实 Decode 中对应几个 token、多少输入特征和多少输出特征，再对照实际 kernel。kernel 名字包含旧架构标签并不自动意味着选错实现，需看适用形状、派发逻辑与对照证据。

工程摘要与适用范围见第一阶段结果页。材料已整理，尚未验证学习者理解。

## 第二阶段：min-p 为什么不需要先算 softmax

min-p 保留概率至少为最高概率的某个比例的 token。设比例为p，条件为 `prob_i >= p * prob_max`。softmax 的共同分母可以抵消，取对数后条件变成 `logit_i >= max_logit + log(p)`。因此过滤只需求行最大值、算阈值，再把低于阈值的分数改成负无穷。

本轮没有改变过滤条件。原实现让一个线程块逐段处理很长的词表；候选先让多个块各算一段最大值，再归约这些最大值并过滤。总读取量没有凭空消失，启动次数还从一次变为两次；只有增加的并行收益覆盖这些额外成本，优化才值得保留。

这解释了实际结果：15万词表的小批量局部计时改善明显，小词表却可能变慢，所以需要有范围的派发。整请求还要执行模型的大量矩阵乘，min-p 只是其中一小步，局部数倍改善也只带来很小的整体变化。

主线还确认：此模型 Q 的总宽度为16头×128=2048，而 hidden_size 为1024；QKV合并输出4096，O投影再把2048变回1024。不能只凭 hidden_size 推断所有投影尺寸。第一层真实观察到 prefill M=64、decode M=2；它们是同时处理的位置数，不是模型层数。

## 第三阶段：M=2 时为什么时间正比于权重字节

解码一步只处理很少的位置（本机 batch2 时 M=2），但每一层仍要把完整的权重读一遍。以 gate_up 为例：权重 6144×1024 个半精度数，约 12.6 MB，而输出只有 2×6144。每个权重参与两次乘加，也就是每 2 字节权重只换来约 2 次浮点运算。GPU 的算力相对带宽通常高出一两个数量级，这种“强度”很低的计算就会先被读权重的时间卡住，而不是被乘法本身卡住。

判断是否真的如此，不能只看内核名，要看三件事是否同时成立：时间与字节数成正比；同一形状换个实现时间不变；把权重换成更小的字节数时间会下降。本轮前两条有数据：四个层内 GEMM 与 lm_head 的“微秒/权重字节”落在很窄的范围，28 层之间抖动只有百分之一二；standalone 用同族 cutlass 内核重测，时间同样跟字节走，只是整段慢约 17%~25%。

第三条提醒了测量的边界：不同进程、不同时刻的 GPU 时钟状态可能不同，绝对带宽数字不能跨上下文直接比较。我一度把带 profiler 的 trace 算出的 402 GB/s 当成“已达硬件上限”，但同一台机器上另测的流带宽只有约 346 GB/s；两个数字不可能同时是上限，说明差异来自测量上下文而不是“没有余量”。能站住的结论因此收窄为：时间正比于字节、GEMM 占单步 83.8%、lm_head 单独占 20.4% 且在图外；不能据此宣布还有多少百分比可挖。

另一个容易忽略的点：CUDA 图重放的内核没有可用的 launch 关联，逐层归属只能靠固定序列和 graph node id。序列一旦因版本或 batch 改变，断言就应该失败，而不是给出一张看起来合理但错位的表。

## 第四阶段：一个局部内核通过之后，还差什么才算“接入真实路径”

局部计时通过只说明这个内核在孤立环境下更快，离“框架真的在用、并且用对了”还隔着四件事，缺一件都不能算接入：

1. **数值契约**：过滤后的 logits 要逐字节一致，而不是“差不多”。min-p 的阈值比较是硬门限（`logit >= max + log(p)`），差一个最低位就可能让某个 token 从“保留”翻成“−inf”，后面采样直接换词。所以对比用 `torch.equal` 看整块张量，不看最大误差。
2. **派发可见**：必须能证明这次调用走的是新内核，而不是悄悄回退了。做法是给两个内核名各套一个计数器，记录每次真实启动落在哪边；光看“结果一样”无法区分“新路径正确”和“新路径根本没被调用”。
3. **边界可预测**：启用条件是行数 1–8、词表 ≥ 32000、行内连续、dtype 在白名单里，两端都含。闭区间的端点最容易被差一错误破坏，所以 `rows=8/vocab=32000` 和 `rows=1/32000` 要单独测，`31999`、`rows=9`、空 batch 也要测——不是测它们更快，而是测它们确实回退且结果不变。
4. **回退不退化**：不满足条件时走上游原内核，代价应当只有一次谓词判断；计时确认回退分支 1.01× 左右，没有偷偷多扫一遍。

为什么用补丁而不是直接改安装的包：补丁可审查（147 行纯增量、0 删除）、可回滚（`git checkout --` 一条命令）、与 pinned 上游版本绑定；验证在临时副本上做，真实引擎用 worker extension 从路径加载补丁文件，共享的 `vllm-src/` 和 `.venv` 一个字节都没动。这样“实验证明有效”和“运行环境被改坏”就不会绑在一起。

暂存部分最大值用 float32 也值得记一笔：被比较的 logits 可能是 fp16/bf16，若部分最大值也存低精度，阈值附近的舍入会把边界元素推错侧；归约只有几十个 float，额外字节可忽略。

最后是老实的话：局部 4–10× 是词表很大、batch 很小时的并行收益；在整请求尺度上它只占一小段（第三阶段里采样器合计约 22.6 µs / 3792 µs），所以前面整请求只测到约 1% 的变化。局部数字不能拿去当端到端提速的承诺，这也是为什么派发窗口取得保守、`vocab` 小或 batch 大时宁可回退。

## 第五阶段：为什么 1% 的差异必须配对测量，而不是"多跑几次取平均"

这轮要回答"局部 8.9×、整请求到底几 %"。第一版脚本只跑两轮、比整段 wall，结果 batch2 落在 −0.13% 和 −1.06% 之间，看起来像噪声；而 decode 间隔给出的却是稳定的 −1% 左右。同一份数据两个指标打架，先要问哪个指标在量什么。

`wall` 包含客户端组请求、调度、prefill 和输出处理，一次 60 多 token 的请求要几百毫秒，min-p 在内核里省下的几十微秒被淹没在调度抖动里。`decode` 间隔只数首末 token 的时间戳，prefill 和客户端开销被排除，才是 min-p 真正作用的那一段。**指标选错，结论会从"稳定 −1%"变成"有时正有时负"。**

第二个问题是"多跑几次取平均"本身不够。两台臂交替（A/B/B/A）能抵消随时间的漂移（比如时钟慢慢降频、缓存状态变化），但抵消不等于能量化不确定性。做法是把每一轮的两次调用先取均值，得到 24 个**轮级配对差**，再对这 24 个数做 bootstrap 重采样——按轮重采样而不是按请求，因为同一轮里的请求共享同一次调度状态，不独立；把它们当独立样本会把区间算窄。

第三个教训更根本：不能拿采样出来的 token id 当数值等价的判据。第一版断言"两臂输出相同"，在 batch4 立刻失败；查 timing 记录发现**同一个臂的两次相同调用也可能差一个 token**。也就是说这台机器上的采样链路本身不是逐位可复现的（并发 kernel、浮点归约顺序、随机数状态的细节都可能贡献），token id 相同只能当旁证。真正的数值判据是过滤后的 logits 逐字节一致——那是补丁的直接输出，早于采样。

最后是测量方式会反过来改变结论：第一版每次都重新 import 模块，结果 wall 出现 +0.10%/+0.71% 的正值，而 decode 稳定为负。import 和 GC 的开销落在被测量区间里，就足以盖过 1% 的效应。改成两臂常驻、只翻转一个标志之后，wall 与 decode 才同向。**当两个指标矛盾时，先怀疑测量装置，再怀疑被测对象。**

带宽模型那边也留了一个未解的矛盾：standalone 测到的流带宽上限是 322–347 GB/s，而引擎内隐含 375 GB/s。两个数不可能同时是"硬件上限"，说明至少有一个测量上下文不同（时钟、并发、L2 状态）。能站住的只是"时间正比于字节、留一法残差 ≤12.8%"，至于为什么引擎内更高，需要锁频或更细的计数器才能回答，这一轮没有权限也没有可靠采样，就不写进结论。

## 第六阶段：复现不是把数字再跑一遍，而是检验"为什么会是这个数字"

拿到 −1.10% 之后，下一步不是再测更多轮把它变准，而是问：这个数字应该随什么变化？模型给了一个可被推翻的预测——如果省下的是 min-p 内核里固定的约 57 µs，那么百分比就该等于 `57 µs ÷ decode 步`；batch 越大、decode 步越长，百分比越小。于是换一个引擎会话、把 batch 扩到 8 重跑：实测 −1.23 / −1.00 / −0.81 / −0.91%，两轮平均节省 62.2 与 55.9 µs，与 profiler 推得的 56.9 µs 同量级。**预测先于数据，数据再看是否落在预测附近**，这比"再跑一次还是 −1%"更能说明机制。

这里有两个容易混的层次：

1. **绝对时间不可跨会话比**：run A 的 decode 步 4.49–5.13 ms，run B 是 4.29–4.95 ms，相差约 4%。时钟状态、机器温度、后台进程都会变，所以只能在同一会话内做配对比较；跨会话只能比"配对差"和"趋势"。
2. **百分比与绝对节省是不同的量**：batch4 的 −0.81% 看起来比 batch2 的 −1.00% 弱，但绝对节省反而更大（69.2 vs 45.7 µs）；是分母变大了。报告百分比时必须同时给出分母，否则读者无法判断是优化变弱还是任务变重。

另外，wall 在 run B 的 batch2 区间包含了 0（[−1.33, +0.11]），而 decode 区间排除 0。这不是"结论不稳"，而是两个指标的噪声底不同：wall 里混入了调度与客户端开销，1% 的效应在它下面时隐时现。选择指标的依据应当是"这个效应作用在哪一段"，而不是"哪个指标更好看"。区间含 0 时就如实写含 0，不用另一个指标去补它的缺口。

## 第七阶段：动手之前先搜同方向的工作，测完再拆收益来源

准备向上游发数据时，第一件事不是写 issue，而是搜有没有人已经做过。结果是 PR #58907 已经开着三周，做的是“去掉逐 tile 的跨 lane 归约”，方向与我们的两行旋钮重叠。这一步改变的不是技术结论，而是**策略**：重复 issue 会被要求自行关闭，正确动作是贴数据到既有 PR。

由此得到两个更一般的教训：

1. **“我们的做法更快”必须能拆成可归因的部分**。单独扫 `BLOCK_SIZE`（内核体完全不动）得到 66.5 → 39.0 → 24.8 → 18.7 → 15.9 µs，说明收益几乎全部来自“加宽 tile、把跨 lane 归约次数从 149 次摊到 10 次”，而不是 `num_warps`，也不是 #58907 改的那处。没有这张表，“旋钮比 PR 快”只是两个黑盒的比较，无法判断谁该采纳谁。
2. **同机同协议三方对比才有意义**。把 upstream / knob / #58907 放进同一个进程、同一张量，先验证输出逐字节一致再计时，并且同时报“排队吞吐”和“单次启动中位”两种口径——因为小内核下它们能差 20% 以上。跨机器、跨 dtype 的数字只能用来对齐量级，不能用来分胜负。

还有一个具体的技术点：`for name, fn in [...]` 里用闭包捕获循环变量，会把三个变体都指向最后一个（第一次跑出来三个数字一模一样，正是这个 bug）。这种错误不会报错，只会让结论看起来“三个实现性能相同”。凡是“多个实现、一个循环”的基准，循环变量的绑定方式必须显式写出来。

## 第八阶段：把“时间正比于字节”从相关关系变成干预实验

第五阶段用留一法拟合出“单步时间 ≈ 权重字节 / 375 GB/s”，最大残差 12.8%。但残差小只说明**数据与模型不矛盾**，不说明模型是真的：也可能是别的机制恰好产生了同样的线性关系。要区分，就要主动改一个输入，看输出是否按模型动。

干预是“把权重字节减半”（fp16 → fp8 W8A8），模型预测整步 −40%（层内 GEMM 3.18 → 1.59 ms，尾部 0.81 ms 不变）。实测只有 −26%。拆开 trace 后差额是可指认的：

- 层内 GEMM：3,220.9 → 1,506.3 µs = **0.468×**。预测 0.5×，落在附近——字节模型在这一项上被干预证实。
- `lm_head` 没被量化：884.7 µs，占整步 20%，完全不缩。
- fp8 每步多 112 个激活量化内核：约 164.6 µs。
- 内核和 −35.4%，但未插桩的端到端只有 −26%：剩余差额是图外固定开销与 fp8 路径额外的启动/同步。

于是“模型对不对”有了比残差更强的答案：**它在预测得到检验的局部精确成立，在它没覆盖的局部（`lm_head`、量化开销、固定尾部）不成立**。这也是报告干预结果时该写的形状——不是“−26%，比预测差”，而是“−26%，因为预测里隐含假设了 lm_head 也被量化”。

第二个干预是上下文长度：把所有实验都建在 128 token 的合成 prompt 上，attention 只占 7.7%，这本身就是结论的边界。把 prompt 拉到 2048 / 8192 后，decode 间隔从 4.2 → 7.3 ms（b1）、4.4 → 11.1 ms（b2），增量对应的 KV 读取速率是 280–317 GB/s，与权重流同一量级。**同一个“带宽受限”机制，在长上下文下作用于 KV 而不是权重**；attention 占比从 7.7% 升到 42.5%/60.5%。教训是：报一个百分比之前先问“分母里有哪些项是我固定住的”，固定的那一项会在别的负载里长大。

最后，`repro_l4.sh` 把这条链路压成一条命令。第一次冒烟测试时它没理会 `--dry-run`：PowerShell 写出的启动脚本是 CRLF，`"$@"` 之后多了一个 `\r`，转发出去的参数成了 `--dry-run\r`。看不见的行尾字符能让“参数没生效”伪装成“脚本逻辑错了”——跨系统写脚本时，换行符和编码要当作接口的一部分来检查。
