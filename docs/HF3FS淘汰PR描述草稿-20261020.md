## 正文要点（与线上一致）

- **目的**：池满后 `allocate_pages_for_keys` 无法回收页，每次 save 永久失败（issue #62389）。
  #62393 只阻止命中/重复 key 吃新页，不含淘汰。
- **为什么不能直接 LRU**：scheduler 在 worker 加载前用 `batch_key_exists`（`get_num_new_matched_tokens`）
  判定命中，worker 稍后才 `get_key_locations`；此时淘汰会把“命中”变成加载失败或读到别人的数据。
- **做法**：`POST /keys/acquire` 返回页位置并钉住 key，`POST /keys/release` 解钉；load 路径取租约后读、
  数据进 host buffer 立即释放（成功/缺键/读失败/异常四条路径都释放）；分配不足时只淘汰
  “complete + 无活租约 + 不是本次请求自己的命中（`exclude=cached_pages`）”的键，最旧优先，
  每 rank 还一页并删除 key；租约带单调时钟死线（默认 120 s，`--lease-ttl-s`）。
- **TTL 的依据**（来自 sivabreddy 在 #62389 的数据）：28k-token prompt 加载约 1.1 s，
  60k 约 1.9 s；一次 3FS 存储 pod 故障时加载停滞 16–18 s。默认 120 s 对观测到的停滞约有 7× 余量。
  **没做租约续期**：超过 TTL 的读者按“已死”处理，页被回收、请求失败，而不是永久钉住池子；
  若对方认为 pod 故障场景需要心跳续期，这是后续小改动（但会引入“续期卡住反而钉住页”的新失败模式）。
- **兼容**：`Hf3fsMetadataInterface.acquire_keys/release_keys` 有非抽象默认实现（普通查询 / no-op）；
  HTTP 客户端在 404/405 时回退到 `get_key_locations`（旧 server 从不淘汰，查询安全）。
- **测试**：上游测试文件新增 7 例（腾出页、租约保护、过期租约回收、跳过 partial、本次命中不淘汰、
  LRU 顺序、跨 rank 各还一页）；隔离 harness **25 passed**；真实 localhost HTTP 探针覆盖
  “全部键被租→分配失败”“释放一个→淘汰落在它身上”。
- **未验证**：真 3FS 上两实例共享一个 metadata server（对方愿测）、与 #61247 的边界（该 PR 改的是
  preemption 后的 block table，本 PR 不碰）、淘汰开销/命中率、connector 级单测（本机无 torch/GPU）、
  `pre-commit` 未跑。
- **AI 披露**：正文最后一节 + commit 的 `Assisted-by: DeepSeek Harness (AI coding agent)`。

## 审阅时要特别看的三处

1. `evict_lru` 里 `num_pages` 的单位：每个被淘汰的 key 在**请求方 rank** 上只还一页，
   所以“需要几页”就等于“淘汰几个 key”；若将来改成按 rank 各自计数，这里要跟着改。
2. `release_leases()` 先清标志再发 RPC：若反过来，RPC 失败后重试会把别人刚加的租约减掉。
3. 过期租约的语义：`lease_expiry > now` 才算“活着的读者”，等于说 TTL 到期即假定读者已死。
   这个假设必须写进文档，否则真实 3FS 上慢读会被误判。

## 第三方真机验证（2026-10-21，issue 作者 sivabreddy）

环境：vLLM v0.32.0 + 本 PR 的 `ed8a5db`（两个文件）+ #62465 的一行 metadata URL 修复；
Llama-3.1-70B-Instruct、TP4、block size 64；两台 H100 各一个实例（pod A 写、pod B 读），
共享一个 metadata server（本 PR 的 server，默认 TTL 120 s），3FS over FUSE + USRBIO；
池故意压到每 rank 2 GiB = 409 页；needle prompt 约 1,850 token，flood prompt 3,256 token（每个 50 个新键）。

| 检查 | 结果 |
|---|---|
| 池未满，B 从 3FS 加载 A 的 prompt | 1,792 / 1,850 token，答案正确 |
| 顺序 flood 12 个 prompt | 每个恰好淘汰 50 个键；4 个 rank 空闲页始终 0；B 能加载最新 3 个（各 3,200 token） |
| 并发 flood（8 个一批） | 同样能加载最新 3 个 |
| 池满后新 prompt | 4/4 写入并被 B 加载（1,792–1,856 token），答案正确 |
| flood 前的旧 prompt | 已被淘汰（B 从 3FS 取到 0 token），答案重算正确 |
| 租约保护（29 键 × 4 rank 持租不释放） | 未租的对照 0/29 留下，被租的 29/29 留下，加载 1,792 token 正确 |
| 过期租约 | 134 s 后的下一次 flood 回收了它（0/29，`leased` 计数 0） |
| 错误计数 | 两实例的保存/加载失败均为 0，28 次 needle 检查 0 个错答案 |

他的两条观察：
1. 死线取同一键上所有租约的最晚者；从不释放的租约持续到“没有读者再碰它之后一个 TTL”
   （他 acquire 后约 10 s B 又读了该 prompt，于是 125 s 时 29 个键里 28 个仍算被租，134 s 才淘汰）。
   → 已写进 `acquire_keys` docstring，并加测试 `test_overlapping_leases_keep_the_key_pinned`（`c9b2b40`）。
2. 一度未复现的异常：更大的并发 flood（60 个 prompt、约 5× 池）后 15 s，B 找不到最新 3 个 prompt，
   且 rank 0 空闲页 100、rank 1–3 各 50。**后续由他自己用日志解释清楚：是测试时序，不是本 PR**。
   时间线：writer 的保存请求在 12:24:19–21 调度、12:24:41–46 才在 4 个 rank 上完成，保存队列落后于
   prefill；读者在 12:24:37–39 去查，此时保存仍在排队，scheduler 记录 **0 matched blocks**，miss 出在
   scheduler 而不是 worker；该窗口 writer 的 `num_save_task_failed=0`、无 `Page allocation failed`；
   metadata server 的 `Evicted key` 一直打到 12:24:48，与迟到的保存吻合。结论：不需要 debug 日志，
   `c9b2b40` 保持原样；他下一次会等 writer 保存队列清空再检查。

同一窗口的旁证：读者自己也算并保存了那 3 个 prompt（12:24:38–40），而 writer 的保存在排队。
服务端对已 complete 的键走 `cached_pages` 分支，**第二个 writer 拿到同一页并覆写**，所以没有泄漏页、
也没有报错；但服务端不串行化两个 writer 的写。同一 key 的 KV 内容应相同，若不同则是静默损坏
（未观测到）。要彻底排除需要写租约，本 PR 不做，已记入设计文档 §9.5。

未覆盖：真实读者进程在读中被杀（他用 HTTP 直接持有租约模拟停滞）、淘汰对吞吐/命中率的影响、
同 key 并发双写的串行化。
