# 第二阶段：形状归因与 min-p 候选

本轮完成了第一层主要线性层的真实输入形状观测，以及一个接入 MRV2 采样路径的 Triton min-p 优化候选。结果限于当前固定 vLLM、Qwen3-0.6B 稠密文本模型及 RTX5060Laptop/WSL；没有服务器结果或上游 PR。

## 主线：先核实际矩阵形状

[shapes-20261017T070340Z](../results/shapes-20261017T070340Z/shapes.json) 使用 eager 诊断和第一层 forward-pre-hook，实际提交两条32-token输入并生成4token，观察到 prefill 的 M=64 与 decode 的 M=2。下表采用 `X[M,K] × W[N,K]^T` 的定义。

| 第一层模块 | Decode M | N | K |
|---|---:|---:|---:|
| qkv_proj | 2 | 4096 | 1024 |
| o_proj | 2 | 1024 | 2048 |
| gate_up_proj | 2 | 6144 | 1024 |
| down_proj | 2 | 1024 | 3072 |

模型有28层；lm_head 的实际权重为 [151936,1024]，本轮仅采其权重元数据，未用该 hook 捕获 head 的运行输入。不能把这些 eager 形状观测称为已将编译版 trace 的每个 GEMM 逐一归属到具体层。配置导出确认该诊断引擎 async_scheduling=True。

初次函数式 apply_model RPC 被框架默认序列化策略拒绝，失败日志 shapes-20261017T070218Z 保留。改用公开 worker extension 和字符串 RPC 后通过，没有启用不安全序列化。

## 副目标：min-p 过滤

真实路径：MRV2 Sampler → apply_sampling_params → SamplingStates.apply_min_p → min-p kernel。非零 min_p 是正式支持的请求参数；之前的 temperature=0、min_p=0 基线不会因此变快。

原实现每行一个线程块，按1024元素分块串行遍历整个词表求最大值，再串行过滤。候选[内核](../kernels/min_p.py)改为两阶段：并行求部分最大值；再并行归约部分结果并过滤。总体仍需扫描 logits 两次，还多出一次启动和临时缓冲区；收益来自更多并行，不是减少了两次扫描。

最终候选派发仅在行数1～8、词表至少32000且列连续时启用，其余调用原实现。适用性能证据只覆盖已测的词表/形状，本轮没有验证所有更大词表或其他模型；未来扩展范围需补实验。临时部分最大值的逻辑大小在 batch8/V151936 下为1216字节，不含分配器开销。

## 正确性证据

- [局部验证](../results/minp-micro-20261017T070433Z/correctness.json)：96组，FP32/FP16/BF16、多个词表尾界、batch1/2/8、行 padding、请求映射和混合 min_p，以及负无穷、正无穷、NaN等特殊值。两阶段本体对真实上游函数的输出及 padding 逐字节一致。这是兼容性对照，不是独立证明上游全部数学行为正确。
- [真实引擎调用](../results/minp-engine-20261017T070614Z/real-verification.json)：4次 [2,151936] FP32 logits 完整比较，零不一致；保留输入、参考及候选输出，合计1,215,488个输出位置。
- [独立复核](../results/minp-engine-20261017T070614Z/independent-check.json)：重新读保存张量，分别重跑原版与候选并逐字节核对；同时检查计时记录 SHA、输出ID和 trace 内核分派。
- min_p=0 的真实引擎请求两臂均未调用 min-p，生成 ID 一致；见 disabled-path.json。
- 两个独立引擎进程的48条正式批次记录，各自覆盖 ABBA/BAAB，固定每请求seed，两臂完整输出 ID 一致。不是模型任务质量评估，也不代表所有采样参数组合均验收。

候选通过本项目 worker extension 安装到真实 SamplingStates 调用别名，未修改上游 checkout。它是可运行的受控接入候选，尚非对外发布的生产补丁。

## 局部计时与真实调用证据

局部使用 FP32、Triton do_bench、CUDA events，每次计时前清L2；ABBA各两份统计。下表为两阶段本体的中位计时统计，单位微秒，不能直接等同 GPU 内核累计时间或整请求耗时。

| V151936 | 原版 µs | 候选 µs | 比值 |
|---|---:|---:|---:|
| batch1 | 116.06 | 11.97 | 9.70× |
| batch2 | 122.90 | 14.02 | 8.77× |
| batch4 | 125.02 | 20.13 | 6.21× |
| batch8 | 124.02 | 32.68 | 3.79× |

V4096/batch2～8候选约慢14%，V151936/batch32几乎没有收益，因此没有全范围替换。V4096/batch1的原版统计有异常波动，不据其单点下结论。原始60条计时保留在 timing.jsonl。

真实引擎 trace 内：原版12次 `_min_p_kernel`；候选12次部分最大值＋12次过滤内核，原版内核计数为0。两段累计 min-p kernel 时间约750.37/67.20µs，属于带 profiler 的记录，不作为未插桩速度。两个 trace 文件名都沿用了 base 前缀，因此按内核内容识别两臂，映射与 SHA 保存在 independent-check.json，未重命名原件。

## 整请求结果：小幅变化，限制结论

两轮为独立引擎进程，同进程内两臂交替。每组每臂4次正式运行，128-token合成输入、固定输出128token，temperature=.8、min_p=.05、显式seed、prefix cache关闭；两臂均正常开启编译和图机制。warmup、数值比较和 profiler 不计入下表。

| batch | 进程1 wall中位数 原版→候选 ms | 变化 | 进程2 原版→候选 ms | 变化 |
|---|---|---:|---|---:|
| 1 | 543.18→528.36 | −2.73% | 520.80→520.13 | −0.13% |
| 2 | 574.83→570.89 | −0.69% | 552.43→546.58 | −1.06% |
| 4 | 590.99→584.61 | −1.08% | 583.41→577.49 | −1.01% |

原件为 [minp-engine](../results/minp-engine-20261017T070614Z/summary.json) 与 [minp-repeat](../results/minp-repeat-20261017T070817Z/summary.json)。batch1跨进程变化较大，不能声称稳定2.7%收益；batch2/4观察到约1%的小幅变化，样本仍少，没有置信区间。不能从局部倍数宣称整模型数倍提速，也不能据此推广到服务器。
