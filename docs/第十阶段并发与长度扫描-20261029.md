# 第十阶段：并发与输出长度扫描——把「单点 TTFT/TPOT」换成两条曲线

日期：2026-10-29。前置：[第八阶段](第八阶段serve延迟指标-20261023.md)（固定并发 8 的
ABBA 服务口径）、[第七阶段](第七阶段batch扩展与min-p路由-20261022.md)（8 行收益悬崖）。

## 1. 目标与边界

前八/九阶段只量了一个点：并发 8、输出 64 token、单轮 64 条请求。面试里真正会被追问的是
“并发上来以后呢”——TTFT 被谁拿走、TPOT 什么时候开始变贵、吞吐在哪个并发饱和、输出长度
改变的是哪一项。这一阶段不写内核、不改补丁，只用现成的 `vllm serve` 测两条曲线：

- **并发轴**：并发 1/2/4/8/16/32，输出固定 64 token，prompt 固定 128 token；
- **长度轴**：输出 64/256 token，固定在并发 8。

`min_p=0.1` 打开，让 min-p 路径留在关键路径上；内核用上游实现（本阶段不比较实现优劣）。
窗口与限制照旧：单卡 8 GB、Qwen3-0.6B、fp16、`max-model-len 2048`、`max-num-seqs 32`、
`gpu-memory-utilization 0.6`、合成 prompt。

## 2. 方法

`scripts/serve_scan.py`（stage `serve-scan` / `serve-scan-quick`）复用 `serve_stage.py` 的
`start_server/stop_server/wait_health/one_request/describe`，单 server 只起一次：

- 每个 cell 至少 4 波请求，`请求数 = max(24, 4 × 并发)`；每波内并发发完再进下一波，
  与第八阶段同一种负载形状（固定并发、非开放环）。
- **每个 cell 用全新 prompt 池**（`np.random.default_rng(seed_base + 1000 × cell)`）：prefix caching
  默认开启，若跨 cell 复用 prompt，后一个 cell 的 prefill 会被缓存接走，长度轴就废了。
- 客户端逐请求记录 TTFT / ITL / TPOT / 总时延（`httpx` 流式，`min_tokens=max_tokens`、`ignore_eos`）。
- 每个 cell 前后各抓一次 `/metrics`（`metrics/<cell>-{before,after}.txt`），用
  `_sum`/`_count` 的差算**引擎侧** TTFT/queue/prefill/decode/TPOT，以及 preemptions、
  prefix cache 命中、generation tokens。客户端数字和引擎侧数字并排放，才能分清“慢在排队、
  慢在 prefill、还是慢在每步 decode”。
- 启动一次 warmup（并发 = 最大 cell 并发，32 条并发请求），避免首波编译/捕获污染第一格。

运行：`bash scripts/run_stage.sh serve-scan`，exit 0，8/8 cell 通过（`status.json` passed=true）。

## 4. 读法

1. **吞吐在 1→32 并发内近似线性**：2.79 → 46.09 req/s、179 → 2950 tok/s，都是 16.5×；
   而 TPOT 只从 5.08 涨到 8.81 ms（+73%）。也就是说 c32 时每步 decode 贵了七成，但一步里
   塞进了 32 倍的 token——摊薄之后仍然是净赚。0.6B 在 8 GB 卡上到 32 并发都没进入算力饱和。
2. **TTFT 的大头是 prefill，不是排队**：c1→c16 引擎 queue 一直是 0.0x ms，prefill 却从
   22.3 涨到 56.9 ms。原因是 prefill 也按 batch 合批，批越大单次 prefill 越慢（chunked prefill、
   更大的矩阵、更多的 KV 写入）。**到 c32 才第一次出现真正的排队**（queue 6.48 ms，占引擎 TTFT
   的 5.3%）——因为 c32 正好顶到 `max-num-seqs=32`，再往上就是排队而非合批。
3. **TPOT 的上升是 decode 的边际成本**：5.08 → 8.81 ms。这和第七阶段“batch 16/32 的 min-p
   路由收益归零”是同一枚硬币的两面：batch 变大后每步里的固定开销被摊薄，而 GEMM/KV 读写变重。
4. **输出长度只改总时延，不改每 token 成本**：64→256 token，总时延 489→1667 ms（3.41×，
   4× token），TPOT 6.75→6.35 ms（反而略降），TTFT 基本不动（prefill 由 prompt 长度决定）。
   tok/s 反而 +15%：长输出把 prefill 和调度开销摊得更薄。**长度轴的结论是“线性”，不是“更长更慢”。**
5. **同配置跨时段不可直接比**：`len64` 和 `c8` 是同一配置，TTFT 63.9 vs 54.8、TPOT 6.75 vs 5.83
   （+15%），因为前者跑在 6 个 cell 之后（GPU 温度/时钟、KV 缓存状态都变了）。所以长度轴内部
   只做 len64 vs len256 的相邻比较；跨 cell 的绝对差要按 ±15% 读，不能当因果。
6. **c8 的 p99 = 140 ms 是个尾部异常**（c16 的 p99 反而只有 100.6），最可能是该 cell 首波撞上
   某个慢请求/调度抖动。单次运行不下结论，只记录；要下结论得重复 3 次看 p99 的分布。

## 5. 限制与未验证

- 只在 **一张 8 GB 卡、0.6B、fp16、单机** 上测；并发上限被 `max-num-seqs=32` 卡住，
  没有测 64/128 并发（要改 `--max-num-seqs` 并确认 KV 够）。
- prompt 是**合成 token id**（128 token），不是真实 workload 的长度分布；输出固定 64/256，
  没有混合长度到达过程（开放环/泊松到达未做）。
- prefix cache 命中率在本轮不可用（`vllm:prefix_cache_queries` 差值取不到，summary 里为 null），
  所以“新 prompt 池是否真的躲开了缓存”只能靠构造保证，没有指标旁证。
- 没有 GPU 侧 counters（SM 占用、DRAM 带宽、KV 读写量）；“prefill 变慢是合批”是从引擎
  分项推的机制假设，不是 NCU 证据。
- 单次运行，噪声地板按第八阶段经验约 ±2%（会话级），跨时段 ±15%；所有差值都在这个前提下读。

## 7. 下一步

1. 把 `--max-num-seqs` 提到 64/128，找吞吐真正饱和的拐点（以及 queue 占比何时超过 prefill）。
2. 每个 cell 重复 3 次，给出 p99 的置信区间，替掉现在的单次读数。
3. 用 NCU 看 c1/c16/c32 的 decode 步：SM 占用、DRAM 吞吐、KV 读写占比，把“TPOT 变贵的机制”
   从推断变成证据。
4. 如果要接真实 workload，加混合长度与到达过程（开放环），否则曲线只代表“同步固定并发”。

### 8.2 三条结论

1. **吞吐在 c64–c128 之间饱和**：3.0 → 16.6（c8）→ 45 → 58 → 64 req/s。从 c64 到 c128
   并发翻倍，吞吐只 +10.7%（57.8 → 64.0），TPOT 却从 13.4 涨到 23.7 ms（+77%）。
2. **队列开始成为 TTFT 的主体**：queue 占比 0.001（c1）→ 0.07（c32）→ 0.25（c64）→ 0.47（c128），
   到 c128 时 TTFT 的 47% 是在排队等槽位，而不是 prefill。这正是 `max-num-seqs=128`
   把等待从“KV 不够”换成了“并发槽位不够”的证据。
3. **重复暴露了首跑污染**：c8-r0 的 TTFT p99 1736 ms、c32-r0 3041 ms，而同一 cell 的
   r1/r2 只有 61/184 ms。warmup 只跑了一轮、并发 128（覆盖 128 这一档），c8/c32 桶第一次
   被用到时落在测量里，疑似 CUDA graph 按 batch 桶惰性捕获的开销（未抓时间线证实）。
   **后两轮才是干净读数**，聚合表用“p50 中位数 + p99 min..max”把这一点显式暴露出来，
   而不是抹平。
