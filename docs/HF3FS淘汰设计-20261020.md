# HF3FS 页淘汰：设计选项与验证边界（2026-10-20）

## 0. 触发

- 他可以用“两个 vLLM 实例共享一个 3FS metadata server”来测。

这是一次明确的邀请，也把范围划清了：剩下的是**页回收**，不是分配。

## 1. 为什么不是“加二十行 LRU”

上一轮读源码的结论（[分配修复与发布检查](HF3FS分配修复与发布检查-20261019.md)）：

- scheduler 在 worker 真正加载之前就用 `batch_key_exists` 计算“外部命中”，
  所以“key 存在”和“页还能被安全读取”是两个时间点上的事实；
- 只在 `get_key_locations` 之后加锁仍有一个窗口：
  scheduler 决定命中 → 淘汰覆写这一页 → worker 加载失败或读到错数据；
- worker 侧失败完成不会自动让 scheduler 重新计算，那条请求会直接错。

因此“complete key 可以淘汰”这句话，必须补一个**读者在途**的判据，否则淘汰会把
hit 变成错数据——这比“保存失败”严重。

## 2. 三种候选机制

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| A. 租约/引用计数 | lookup 时 +1，读完 −1；只淘汰 refcount==0 且 complete 的 key | 不变量最少、易推理 | 进程崩溃会泄漏租约，需要 TTL 兜底与恢复扫描 |
| B. epoch 代际 | 淘汰只标 stale，延迟删除；reader 发现 epoch 变化就重试 | 无租约状态机 | 要求 reader 有重试路径，错误分支变多 |
| C. 调度器可见集 | scheduler 把已决定命中的 key 上报为 pinned，server 只淘汰非 pinned | 语义直接 | 需要跨 rank 聚合与请求生命周期衔接 |

**建议第一阶段做 A**：它的不变量可以逐条写出来（见第 3 节），而且能退化——
租约超时即等价于“只淘汰确定没人读的页”，先保证正确性，再谈命中率。

## 3. 必须先写清的不变量

- **I1** 页只能从 free list 分配；淘汰回收的页必须重置后才能再分配。
- **I2** 只有 complete key 可淘汰；partial key 归写入方（与 #61247 的边界）。
- **I3** 任何可能被读者使用的 key 不得淘汰（租约或 epoch 保证）。
- **I4** key 移除与页回收要么全成功、要么全失败；崩溃后可用启动扫描修复。
- **I5** 多实例/多 rank 共享同一 server 时，上述不变量由 server 串行化保证。

I3 是全部难点；I4 决定崩溃恢复要不要写。

## 4. 我们能与不能验证的

**能**（本机、已有资产）：隔离元数据测试（uvicorn 假 server）、双客户端并发
（模拟两个实例）、真实 HTTP、受控 GPU 保存/加载、客户端被 kill 后的租约到期。

**不能**：真实 3FS 后端、真实集群多 rank、淘汰本身的开销、长时间稳定性。

他提的“两个实例共享一个 metadata server”正好覆盖 I3/I4/I5 的最小场景；
他有真 3FS，我们没有——所以分工应该是：我们出协议级正确性 + 受控后端证据，
他做最终验收。

## 6. 风险

- 与 #61247（writer 排空、ownership-ambiguous 页回收）撞车 → 先读它的实现再定边界。
- 租约 TTL 太短会误淘汰，太长则满池恢复慢 → 要给默认值和可配置项。
- 我们只能做到“协议正确 + 受控后端”，最终验收依赖对方；可能白做。
- 成本：设计 1 轮、实现 1–2 轮、测试 1 轮。

### 9.1 server：租约 + LRU

`hf3fs_metadata_server.py`：

- `KeyMetadata` 增加 `lease_count`、`lease_expiry`（monotonic 截止时间）。
- `GlobalMetadataState` 增加 `_lru: OrderedDict`（只放 complete key）、`evicted_keys`、
  `lease_ttl_s`（默认 120 s，`--lease-ttl-s` 可调）。
- `acquire_keys(rank, keys, ttl_s)`：complete 且该 rank 有页才返回页号，同时
  `lease_count += 1`、`lease_expiry = max(..., now + ttl)`、刷新 LRU；
  key 缺失返回 `None`，语义与 `get_key_locations` 一致，调用方可直接替换。
- `release_keys(rank, keys)`：`lease_count -= 1`，归零时清 expiry。
- `evict_lru(num_pages, exclude)`：按 LRU 顺序，跳过 live lease、跳过 `exclude`
  （本次请求自己命中的键）、跳过 partial key；过期租约视为读者已崩溃并回收；
  逐 rank `release_pages` 后删除 key。
- `allocate_pages_for_keys`：free 不足时先 `evict_lru(缺页数, exclude=cached_pages)`，
  再走原有分配逻辑；仍不足则保持原来的“返回 -1 + 警告”。
- HTTP 增加 `POST /keys/acquire`、`POST /keys/release`；`Hf3fsMetadataInterface`
  的 `acquire_keys`/`release_keys` 有**非抽象默认实现**（退化为 `get_key_locations`
  与 no-op），因此 mock/单机 client/其他后端不会被破坏。

### 9.2 connector：加载路径持租约

`AsyncOperationManager._handle_load_task` 把 `get_key_locations` 换成
`acquire_keys`，并加一个局部 `release_leases()`（先清标志再发 RPC，避免失败重试误放
别的读者的租约）；三条失败路径（key 缺失、读失败、异常）与成功路径都会释放，
成功路径在数据进 host buffer 后立即释放，scatter 不再依赖这些页。

### 9.3 测试与证据

`tests/v1/kv_connector/unit/test_hf3fs_metadata_server.py` 新增
`TestGlobalMetadataStateEviction` 共 8 例：新键触发淘汰、租约保护、重叠租约（一个读者
释放不解开另一个）、过期租约回收、跳过 partial key、本次请求命中不淘汰、LRU 顺序
（acquire 刷新位置）、跨 rank 淘汰每 rank 各还一页。

隔离 harness（复制源文件与上游测试、只改 import、`--noconftest`）结果：

第三方分配仍返回 -1；释放其中一个后，淘汰落在被释放的那个键上，另一个保留。

### 9.4 第三方真机验证（2026-10-21，issue 作者 sivabreddy）

vLLM v0.32.0 + 本 PR 的 `ed8a5db`，Llama-3.1-70B TP4、block 64，两台 H100 各一实例共享
一个 metadata server（真 3FS over FUSE + USRBIO），池压到每 rank 409 页。结论：池满后
保存继续成功、旧 prompt 被淘汰、最新 3 个可加载；被租的 29/29 键存活、未租对照 0/29；
过期租约在 134 s 后的下一次 flood 被回收；28 次 needle 检查 0 错答案，两实例保存/加载
失败计数均为 0。他提出的“死线取同键所有租约的最晚者”已写进 docstring 并用测试钉住。

他一次未复现的异常（60-prompt flood 后最新 3 个找不到、空闲页 100/50）后来由他自己用日志
解释清楚：**是测试时序**——writer 的保存队列落后于 prefill，读者在保存排队期间去查，
scheduler 记录 0 matched blocks；窗口内保存失败计数为 0，metadata server 的
`Evicted key` 一直打到 12:24:48，与迟到的保存吻合。不需要改代码。

同一窗口的旁证：读者自己也算并保存了同样 3 个 prompt，而 writer 的保存在排队。服务端对
已 complete 的键走 `cached_pages` 分支，**第二个 writer 拿到的是同一页并覆写**，所以没有
泄漏页、也没有报错；但服务端并不串行化两个 writer 的写。同一 key 的 KV 内容应当相同，
若不同则是静默损坏（未观测到）。要彻底排除需要写租约，本 PR 不做。

### 9.5 仍然缺的

- 同一 key 的并发双写没有写租约/串行化（同上；只在“同 key 内容必然相同”的前提下安全）；
- 真实读者进程在读中被杀（对方用 HTTP 直接持有租约模拟停滞）；
- 淘汰对吞吐与命中率的影响（本实现只保证正确性）；
- 与 #61247（writer 侧排空/回收）的边界仍按“互不重叠”处理，未联合测试。
